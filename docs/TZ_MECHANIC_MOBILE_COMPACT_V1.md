# TURBO LEV — Кабінет механіка Mobile Compact V1

Дата: 2026-09-15
Статус: реалізовано в `feat/mechanic-mobile-compact-ui`

## 1. Проблема

На смартфонах кабінет механіка візуально поводився як desktop/tablet-композиція, стиснута до ширини телефону. На ширинах приблизно 390–430 px це створювало такі проблеми:

- великі вертикальні відступи та завелика висота карток;
- фільтри «Усі / Протерміновані / Сьогодні / Майбутні» займали два рядки, а довгий текст ламався;
- на першому екрані було видно занадто мало робіт;
- номерний знак та status pill конкурували за горизонтальний простір;
- hero-шапка і нижня навігація забирали надто багато корисної висоти;
- інтерфейс виглядав як адаптований веб-сайт, а не як робочий мобільний застосунок механіка.

## 2. Мета

Зробити mobile-first presentation layer для кабінету механіка без зміни бізнес-логіки, API, маршрутів, статусів та робочих процесів.

Пріоритет механіка на телефоні:

1. яка машина;
2. що потрібно зробити;
3. коли/на якому посту;
4. яка наступна дія.

## 3. Межі змін

Змінюється лише presentation layer:

- `app/mechanic-live-cabinet.tsx` — додає окремий scope-контейнер;
- `app/mechanic-mobile-compact.module.css` — mobile-first overrides;
- бізнес-логіка `MechanicStandaloneCabinet`, API, scanner bridge, diagnostics bridge і task workflow не змінюються.

Desktop/tablet понад 600 px залишаються на чинній верстці.

## 4. Mobile breakpoints

### <= 600 px

Основний mobile режим:

- бокові відступи: 12 px;
- вертикальний gap: 10 px;
- hero: приблизно 82 px + safe area;
- top bar: приблизно 58 px + safe area;
- картка наступної/протермінованої роботи: компактна, без зайвого повітря;
- primary action: мінімум 44 px;
- номерний знак у списках і featured task: 28 px по висоті;
- bottom navigation: приблизно 64 px + safe area;
- фільтри робіт: горизонтальні chips без переносу на другий рядок.

### <= 390 px

Compact-phone режим:

- бокові відступи: 10 px;
- hero ще компактніший;
- шрифти заголовків зменшуються на 1–2 px;
- chips стають нижчими;
- номерний знак у списках: 26 px по висоті.

## 5. Екран «Головна»

### Hero

- логотип зменшений;
- назва «ТУРБО ЛЕВ» компактніша;
- підпис «Кабінет механіка · Імʼя» 12 px;
- кнопка сповіщень 42 × 42 px.

### Featured task

- padding 12 px;
- radius 14 px;
- назва авто 17 px;
- status pill максимум 116 px;
- робота та метадані ущільнені;
- CTA 44 px мінімум.

### «Мої роботи»

- картка секції 12 px padding;
- рядок роботи приблизно 54 px мінімум;
- статус не повинен виштовхувати номер/назву за межі viewport;
- номерний знак зменшений до mobile size.

## 6. Екран «Мої роботи»

Фільтри:

- один горизонтальний ряд;
- swipe/scroll по горизонталі;
- кожен chip `min-width: max-content`;
- текст не переноситься;
- висота 38 px (36 px для <= 390 px).

Картки:

- padding 11–12 px;
- radius 14 px;
- проблема/опис 13 px;
- meta 11 px;
- status pill 10 px;
- автомобіль не переноситься без потреби, довгий текст обрізається через ellipsis.

## 7. Safe area

Обов’язково враховуються:

- `env(safe-area-inset-top)`;
- `env(safe-area-inset-bottom)`.

Bottom navigation не повинна конфліктувати з Home Indicator iPhone/Safari.

## 8. Доступність

- touch targets основних дій не менше 44 px;
- горизонтальні фільтри зберігають native scrolling;
- існуючі `aria-label` та keyboard semantics не змінюються;
- `prefers-reduced-motion` поважається.

## 9. Acceptance criteria

На 390, 393, 414 і 430 px:

- немає горизонтального overflow основної сторінки;
- фільтри не переходять у два рядки;
- «Протерміновані» не розривається всередині слова;
- номерний знак і status pill не виходять за межі картки;
- на першому екрані видно featured task і початок списку «Мої роботи»;
- bottom navigation не перекриває контент;
- бізнес-логіка старту/паузи/завершення роботи не змінюється.

На ширинах > 600 px чинний layout не повинен візуально змінитися.

## 10. Реалізаційний принцип

Новий CSS scoped через `MechanicLiveCabinet`, а правила активуються тільки до 600 px. Для точкового mobile override використовуються стабільні семантичні атрибути чинного DOM (`data-mechanic-cabinet`, `aria-label`) замість втручання у workflow-компонент. Це дозволяє відокремити мобільну щільність від бізнес-логіки та мінімізувати regression risk.
