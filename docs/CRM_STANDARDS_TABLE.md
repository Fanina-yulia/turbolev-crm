## 2. Технічне завдання `CRM-AUDIT-001`

### 2.1. Мета

Підтвердити, що CRM працює як одна наскрізна система СТО, а не як набір ізольованих сторінок. Аудит повинен виявляти не лише помилки конкретного екрану, а й розриви між модулями: втрачені дані авто, неправильні ролі, неповні переходи статусів, відсутні сповіщення, дублікати та регресії інтерфейсу.

### 2.2. Обов'язковий обсяг

Перевіряються всі модулі реєстру:

| Група | Модулі та контрольні питання |
|---|---|
| Core | Auth, routing, shell, permissions, ролі, помилки 401/403, міграції, build/deploy |
| Огляд | Dashboard та аналітика: показники, джерела даних, порожні й помилкові стани |
| Клієнт і авто | Створення/редагування, VIN/номер, власник, пошук, дублікати, зображення авто |
| Вхідний потік | Lead, заявка, конвертація в Client + Vehicle, запис і повторне натискання |
| Планувальник | День/тиждень, пости, механік, конфлікти, перенесення, ARRIVED |
| Діагностика | Створення, призначення, findings, ДК, оплата, коментар механіка, статуси |
| Ремонт | Work Order, роботи, деталі, погодження, QC, фінансові gates |
| Кабінети | Сервіс-менеджер, механік, клієнтський кабінет, mobile flow і права |
| Деталі та склад | Підбір за ДК/VIN, пропозиції, постачальник, ціна, замовлення, залишки |
| Фінанси | Оплати, balance due, нарахування, доступ до фінансових даних |
| Зображення | Пошук готового asset, генерація fallback, кешування, WebP, повторний запит |
| Сповіщення | Створення, адресат, unread/read, deep link, відсутність висячих повідомлень |
| Комунікації | Телефонія, callback, канали, зв'язок із клієнтом/лідом, graceful fallback |
| Налаштування | Збереження, credentials, інтеграції, маскування секретів, permissions |

### 2.3. Рівні перевірки

1. **Структурна:** маршрути, навігація, таблиця модулів, відсутність unmapped production files.
2. **Функціональна:** create/read/update, порожні стани, повторне натискання, помилки, скасування та повернення назад.
3. **Наскрізна:** Lead → Client/Vehicle → Planner → Diagnostics → Diagnostic Card → Parts → Quote → Payment → Work Order → QC → Closed.
4. **Дані:** VIN/номер/власник/зображення не губляться і не змішуються між модулями; дублікати не створюються.
5. **Доступ:** дозволені та заборонені ролі, location scope, прямий API-виклик без сесії, неправильний scope.
6. **Інтерфейс:** цілісна сторінка, читабельність, responsive layout, keyboard/focus, повідомлення про помилки.
7. **Інтеграції:** Telegram, клієнтський кабінет, зображення, телефонія та зовнішні API; перевірка успішного і недоступного сервісу.
8. **Реліз:** TypeScript, production build, міграції, preview, production HTTP/runtime smoke та перевірка фактичної версії.

### 2.4. Обов'язковий стандарт цілісної сторінки

Для робочої CRM-сторінки:

- вертикальна прокрутка відбувається на рівні документа;
- `.list`, `.detail`, `.workspace`, `.shell`, картка, header і action bar ростуть разом із контентом;
- не використовуються `position: sticky/fixed`, `height/max-height: calc(100vh...)` або `overflow: auto/scroll` для основного контенту сторінки;
- сторінка не обрізає нижні блоки, кнопки, коментарі, деталі, фото чи історію;
- на mobile сторінка переходить в один стовпець без накладання нижньої навігації на робочий контент;
- виняток допускається тільки з письмовим обґрунтуванням у ТЗ і не поширюється на сусідні робочі блоки.

### 2.5. Viewport-матриця

Visual smoke виконується мінімум на ширинах `1920`, `1440`, `1280`, `1024`, `768` і `390` px. На кожній ширині перевіряються:

- відсутність внутрішньої вертикальної прокрутки в основному робочому контенті;
- відсутність горизонтального overflow у body/workspace;
- доступність заголовка, основних даних, дій і нижнього блоку;
- коректне перенесення довгих VIN, номерів, імен, коментарів і назв деталей;
- відсутність накладання sticky/fixed елементів на поля та кнопки.

### 2.6. Матриця негативних перевірок

Аудит обов'язково містить перевірки, які повинні завершитися відмовою:

- API без сесії — `401`;
- API без permission або scope — `403`;
- неправильний VIN/держномер — дія не змінює запис;
- повторне створення/подвійне натискання — не створює дубль;
- відсутній asset зображення — запускається дозволений fallback, але UI не зависає;
- недоступна інтеграція — зрозумілий стан помилки, без втрати локальних даних;
- вміст сторінки довший за viewport — документ прокручується цілісно, внутрішній page scroll не з'являється.

### 2.7. Критерії приймання

Аудит вважається пройденим, якщо:

1. Перевірено всі модулі з реєстру та їхні заявлені залежності.
2. Пройдено build, TypeScript, security inventory, contract/smoke checks і production runtime check.
3. Наскрізний сценарій не втрачає Client, Vehicle, VIN, держномер, owner, Diagnostic Card, деталі, оплату та сповіщення.
4. Немає P0/P1 дефектів; P2 мають бути зареєстровані з відповідальним і строком.
5. На всіх viewport із матриці робочі сторінки є цілісними та не мають небажаних фіксованих секцій.
6. Результат містить список перевірених модулів, знайдені дефекти, evidence, commit/deployment і висновок `PASS` або `FAIL`.

### 2.8. Артефакт результату

Для кожного повного аудиту формується звіт за структурою:

| Поле | Значення |
|---|---|
| Scope | Усі модулі з `docs/modules/module-registry.json` |
| Commit / deployment | SHA коміту та production URL |
| Checks | Команди й результат кожної перевірки |
| Findings | ID, модуль, severity, кроки відтворення, evidence |
| Cross-module impact | Які сутності, API, ролі та інтеграції зачеплені |
| Decision | `PASS`, `PASS WITH P2`, або `FAIL` |
| Owner / follow-up | Відповідальний і наступна дія для кожного дефекту |

## 3. Порядок застосування правила

1. Будь-яка зміна спочатку отримує модуль і залежності в `module-registry.json`.
2. Якщо користувач просить перевірити всю CRM або зміна зачіпає auth, permission, спільну сутність, workflow, API-контракт чи глобальний UI — запускається `CRM-AUDIT-001`.
3. Перед merge обов'язково запускається автоматична перевірка цілісних сторінок.
4. Перед production — повний набір CI/build і runtime smoke.
5. Новий виняток із правила `CRM-UI-001` додається до цього ТЗ до внесення CSS/компонента, із зазначенням причини та межі винятку.
