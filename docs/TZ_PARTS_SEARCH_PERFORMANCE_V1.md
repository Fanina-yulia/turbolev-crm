# Технічне завдання: швидкий і керований пошук деталей

Версія: 1.0  
Дата: 09.09.2026  
Модуль: «Підбір запчастин» / «Комерційна пропозиція»  
Система: Turbo LEV CRM  
Статус: реалізовано в цьому релізі

## 1. Мета

Забезпечити швидкий пошук оригінальних деталей та аналогів для конкретного автомобіля, не втрачаючи вимоги бізнес-процесу:

- пріоритет ідентифікації автомобіля — `vehicleId` і VIN;
- пошук за номером деталі та назвою;
- обов’язкове ручне підтвердження, якщо сумісність не підтверджена VIN/каталогом;
- окремий результат для кожної деталі, постачальника, артикула та складу;
- одночасна підтримка BM Parts, Юнік Трейд та майбутніх постачальників;
- автоматична ціна продажу за чинними правилами CRM, базово закупівельна ціна × 1,40;
- коректний частковий результат, якщо один постачальник повільний або тимчасово недоступний.

## 2. Проблема та evidence

До зміни один клік у вікні підбору створював два послідовні HTTP-запити:

1. `/api/parts/search` — fitment, VIN-контекст, довідковий каталог і нормочас;
2. після його завершення `/api/parts/suppliers` — повторний fitment і пошук у постачальників.

У production-логах зафіксовано `Vercel Runtime Timeout Error: Task timed out after 30 seconds` для `/api/parts/search` і `/api/parts/suppliers`, включно з відповідями `504`.

Додаткові причини затримки:

- `resolvePartFitment` міг повторно звертатися до БД, BM Parts і VIN-сервісу;
- BM Parts послідовно перебирал фільтри авто, варіанти пошукової назви та режими наявності;
- кожен запит BM Parts мав тайм-аут 12 секунд;
- звичайний пошук постачальника міг розмножувати один запит до 7–10 запитів на кожен адаптер;
- одночасні запити Юнік Трейд могли повторно виконувати login_check;
- інтерфейс очищав кількість налаштованих API на початку пошуку, тому показував помилкове `0 API підключено`.

## 3. Цільовий сценарій

```text
Потреба з ДК
  -> один клієнтський запит /api/parts/search?includeSuppliers=1
  -> паралельно: fitment + нормалізація + довідковий каталог
  -> один fitment-контекст для всіх наступних операцій
  -> обмежений паралельний пошук BM Parts / Юнік Трейд
  -> часткові пропозиції + статус кожного постачальника
  -> ручне підтвердження для непідтверджених позицій
  -> вибір деталі та формування КП
```

Підбір не об’єднує однакові деталі між постачальниками: кожна пропозиція зберігає власні `supplierId`, постачальника, артикул, склад, закупівельну ціну та статус сумісності.

## 4. Функціональні вимоги

### 4.1. Контекст пошуку

Кожен пошук передає, якщо значення доступні:

- `vehicleId`;
- VIN або держномер для знаходження авто в CRM;
- `findingId` / `manualPartId`;
- назву деталі та пошуковий рядок;
- OEM/каталожний номер;
- вісь, сторону, верхню/нижню позицію;
- `genericArticleId`;
- OE-номери, отримані з fitment-каталогу.

Пріоритет пошуку:

1. `vehicleId` і VIN картки автомобіля;
2. VIN, введений оператором;
3. держномер лише для знаходження картки авто;
4. номер деталі;
5. назва деталі.

Якщо немає підтвердженого каталожного зв’язку, пропозиція має статус `MANUAL_REQUIRED` і не може бути додана без ручного підтвердження.

### 4.2. Єдиний комбінований API-запит

`GET /api/parts/search?includeSuppliers=1` повертає в одному response:

- `vehicle`, `fitment`, `catalogMatches`, `oeNumbers`, `analogArticles`;
- довідкові `parts`;
- `offers` із ціною закупівлі та продажу;
- `configuredSuppliers`;
- `supplierProviders` / `providers` зі статусом кожного адаптера;
- `supplierStatuses` і `supplierSummary`;
- `supplierSearchBlocked` та пояснення блокування.

Постачальницький пошук захищений тією самою permission/scope-перевіркою, що й окремий маршрут `/api/parts/suppliers`.

Окремий `/api/parts/suppliers` зберігається для сумісності зовнішніх/старих викликів, але новий UI підбору не викликає його другим запитом.

### 4.3. Кеш і deduplication fitment

`resolvePartFitment` використовує серверний in-memory cache:

- TTL: 5 хвилин;
- максимум: 256 ключів;
- ключ включає авто, VIN, номер, назву, позицію, сторону, вісь і товарну групу;
- паралельні однакові запити отримують один in-flight Promise;
- кеш не змінює вимогу повторної серверної перевірки при фактичному збереженні деталі;
- після зміни інтеграцій або каталогу допустимо очистити кеш перезапуском функції/деплоєм.

Кеш є оптимізацією serverless instance, а не постійним сховищем. Відсутність cache hit не змінює коректність результату.

### 4.4. BM Parts

Інтерактивний пошук має обмежені межі:

- не більше 2 фільтрів моделі авто;
- не більше 3 запитів назви/номера;
- первинний режим — `available=1`;
- fallback `available=0` запускається лише для оригінального запиту і не розмножується на всі варіанти;
- відповіді в межах групи запитуються паралельно;
- тайм-аут одного HTTP-запиту — 5 секунд;
- модельний discovery-запит не виконується в інтерактивному кліку, щоб не створювати додатковий waterfall;
- деталі товарів завантажуються паралельно, максимум для 10 позицій;
- кешуються credentials, VIN-контекст і product details у межах коротких TTL.

Модельний discovery може залишатися доступним для окремих інструментів каталогу та діагностики, але не повинен блокувати первинну відповідь оператора.

### 4.5. Юнік Трейд

- тайм-аут зовнішнього запиту — 5 секунд;
- credentials кешуються на 30 секунд;
- одночасні пошуки використовують один in-flight `login_check` для однакових доступів;
- прямий пошук обмежується максимум 4 запитами на адаптер;
- аналоги обмежуються максимум 3 reference-запитами;
- повторна авторизація після HTTP 401 зберігається.

### 4.6. Загальний registry постачальників

- максимум 4 пошукові запити на одного постачальника в звичайному режимі;
- незалежні запити виконуються паралельно через `Promise.allSettled`;
- кожен адаптер має загальний budget 8 секунд;
- timeout одного адаптера не скасовує результати інших адаптерів;
- у відповіді є `providers[]` з `ok` та повідомленням про помилку;
- результат сортується за сумісністю, OEM/аналогом, наявністю та ціною;
- пропозиції від різних постачальників не зливаються в один рядок.

## 5. Стани UI

Поки виконується один комбінований запит:

- відображається `Перевіряю API…`;
- зберігається відома кількість налаштованих API, а не штучний `0`;
- до 8 секунд: `Шукаю пропозиції…`;
- після 8 секунд: `Пошук триває довше…` з поясненням, що один API може відповідати повільно;
- після завершення показуються доступні результати і помилки окремих постачальників;
- старий `/api/parts/suppliers` не запускається додатково;
- при зміні пошуку попередній fetch abort-иться, а stale response не змінює новий результат.

## 6. Ціни та бізнес-правила

- ціна закупівлі завжди відображається окремо;
- продажна ціна розраховується сервером із чинного правила CRM;
- базове правило: `закупівельна ціна × 1,40`;
- робоча націнка для робіт із заміни деталей не додається до товарної ціни постачальника;
- автоматичне об’єднання однакових деталей між постачальниками заборонене;
- перед додаванням до КП зберігаються постачальник, артикул, склад, quantity, purchase price, sell price і fitment evidence.

## 7. Спостережуваність

Для наступної ітерації рекомендовано додати структурований `searchId` і вимірювати:

- `fitmentMs`;
- `catalogMs`;
- `supplierMs` по кожному адаптеру;
- `totalMs`;
- кількість пропозицій і timeout/error по постачальнику.

У логах не зберігати повний VIN, API key, пароль або персональні дані клієнта. Допустимі лише ідентифікатори маршруту, постачальника, режиму пошуку та тривалості.

## 8. Performance budget

Для інтерактивного пошуку:

| Метрика | Ціль | Критична межа |
|---|---:|---:|
| Клієнтські HTTP-запити на один пошук | 1 | 2 лише для fallback/старого клієнта |
| BM Parts пошукові запити в одній хвилі | до 6 | 8 |
| Пошукові запити одного звичайного адаптера | до 4 | 4 |
| Тайм-аут одного зовнішнього HTTP | 5 с | 5 с |
| Budget одного постачальника | до 8 с | 8 с |
| Target першої відповіді | до 8 с | 15 с |
| Route hard ceiling | до 30 с | не допускати 504 |

Ціль `до 8 с` означає відповідь за наявності нормально працюючих інтеграцій. Якщо один постачальник не відповідає, CRM повертає частковий результат до завершення route budget і явно показує помилку цього постачальника.

## 9. Безпека та коректність

- combined route із `includeSuppliers=1` перевіряє `PROCUREMENT_READ` і location scope;
- API keys, JWT, passwords та повні VIN не потрапляють у клієнтські логи;
- браузер не може самостійно підмінити `fitmentStatus` під час збереження пропозиції;
- manual confirmation потрібен для `MANUAL_REQUIRED`, `REFERENCE_ONLY`, `NO_MATCH` і `CATALOG_NOT_CONNECTED`;
- скасований або застарілий запит не має права перезаписати актуальний state React.

## 10. Критерії приймання

1. Один клік «Пошук» у новому UI створює один `/api/parts/search?includeSuppliers=1`, без другого `/api/parts/suppliers`.
2. У response є fitment, пропозиції, налаштовані постачальники та статуси адаптерів.
3. BM Parts не виконує послідовний перебір `фільтр × назва × available`.
4. Паралельні запити одного fitment-контексту не дублюють дорогий lookup.
5. Timeout BM Parts або Юнік Трейд повертає частковий результат і статус помилки, а не 504 всього сценарію.
6. Повторне введення того самого запиту в межах TTL використовує cache/in-flight dedup.
7. Для непідтверджених деталей зберігається обов’язкове ручне підтвердження.
8. Однакові деталі від різних постачальників залишаються окремими пропозиціями.
9. `npm run build`, контракти та performance smoke проходять.
10. Після push production deployment має статус `READY`, а нових timeout-груп для `/api/parts/search` і `/api/parts/suppliers` не з’являється в перевірочному вікні.

## 11. Реалізовано в цьому релізі

- комбінований пошук через `includeSuppliers=1`;
- паралельний старт fitment/normalization/knowledge/reference;
- fitment cache та in-flight deduplication;
- обмежений паралельний BM Parts пошук із 5-секундним timeout;
- bounded supplier fan-out і 8-секундний timeout адаптера;
- credential cache та in-flight authentication для Юнік Трейд;
- клієнтський slow-search indicator після 8 секунд;
- збереження налаштованих API у UI під час нового пошуку;
- цей документ як канонічне ТЗ модуля.
