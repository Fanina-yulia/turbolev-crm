# TURBO LEV — ТЗ: прямий ремонт без діагностики з 4 сценаріями запчастин

## 1. Мета

Реалізувати канонічний маршрут `REPAIR_ONLY / DIRECT_REPAIR`, у якому автомобіль може перейти до ремонту без DiagnosticRequest і без Діагностичної карти, але тільки після формування актуальної Комерційної пропозиції (КП) та її погодження клієнтом.

КП прямого ремонту формується не з ДК, а з фактичного складу ремонту:

- роботи/послуги;
- матеріали;
- запчастини;
- джерело кожної запчастини;
- ціни, що оплачує клієнт.

## 2. Базовий маршрут

`Запис / walk-in → прибуття → DIRECT_REPAIR → склад ремонту → спосіб забезпечення запчастинами → КП → погодження → готовність деталей → READY_FOR_REPAIR → IN_REPAIR → QC → оплата → видача`.

Для прямого ремонту не створюються DiagnosticRequest і DiagnosticCard.

## 3. Чотири сценарії забезпечення запчастинами

### 3.1. `SERVICE_SUPPLIED` — запчастини підбирає та постачає СТО

1. Сервіс-менеджер додає роботи.
2. Для потрібних запчастин використовує підбір постачальників або додає позицію вручну.
3. Кожна така PART-позиція має джерело `SERVICE`.
4. У КП входить продажна ціна деталі.
5. Після погодження створюється/використовується PartsRequest.
6. Ремонт не переходить у `READY_FOR_REPAIR`, доки всі обов'язкові SERVICE-позиції не отримані.

### 3.2. `CUSTOMER_SUPPLIED` — клієнт привозить усі потрібні запчастини

1. Сервіс-менеджер додає роботи.
2. Потрібні деталі фіксуються окремими PART-позиціями з джерелом `CUSTOMER`.
3. Продажна ціна та собівартість клієнтської деталі в WorkOrder дорівнюють `0`.
4. У КП деталь відображається як «Надає клієнт» і не збільшує суму КП.
5. PartsRequest для CUSTOMER-позицій не створюється.
6. Перед стартом ремонту кожна обов'язкова CUSTOMER-позиція повинна бути підтверджена як фактично передана/наявна на СТО.

### 3.3. `MIXED` — частина деталей СТО, частина клієнта

1. На рівні WorkOrder встановлюється режим `MIXED`.
2. Кожна PART-позиція окремо має `partSupplySource = SERVICE | CUSTOMER`.
3. SERVICE-позиції проходять підбір/PartsRequest і враховуються у вартості КП.
4. CUSTOMER-позиції мають нульову продажну ціну, не потрапляють у закупівлю та вимагають підтвердження фактичної наявності.
5. Ремонт готовий до старту лише коли виконані умови для обох груп.

### 3.4. `NO_PARTS` — ремонт не потребує запчастин

1. У WorkOrder встановлюється режим `NO_PARTS`.
2. Активних PART-позицій бути не повинно.
3. КП формується лише з робіт/послуг/матеріалів.
4. Gate готовності деталей вважається виконаним.

## 4. Відмінність «прямого ремонту» від діагностики

Прямий ремонт дозволений, коли робота визначена до початку процесу: наприклад «заміна передніх колодок».

Якщо клієнт описує симптом без підтвердженої причини («гуде спереду, думаю що підшипник»), маршрут повинен залишатися діагностичним: `DIAGNOSTICS_ONLY` або `DIAGNOSTICS_TO_REPAIR`.

## 5. Модель даних

### WorkOrder

Додати nullable поле:

- `directRepairPartsMode: DirectRepairPartsMode?`

Enum:

- `SERVICE_SUPPLIED`
- `CUSTOMER_SUPPLIED`
- `MIXED`
- `NO_PARTS`

Поле застосовується насамперед до `origin = DIRECT_REPAIR`.

`directPriceConfirmedAt` залишається сумісним legacy-полем, але більше не замінює фактичне погодження актуальної КП.

### WorkOrderLine

Додати поля:

- `partSupplySource: PartSupplySource?` (`SERVICE | CUSTOMER`);
- `customerPartConfirmedAt: DateTime?`.

Правила:

- для не-PART рядків `partSupplySource = null`;
- SERVICE PART може мати supplier/supplierQuote/вартість;
- CUSTOMER PART не може впливати на дохід або собівартість: plannedUnitPrice = 0, plannedUnitCost = 0;
- при зміні PART на CUSTOMER supplier-поля очищаються;
- підтвердження клієнтської деталі фіксується часом і AuditEvent.

## 6. Комерційна пропозиція

Для `DIRECT_REPAIR` КП є обов'язковою перед стартом нового ремонту.

Estimate snapshot повинен включати:

- тип і опис рядка;
- артикул/бренд;
- кількість;
- ціну;
- знижку;
- `partSupplySource`;
- факт наявності клієнтської деталі для операційного read model.

Зміна складу робіт, кількості, ціни або джерела PART після погодження робить попередню КП неактуальною та вимагає нової ревізії.

У клієнтській КП CUSTOMER-позиція відображається як «Надає клієнт» із сумою `0 грн`.

## 7. Hard Gates перед `READY_FOR_REPAIR`

Для нового прямого ремонту обов'язково:

1. `directRepairPartsMode` обраний;
2. є щонайменше одна активна робота/послуга;
3. існує актуальний WorkOrderEstimate;
4. актуальний estimate погоджений клієнтом;
5. конфігурація запчастин узгоджена з обраним режимом;
6. SERVICE-позиції, якщо є, отримані;
7. CUSTOMER-позиції, якщо є, підтверджені як наявні;
8. механік призначений згідно чинного workflow.

`directPriceConfirmedAt` не є самостійним bypass для approval gate.

## 8. Поведінка під час створення DIRECT_REPAIR

Поточну legacy-поведінку змінити:

- не ставити `directPriceConfirmedAt = now()` при створенні;
- не створювати WorkOrder одразу у `READY_FOR_REPAIR`;
- створювати WorkOrder у `PARTS_REVIEW`;
- стартові роботи створювати як `DRAFT`;
- після погодження актуальної КП DRAFT-рядки переходять у APPROVED чинним механізмом estimate decision.

## 9. API

### `GET /api/work-orders/:id/direct-repair`

Повертає:

- `origin`;
- `partsMode`;
- counts SERVICE/CUSTOMER PART;
- customer parts confirmed/pending;
- `partsConfigurationComplete`;
- `partsReady`;
- пояснення blocker-ів.

### `PATCH /api/work-orders/:id/direct-repair`

Дії:

- `{ action: "SET_PARTS_MODE", mode }`;
- `{ action: "SET_PART_SOURCE", lineId, source }`;
- `{ action: "CONFIRM_CUSTOMER_PART", lineId, confirmed: true|false }`.

Всі мутації:

- RBAC `WORK_ORDERS_WRITE`;
- WorkOrder row scope;
- advisory lock;
- AuditEvent;
- заборона зміни конфігурації після фіналізації ACTUAL finance.

## 10. UI — «Комерційна пропозиція»

Для `origin = DIRECT_REPAIR` над складом ремонту показати окремий блок «Прямий ремонт».

### Крок 1. Роботи

Поточний модуль робіт залишається джерелом складу ремонту. Роботи можна додати з прайсу або вручну.

### Крок 2. Як забезпечуються запчастини?

4 картки/кнопки:

- «Підбирає СТО»;
- «Запчастини клієнта»;
- «Змішаний варіант»;
- «Запчастини не потрібні».

Поруч показувати поточний статус і коротке пояснення.

### Крок 3. Запчастини

#### SERVICE_SUPPLIED

Показати пошук постачальників і ручне додавання SERVICE PART. Кнопка закупівлі доступна тільки для SERVICE-позицій.

#### CUSTOMER_SUPPLIED

Показати форму:

- артикул (необов'язково);
- бренд (необов'язково);
- назва;
- кількість;
- кнопка «Додати деталь клієнта».

У списку — badge «Надає клієнт» і кнопка «Деталь на СТО / підтверджено».

#### MIXED

При додаванні/редагуванні PART обов'язково вибрати `СТО` або `Клієнт`.

#### NO_PARTS

Приховати закупівлю, показати пояснення «Для цього ремонту запчастини не потрібні». Якщо PART уже існують — не дозволяти вибрати `NO_PARTS`, доки їх не скасовано/видалено з активного scope.

### Крок 4. КП

Кнопка «Сформувати / відправити КП» активна, коли:

- є роботи;
- режим запчастин обраний;
- конфігурація PART валідна.

Після `SENT`: погодження/відхилення чинним механізмом.

Після APPROVED показати «КП погоджено».

## 11. PartsRequest

PartsRequest включає тільки `partSupplySource = SERVICE`.

CUSTOMER-позиції:

- не створюють закупівельні items;
- не мають supplier order;
- readiness визначається `customerPartConfirmedAt`.

Якщо у ремонті немає SERVICE PART, PartsRequest не потрібен.

## 12. Backward compatibility

1. Існуючі WorkOrder інших origin не змінюють маршрут.
2. Існуючі DIRECT_REPAIR, які вже у `READY_FOR_REPAIR / IN_REPAIR / terminal`, не блокуються ретроактивно.
3. Новий flow застосовується до нових/direct repair, що ще перебувають до старту ремонту.
4. Legacy `directPriceConfirmedAt` зберігається для аудиту, але новий approval gate спирається на актуальний estimate.

## 13. Аудит

Окремі AuditEvent:

- `DIRECT_REPAIR_PARTS_MODE_SET`;
- `DIRECT_REPAIR_PART_SOURCE_SET`;
- `CUSTOMER_PART_CONFIRMED`;
- `CUSTOMER_PART_UNCONFIRMED`;
- стандартні estimate created/sent/approved/rejected.

## 14. Acceptance criteria

1. DIRECT_REPAIR створюється без DiagnosticRequest і DiagnosticCard.
2. Новий DIRECT_REPAIR не переходить одразу у READY_FOR_REPAIR.
3. СТО-постачання: SERVICE parts потрапляють у КП і PartsRequest; ремонт блокується до отримання.
4. Клієнтські деталі: у КП мають 0 грн і позначку «Надає клієнт»; PartsRequest не створюється; старт блокується до підтвердження наявності.
5. MIXED: обидва джерела працюють в одному WorkOrder/Estimate; закупівля містить лише SERVICE.
6. NO_PARTS: КП формується без PART і parts gate виконаний.
7. Зміна джерела деталі після SENT/APPROVED робить попередній approval неактуальним.
8. Без актуального APPROVED estimate новий прямий ремонт не стає READY_FOR_REPAIR.
9. Після погодження КП і готовності деталей чинний ремонтний workflow працює без ДК.
10. В UI немає формулювання «Прямий ремонт без КП».
11. Сторінка автомобіля не показує «Не вдалося сформувати кошторис» як штатний стан DIRECT_REPAIR; натомість показує керований flow.
12. Prisma migration additive, drift відсутній.
13. TypeScript/build/contract smoke проходять.
14. Production deployment має статус READY.
