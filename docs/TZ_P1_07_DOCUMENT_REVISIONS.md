# P1-07 — Контроль документів і ревізій

## Мета

Зробити всі клієнтські документи керованими, відтворюваними та аудитовними. Кожна опублікована версія повинна бути прив'язана до конкретного джерела даних, fingerprint джерела, версії шаблону та незмінного snapshot.

## Документи в контурі

| Тип | Коли існує | Джерело | Для прямого ремонту |
|---|---|---|---|
| Діагностична карта | лише після фіналізації діагностики | `DiagnosticCardRevision FINAL` | не створюється |
| Комерційна пропозиція | після надсилання/погодження кошторису | `WorkOrderEstimate` | не створюється автоматично |
| Рахунок / накладна | коли є клієнтські фінансові рядки | фінансовий read model Work Order | створюється за роботами й деталями |
| Акт виконаних робіт | після закриття Work Order | `ServiceCompletionAct` | обов'язковий після завершення ремонту |

## Канонічна сутність

`ControlledDocumentRevision` зберігає:

- логічний `documentKey`;
- тип документа;
- послідовний номер ревізії;
- статус `ISSUED`, `SUPERSEDED`, `VOIDED`;
- Work Order або Diagnostic Request;
- тип та ідентифікатор source entity;
- source revision і source fingerprint;
- версію та fingerprint шаблону;
- content hash;
- незмінний snapshot для повторного аудиту;
- ім'я файла, MIME type, автора, дати видачі/анулювання;
- audit event для кожної видачі та анулювання.

Бінарний PDF діагностичної карти й надалі зберігається у спеціалізованій `DiagnosticCardPdf`, яка жорстко прив'язана до фінальної ревізії карти. Канонічний реєстр не замінює цей storage, а доповнює його єдиною історією документів.

## Життєвий цикл

1. Видача нової версії блокується advisory lock за `documentKey`.
2. Якщо ідентичний `contentHash` уже існує, операція ідемпотентно повертає існуючу ревізію.
3. Попередня `ISSUED` версія переходить у `SUPERSEDED`.
4. Нова версія отримує наступний номер та `ISSUED`.
5. Для анулювання дозволена лише актуальна `ISSUED` ревізія.
6. `SUPERSEDED` та `VOIDED` записи не редагуються й не видаляються.

## API

### Історія

`GET /api/work-orders/:id/documents/revisions`

Опційний query `type=DIAGNOSTIC_CARD|COMMERCIAL_PROPOSAL|INVOICE|COMPLETION_ACT`.

### Видача

`POST /api/work-orders/:id/documents/revisions`

```json
{ "action": "ISSUE", "type": "COMMERCIAL_PROPOSAL" }
```

Система сама формує snapshot актуального джерела, підтягує версію шаблону та записує audit.

### Анулювання

```json
{ "action": "VOID", "revisionId": "…", "reason": "Помилково сформовано" }
```

Анулювання не видаляє історію та не робить попередню ревізію «актуальною» автоматично.

## Бізнес-інваріанти

- прямий ремонт не має діагностичної карти та КП;
- діагностична карта можлива лише з фінальною діагностикою;
- КП неможлива зі статусом кошторису `DRAFT`;
- акт можливий лише після завершення/закриття Work Order;
- повторна видача того самого snapshot не створює дубль;
- зміна джерела або шаблону створює нову ревізію;
- анулювання не перезаписує snapshot;
- доступ до історії та мутацій проходить Work Order scope/RBAC;
- кожна mutation має `AuditEvent`.

## Acceptance criteria

1. Міграція застосовується на чистій БД і Prisma drift відсутній.
2. Історія документів повертається з Work Order document package.
3. ISSUE для однакового джерела є ідемпотентним.
4. Нове джерело або шаблон supersede-ить попередню ревізію.
5. VOID дозволено лише для поточної ISSUED ревізії та залишає audit.
6. Прямий ремонт не породжує діагностичну карту або КП.
7. Прямий ремонт після закриття має рахунок і акт за фактично виконаними рядками.
8. Контрактний smoke, module scope та production build проходять.
