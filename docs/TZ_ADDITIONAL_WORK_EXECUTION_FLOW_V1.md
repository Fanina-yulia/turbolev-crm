# TURBO LEV — ТЗ: повний цикл робіт, додаткових робіт і погоджень V1

## 1. Мета

Побудувати один наскрізний процес виконання робіт у CRM, у якому Планувальник, кабінет механіка, Work Order / Комерційна пропозиція, погодження клієнта, блокери, контроль виконання та фінальна сума працюють як одна система.

Головний принцип: **Work Order є єдиним джерелом правди щодо фактичного складу ремонту. Комерційна пропозиція — клієнтське представлення того самого Work Order, а не окрема сутність робіт.**

## 2. Межі відповідальності екранів

### 2.1. Робоче вікно запису в Планувальнику

Використовується для швидкого оперативного перегляду запису. Воно не є повним редактором ремонту.

До приїзду автомобіля допускається редагування первинного запиту: проблема, коментар, попередня сума, дата/час, пост, механік.

Після появи `workOrderId` зміна складу платних робіт повинна виконуватися через Work Order / Комерційну пропозицію. Олівець у блоці робіт має переводити користувача до відповідного Work Order.

### 2.2. Work Order / Комерційна пропозиція

Є канонічним місцем для:

- робіт;
- додаткових робіт;
- додаткових діагностик;
- деталей;
- ціни;
- нормо-годин;
- погодження клієнта;
- статусу виконання;
- фінального факту.

Після початку ремонту початковий запис у Планувальнику не переписується заднім числом.

## 3. Основні сценарії

### 3.1. Роботу додає сервіс-менеджер або інший уповноважений користувач CRM

1. Відкривається Work Order / Комерційна пропозиція.
2. Створюється новий `WorkOrderLine` зі статусом `DRAFT`.
3. Вказуються назва, тип, кількість, ціна, за потреби нормо-години та механік.
4. Зміна складу створює нову актуальну ревізію кошторису.
5. Позиція не може бути запущена механіком до переходу в `APPROVED`.
6. Після погодження клієнтом рядок переходить у `APPROVED` і з'являється у виконанні.

### 3.2. Механік пропонує додаткову роботу

У картці активної роботи механік використовує дію **«＋ Додати виявлене»**.

Види пропозиції:

- `ADDITIONAL_WORK` — додаткова робота;
- `ADDITIONAL_DIAGNOSTIC` — додаткова діагностика;
- `REPAIR_COMPLICATION` — ускладнення під час ремонту, наприклад закислі болти, зірвана різьба, пошкоджене кріплення.

Механік вказує:

- що потрібно виконати;
- орієнтовні нормо-години;
- технічний коментар;
- чи можна продовжувати поточний ремонт;
- або робота блокує подальше виконання.

Механік **не встановлює фінальну ціну і не погоджує роботу замість клієнта**.

Результат — новий `WorkOrderLine` зі статусом `DRAFT`, джерелом `MECHANIC_ADDITIONAL_WORK`, метаданими виду/впливу/автора та `approvalRequired=true`.

### 3.3. Ускладнення блокує ремонт

Якщо механік обирає `BLOCKS_REPAIR`:

1. CRM створює `OperationalBlocker`:
   - code: `TECHNICAL_DECISION`;
   - sourceType: `WORK_ORDER_LINE`;
   - sourceId/workOrderLineId: ID нової додаткової позиції;
   - priority: `HIGH`, а для критичного сценарію може бути `CRITICAL`;
   - причина — технічний коментар/опис механіка;
   - наступна дія — оцінити, погодити з клієнтом і дати рішення.
2. Блокер потрапляє у контрольні механізми CRM / Центр уваги.
3. Після погодження позиції блокер автоматично переходить у `RESOLVED`.
4. Після відхилення/скасування позиції блокер автоматично переходить у `CANCELLED`.

### 3.4. Додаткова діагностика

Додаткова діагностика створюється як `DRAFT`-позиція того самого Work Order. Якщо вона платна, вона проходить клієнтське погодження так само, як додаткова робота. Якщо політика СТО передбачає безкоштовну внутрішню перевірку, уповноважений менеджер може оформити її за чинними правилами без створення окремого клієнтського боргу.

## 4. Статуси рядка Work Order

Канонічний цикл:

`DRAFT → APPROVED → IN_PROGRESS → COMPLETED`

Альтернативно:

`DRAFT → CANCELLED`

Правила:

- `DRAFT` — не дозволено виконувати;
- `APPROVED` — погоджено до виконання;
- `IN_PROGRESS` — виконується;
- `COMPLETED` — виконано;
- `CANCELLED` — виключено з ремонту.

Механік не може самостійно обійти `DRAFT → APPROVED`.

## 5. Погодження клієнта

Використовується чинний механізм `WorkOrderEstimate` та його ревізій.

При додаванні нової платної позиції після попереднього погодження попередня комерційна пропозиція більше не описує актуальний склад робіт. CRM формує нову ревізію кошторису.

Підтримуються:

- повне погодження;
- повна відмова;
- змішане погодження по рядках.

Для змішаного погодження:

- погоджені рядки → `APPROVED`;
- відхилені рядки → `CANCELLED`;
- у ремонт потрапляють лише погоджені позиції.

## 6. Відображення сум

У робочому вікні запису після появи Work Order замість однієї нечіткої суми показуються дві величини:

- **Погоджено** — сума рядків `APPROVED`, `IN_PROGRESS`, `COMPLETED`;
- **Очікує погодження** — сума рядків `DRAFT`.

`CANCELLED` у суми не входить.

До появи Work Order показується чинна попередня сума `ServiceAppointment.estimatedAmount`.

Якщо Work Order містить різні валюти, CRM не складає їх математично в одну суму і повертає ознаку `mixedCurrency`.

## 7. Навігація

### 7.1. Планувальник

- якщо `workOrderId` відсутній — редагується первинний запис;
- якщо `workOrderId` є — олівець блоку «Роботи/Діагностика» відкриває `Комерційна пропозиція` з точним `workOrderId`.

### 7.2. Кабінет механіка

Кнопка `＋ Додати виявлене` відкриває сценарій створення додаткової потреби. Поточна робота залишається контекстом джерела.

### 7.3. Сервіс-менеджер

Після пропозиції механіка менеджер отримує повідомлення/контрольний сигнал і працює з тією ж комерційною пропозицією. Він уточнює назву, ціну, кількість, нормо-години, додає деталі та відправляє актуальну ревізію клієнту.

## 8. Дані додаткової роботи механіка

У `WorkOrderLine.metadata` зберігаються:

- `source = MECHANIC_ADDITIONAL_WORK`;
- `requested = true`;
- `approvalRequired = true`;
- `requestKind`;
- `impact`;
- `note`;
- `requestedByUserId`;
- `requestedByMechanicId`;
- `requestedByName`;
- `requestedAt`.

Це не замінює канонічні поля рядка; метадані потрібні для походження та аудиту.

## 9. API

### 9.1. `POST /api/cabinet/mechanic/tasks/:lineId/additional-work`

Додаткові поля V1:

```json
{
  "description": "Відновлення різьби кріплення",
  "laborHours": 1.5,
  "note": "Один болт зірваний",
  "kind": "REPAIR_COMPLICATION",
  "impact": "BLOCKS_REPAIR"
}
```

Валідація:

- лише роль `MECHANIC`;
- лише призначена механіку робота;
- лише активний ремонт;
- допустимі kind/impact;
- дублікати активних пропозицій не створюються;
- ціна від механіка не приймається.

### 9.2. `GET /api/planner/:appointmentId/commercial-summary`

Повертає:

- `workOrderId`;
- `editTarget`;
- `estimatedAmount`;
- `commercialSummary.approvedAmount`;
- `commercialSummary.pendingAmount`;
- `currency`;
- `mixedCurrency`.

Доступ відповідає scope Планувальника.

## 10. RBAC і безпека

- механік може створювати пропозицію лише для своєї призначеної роботи;
- механік не може передати `plannedUnitPrice` через endpoint;
- ціну та клієнтське погодження змінюють лише ролі/маршрути з відповідними правами;
- API Планувальника дотримується `ALL / LOCATION / ASSIGNED` scope;
- destructive production migrations заборонені;
- усі важливі зміни мають залишати audit trail.

## 11. Автоматичне закриття блокера

База даних гарантує інваріант: активний `TECHNICAL_DECISION` blocker, прив'язаний до додаткового `WorkOrderLine`, автоматично закривається після зміни статусу рядка:

- `APPROVED` → `RESOLVED`;
- `CANCELLED` → `CANCELLED`.

Це має працювати незалежно від джерела погодження: CRM, клієнтський портал або змішане погодження.

## 12. UX-вимоги

- усі видимі тексти не менше 11 px;
- механік бачить чітке попередження: «Механік не встановлює ціну і не запускає роботу без погодження»;
- для `BLOCKS_REPAIR` показується явна попереджувальна ознака;
- кнопка в кабінеті механіка має назву `＋ Додати виявлене`;
- робоче вікно запису залишається компактним і не перетворюється на редактор кошторису.

## 13. Acceptance Criteria

1. Механік може запропонувати додаткову роботу, діагностику або ускладнення.
2. Створюється DRAFT WorkOrderLine у тому самому Work Order.
3. Механік не може встановити ціну через mechanic API.
4. DRAFT-рядок не можна розпочати як виконання.
5. Для блокуючого ускладнення створюється OperationalBlocker.
6. Погодження рядка автоматично закриває blocker.
7. Скасування рядка автоматично скасовує blocker.
8. Після додаткової позиції чинний механізм ревізій кошторису вимагає актуального погодження.
9. Змішане погодження не допускає відхилені рядки в ремонт.
10. Планувальник показує погоджену суму окремо від суми, що очікує погодження.
11. За наявності Work Order редагування складу робіт із робочого вікна веде до Комерційної пропозиції.
12. До появи Work Order зберігається попередня сума запису.
13. Scope/RBAC не розширюються.
14. CI: Prisma validate, migration replay/drift, contract smoke, RBAC/API security та production build проходять.

## 14. Не входить у V1

- автоматичне ціноутворення додаткової роботи на основі AI;
- автоматичне погодження клієнтом без чинного estimate workflow;
- автоматична закупівля деталей до погодження;
- зміна фактичного фінансового документа після його остаточного блокування без correction/reversal workflow.
