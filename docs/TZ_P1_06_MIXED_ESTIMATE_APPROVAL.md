# P1-06 — Контроль змішаного погодження комерційної пропозиції

## Мета

Заборонити неявне погодження всього Work Order, коли клієнт прийняв лише частину позицій комерційної пропозиції. Змішане рішення має залишатися окремим контрольованим станом до явної дії уповноваженого менеджера.

## Бізнес-правило

1. Work Order Estimate має версію та незмінний fingerprint складу активних рядків.
2. Клієнт може прийняти або відхилити кожен активний рядок.
3. Якщо прийняті й відхилені рядки присутні одночасно, стан — `MIXED`, `mixedApprovalPending=true`.
4. Такий стан не відкриває ремонт, закупівлю чи видачу запчастин автоматично.
5. Менеджер у межах станції повинен виконати одну з двох явних дій:
   - **CONFIRM** — підтвердити прийняту частину;
   - **REQUEST_REVISION** — повернути КП на повторне погодження.

## Наслідки CONFIRM

- прийняті рядки переходять у `WorkOrderLine.status=APPROVED`;
- відхилені рядки переходять у `CANCELLED` із причиною та посиланням на клієнтське рішення;
- попередня версія КП переходить у `SUPERSEDED`;
- створюється рівно одна нова версія лише з прийнятими рядками;
- нова версія отримує `APPROVED`;
- Parts Request, ремонтні воркфлоу та кабінет механіка бачать тільки прийняті рядки;
- дія та склад рішення записуються в audit log.

Якщо всі рядки вже почали виконуватися або завершені, їх не можна скасувати через змішане погодження.

## Наслідки REQUEST_REVISION

- поточна версія КП переходить у `SUPERSEDED`;
- усі активні рядки переносяться в нову версію;
- нова версія отримує `DRAFT`;
- жоден рядок не відкриває ремонтний або складський gate;
- клієнт може повторно надіслати рішення для нової версії.

## API

### Менеджерський стан

`GET /api/work-orders/:id/estimate/mixed-decision`

Повертає:

- `mixedApprovalPending`;
- `selectionMode`: `ALL_APPROVED | ALL_REJECTED | MIXED | null`;
- `decisionCount`;
- `approvedDecisionCount`;
- `rejectedDecisionCount`;
- fingerprint та ідентифікатори активних рядків.

### Менеджерська дія

`POST /api/work-orders/:id/estimate/mixed-decision`

Тіло:

```json
{ "action": "CONFIRM" }
```

або

```json
{ "action": "REQUEST_REVISION", "reason": "Потрібно уточнити обсяг робіт" }
```

Доступ: `WORK_ORDERS_ESTIMATE` і location scope поточної Service Appointment.

## Транзакційні гарантії

- транзакційний advisory lock на Work Order;
- перевірка актуального fingerprint перед записом;
- повторна дія на вже зміненій версії повертає conflict;
- дубльовані ревізії не створюються;
- рядок, який уже `IN_PROGRESS` або `COMPLETED`, не можна скасувати;
- відхилені рядки не проходять у Parts Request та ремонтні gates;
- кожна manager action має audit trail з actor, Work Order, estimate revision, рішенням та причиною;
- відсутність станції або відсутність дозволу location scope блокує дію.

## Інтеграції

- Work Order cycle відображає gate для менеджера;
- клієнтський портал показує `managerReviewRequired`;
- існуючі одностайні `APPROVE/REJECT` сценарії не змінюють поведінку;
- змішане рішення не маскується під «погоджено».

## Acceptance criteria

1. Змішане рішення відображається як pending manager review.
2. CONFIRM створює рівно одну нову APPROVED ревізію тільки з прийнятими рядками.
3. Відхилені позиції мають CANCELLED і не потрапляють у ремонт/закупівлю.
4. REQUEST_REVISION створює DRAFT ревізію з усіма активними рядками.
5. Повторний запит із застарілим fingerprint не мутує дані.
6. Дії без station scope або без permission відхиляються.
7. Audit log містить обидві manager actions.
8. Контрактний smoke, production build і module scope проходять.
