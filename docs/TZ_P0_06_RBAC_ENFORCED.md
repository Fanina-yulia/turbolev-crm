# Технічне завдання P0-06 — production RBAC у режимі ENFORCED

## 1. Мета

Перевести production-доступ CRM до контрольованого режиму ENFORCED, але тільки після підтвердження, що:

- кожен активний користувач має хоча б одну активну роль;
- кожен активний користувач має рівно одну активну primary-роль;
- усі активні ролі відповідають єдиному canonical role contract;
- для location-scoped ролей задана станція;
- механіки пов’язані з активним ServiceMechanic у тій самій станції;
- існує активний auth-linked OWNER, який заходив у CRM протягом останньої години;
- self-registration вимкнена;
- OWNER зберігає повний набір зареєстрованих дозволів.

## 2. Правила перемикання

1. Режим за замовчуванням не змінюється міграцією: існуюче середовище спочатку проходить readiness.
2. PATCH /api/security/config приймає тільки SHADOW або ENFORCED.
3. Mutation доступна лише через SECURITY.ACCESS_MANAGE із strict: true.
4. Сервер перед ENFORCED повторно перевіряє provisioning активних користувачів. Це захищає від race condition між readiness-звітом і фактичним перемиканням.
5. Без активного auth-linked OWNER із недавнім входом перемикання відхиляється з 409 RECENT_OWNER_LOGIN_REQUIRED.
6. Якщо хоча б у одного активного користувача немає рівно однієї primary-ролі, перемикання відхиляється з 409 RBAC_PROVISIONING_INCOMPLETE.
7. Self-registration у будь-якому режимі примусово залишається вимкненою.
8. Перемикання записується в audit log.

## 3. Команди preflight

Перед production-перемиканням виконати:

~~~bash
npm run rbac:readiness
npm run rbac:enforced:readiness
~~~

- перша команда перевіряє загальну готовність матриці;
- друга додатково вимагає, щоб поточний режим уже був ENFORCED і bootstrap був завершений.

Якщо перша команда не проходить, дані або role assignments виправляються через розділ «Налаштування → Безпека». Якщо друга команда не проходить після перемикання, це означає, що production-конфігурація фактично не була активована.

## 4. Acceptance criteria

1. Увімкнення ENFORCED неможливе при неповному provisioning.
2. Увімкнення ENFORCED неможливе без недавньої сесії OWNER.
3. API не покладається на приховування кнопки в UI — усі перевірки виконуються на сервері.
4. Для кожного активного користувача readiness показує кількість активних і primary-ролей.
5. Активні canonical roles та permission matrix проходять перевірку.
6. Перевіряються location-scoped assignments, mechanic location, appointment mismatch та OWNER permissions.
7. Перемикання має audit event із новим режимом і bootstrap state.
8. Smoke, CI та production deployment проходять без помилок.

## 5. Відкат і підтримка

- Адміністратор із SECURITY.ACCESS_MANAGE може повернути SHADOW, якщо під час production-перевірки знайдено помилкове призначення.
- SHADOW не вимикає server-side authorization; він лише дає діагностичний режим для перевірки матриці.
- Будь-яке ручне редагування бази поза UI заборонене як штатний спосіб зміни ролей і має бути окремо зааудитоване.
