# Технічне завдання P1-01 — системний тип роботи DIAGNOSTIC / REPAIR / BOTH

## 1. Мета

Відокремити операційний тип послуги від її назви, категорії або довільного тексту. Тип у каталозі стає джерелом істини для створення заявки, планувальника, кабінету механіка та подальшого Work Order.

## 2. Модель даних

У ServiceCatalogItem додається обов’язкове поле serviceType:

| Код | Призначення |
|---|---|
| DIAGNOSTIC | Послуга належить до діагностики. Автомобіль потрапляє в маршрут лише діагностики. |
| REPAIR | Послуга належить до ремонту. Автомобіль потрапляє в маршрут прямого ремонту. |
| BOTH | Одна позиція охоплює обидва етапи. Маршрут — діагностика → ремонт. |

Поле itemType зберігається як класифікація змісту каталогу. Воно не замінює serviceType і не визначає маршрут заявки.

## 3. Правила маршрутизації

1. Усі вибрані позиції DIAGNOSTIC → DIAGNOSTICS_ONLY.
2. Будь-яка позиція REPAIR разом із DIAGNOSTIC → DIAGNOSTICS_TO_REPAIR.
3. Будь-яка позиція BOTH → DIAGNOSTICS_TO_REPAIR, оскільки вона містить обидва етапи.
4. Одна або декілька позицій REPAIR без діагностики → REPAIR_ONLY.
5. Якщо позицій немає, використовується явний перемикач мети заявки як fallback.
6. Ручна робота без типу вважається REPAIR і не може випадково відкрити діагностичний маршрут.
7. Назва, категорія та текст скарги не використовуються для визначення маршруту.

## 4. Інтерфейс налаштувань

У «Налаштування → Прайс робіт» потрібно:

- показувати serviceType у таблиці;
- додати фільтр «Усі процеси / Діагностика / Ремонт / Діагностика + ремонт»;
- дозволити змінювати serviceType у картці позиції;
- блокувати активацію позиції без READY, категорії та ціни за чинними правилами;
- зберігати зміну в audit log через існуючий каталог.

## 5. Імпорт

- XLSX може передавати колонку «Тип процесу», «Тип роботи», «Тип послуги» або «Service type».
- Значення нормалізуються до DIAGNOSTIC, REPAIR або BOTH.
- Якщо колонка відсутня, первинне backfill використовує DIAGNOSTIC для позицій itemType DIAGNOSTIC і REPAIR для решти.
- Нова позиція імпортується у staging і не активується автоматично.
- Перед активацією оператор перевіряє serviceType так само, як ціну, категорію та READY.

## 6. Intake та планувальник

New Request Pricing Bridge передає serviceType кожної вибраної позиції в preliminaryWorks. Intake нормалізує тип, обчислює routeKind та зберігає маршрут у ServiceAppointment через purpose і requiresDiagnosticFirst.

Для прямого ремонту створюється Work Order без DiagnosticRequest і без комерційної пропозиції. Для DIAGNOSTICS_TO_REPAIR спочатку створюється діагностичний етап; Work Order з’являється після підтвердження діагностики. У прямому Work Order джерельний serviceType і catalogItemId зберігаються у WorkOrderLine metadata/field для аудиту.

## 7. Міграція та сумісність

- Додається enum ServiceCatalogServiceType і поле serviceType з default REPAIR.
- Існуючі DIAGNOSTIC позиції переводяться в DIAGNOSTIC.
- Інші існуючі позиції переводяться в REPAIR.
- Значення BOTH встановлюється оператором для пакетів або послуг, що об’єднують обидва етапи.
- Старі інтеграції без serviceType залишаються працездатними через безпечний fallback REPAIR.

## 8. Acceptance criteria

1. Для однакового набору позицій маршрут однаковий у UI, intake та сервері.
2. Додавання діагностичної та ремонтної позиції неможливе без діагностичної карти перед ремонтом.
3. Позиція BOTH не створює помилковий direct repair.
4. Класифікація не використовує regex по назві в intake або wizard.
5. Каталог повертає serviceType у GET /api/work-prices.
6. Налаштування дозволяють фільтрувати та редагувати serviceType.
7. Імпорт і direct repair зберігають serviceType.
8. Міграція проходить на чистій базі та на існуючих даних.
9. Contract smoke, CI та production deployment READY.
