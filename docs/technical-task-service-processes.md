# Технічне завдання: діагностика, прямий ремонт і комбінований сервісний процес

## 1. Мета

Розділити в CRM два різні робочі контури:

1. діагностичний — механік заповнює Діагностичну карту;
2. ремонтний — механік виконує погоджені роботи, фіксує паузи/проблеми, проходить QC і формує акт виконаних робіт.

Процес має підтримувати три маршрути:

| Маршрут | Умова | Документи | Робочий результат |
|---|---|---|---|
| Діагностика only | Обрані лише роботи категорії “Діагностика” | Діагностична карта | Діагностику завершено; ремонтний наряд не створюється |
| Прямий ремонт | Робота відома без діагностики | Наряд-замовлення → КП → акт | Склад ремонту формується без ДК, але до старту ремонту погоджується КП |
| Діагностика → ремонт | Є діагностика та хоча б одна інша робота | Діагностична карта → наряд-замовлення/КП → акт | Спочатку завершується ДК, потім створюється ремонтний наряд |

## 2. Правила класифікації заявки

- Робота вважається діагностичною, якщо її назва або категорія містить “діагност” / `diagnos`.
- Якщо є тільки діагностичні роботи — `purpose = DIAGNOSTICS`.
- Якщо є хоча б одна недіагностична робота — `purpose = REPAIR`.
- Якщо одночасно є діагностична і недіагностична робота — `requiresDiagnosticFirst = true`.
- Прямий ремонт створює `WorkOrder.origin = DIRECT_REPAIR`, без `DiagnosticRequest` і без Діагностичної карти. Комерційна пропозиція формується безпосередньо з відомих робіт та конфігурації запчастин.
- Прямий ремонт допустимий лише коли конкретна робота визначена. Симптом без підтвердженої причини залишається діагностичним маршрутом.
- Комбінований процес створює `WorkOrder` лише після підтвердження ДК, з `origin = DIAGNOSTIC_THEN_REPAIR`.
- Ремонт, створений після окремої завершеної діагностики, має `origin = AFTER_DIAGNOSTICS`.

## 3. Модель даних

### WorkOrder

- `diagnosticRequestId` — nullable; обов’язковий лише для маршрутів після діагностики.
- `origin` — `AFTER_DIAGNOSTICS`, `DIRECT_REPAIR`, `DIAGNOSTIC_THEN_REPAIR`.
- `directPriceConfirmedAt` — legacy-сумісне поле; для нового DIRECT_REPAIR воно не замінює актуальний `WorkOrderEstimate APPROVED`.
- Новий прямий наряд створюється у `PARTS_REVIEW`, а стартові роботи — як `DRAFT` до погодження КП.
- Фізична конфігурація 4 режимів запчастин зберігається в additive extension `DirectRepairCommercialConfig`, а джерело PART-позицій — у `DirectRepairPartSource`.

### DirectRepairCommercialConfig / DirectRepairPartSource

Режими:

- `SERVICE_SUPPLIED` — усі деталі постачає СТО;
- `CUSTOMER_SUPPLIED` — усі деталі надає клієнт;
- `MIXED` — джерело визначається для кожної PART-позиції;
- `NO_PARTS` — активних PART-позицій немає.

Для CUSTOMER PART продажна ціна й собівартість дорівнюють 0; закупівля СТО не створюється. Перед стартом ремонту фіксується `customerPartConfirmedAt`.

### ServiceAppointment

- `purpose` визначає первинну мету заїзду.
- `requiresDiagnosticFirst` визначає комбінований маршрут.
- `workOrderId` прив’язується одразу для прямого ремонту або після підтвердження ДК для подальшого ремонту.

### ServiceCompletionAct

- Один акт на один WorkOrder (`workOrderId UNIQUE`).
- Містить номер, статус, валюту, snapshot фактичних рядків, загальну суму, дату та автора випуску.
- Створюється ідемпотентно при переході наряду до `READY_FOR_PICKUP` після фіналізації фактичної фінансової суми.
- Старі завершені наряди можуть бути дооформлені при першому запиті акта.

## 4. Стани та переходи

### Діагностика

`PENDING → IN_PROGRESS → CONFIRMED`.

Після `CONFIRMED`:

- для діагностики-only — процес залишається завершеним, WorkOrder не створюється;
- для комбінованого маршруту — сервіс-менеджер створює ремонтний WorkOrder;
- підтвердження не створює ремонт автоматично для кожного діагностичного автомобіля.

### Ремонт

`PARTS_REVIEW → WAITING_APPROVAL / WAITING_PARTS → READY_FOR_REPAIR → IN_REPAIR → PAUSED / WAITING_QC → READY_FOR_PICKUP → CLOSED`.

Для нового прямого ремонту:

- діагностична карта не потрібна;
- сервіс-менеджер визначає роботи й один із чотирьох режимів запчастин;
- формується актуальна КП;
- approval gate виконується тільки актуальною погодженою КП;
- SERVICE PART повинні бути отримані через PartsRequest;
- CUSTOMER PART повинні бути підтверджені як фактично наявні;
- після виконання commercial/parts/mechanic gates наряд переходить у `READY_FOR_REPAIR`.

Існуючі прямі ремонти, які вже були фактично запущені до введення цього контракту, не блокуються ретроактивно.

### Механік

- “Почати ремонт” переводить рядок роботи в `IN_PROGRESS`, а наряд — у `IN_REPAIR`.
- “Стоп” переводить виконання в паузу, обов’язково зберігає код і текст причини.
- Повторне сканування автомобіля потрібне для продовження після стопу.
- “Завершити роботу” доступне тільки для активної роботи.
- Перед останнім завершенням ремонтної роботи обов’язкові три фото: `TOOL_FIRST`, `TOOL_SECOND`, `WORKSPACE_CLEAN`.
- Після завершення всіх робіт наряд переходить у `WAITING_QC`.

## 5. Документи в картці автомобіля

| Сценарій | Діагностична карта | КП | Акт |
|---|---:|---:|---:|
| Діагностика only | Так | Не застосовується | Не застосовується |
| Прямий ремонт до завершення | Не застосовується | Обов'язкова до старту ремонту | Ще немає |
| Прямий ремонт після QC | Не застосовується | Так, актуальна погоджена ревізія | Так |
| Діагностика → ремонт | Так | Так | Так після QC |
| Ремонт після окремої ДК | Так | Так | Так після QC |

У vehicle status summary «Діагностична карта» для DIRECT_REPAIR має стан `not_applicable / Не застосовується`, але КП є застосовною і відображає реальний стан estimate/approval.

## 6. API

- `POST /api/intake` — класифікує роботи; для прямого ремонту створює WorkOrder і DRAFT-рядки.
- `POST /api/planner/appointments/:id/arrival` — підтверджує заїзд без створення діагностики для прямого ремонту.
- `POST /api/diagnostics/:id/next-step` — створює WorkOrder після підтвердженої ДК тільки для маршруту, де ремонт застосовний.
- `GET/PATCH /api/work-orders/:id/direct-repair` — керує режимом і джерелами запчастин, клієнтськими деталями та їх фактичною наявністю.
- `POST /api/work-orders/:id/estimate` — створює/відправляє source-aware КП.
- `POST /api/work-orders/:id/estimate/decision` — фіксує погодження/відхилення актуальної КП.
- `GET /api/vehicles/card?id=...` — повертає походження наряду, стан КП та акта.
- `GET /api/vehicles/status-summary` — повертає незалежні статуси документів.
- `GET /api/work-orders/:id/completion-act` — повертає акт і snapshot рядків.
- `GET /api/work-orders/:id/completion-act/pdf` — формує PDF акта.

Усі WorkOrder endpoints проходять авторизацію та перевірку row-scope через `canAccessWorkOrder`.

## 7. Аудит і фінанси

- Класифікація маршруту зберігається в audit metadata заявки та запису.
- Створення прямого наряду, вибір режиму запчастин, зміна джерела PART, підтвердження деталі клієнта, ревізії КП, зміни статусів, стоп/продовження/завершення та випуск акта аудіюються.
- Фінансове завершення виконується до `READY_FOR_PICKUP`.
- CUSTOMER PART має 0 грн продажу і 0 грн собівартості в наряді.
- Оплата не підміняє фізичний статус ремонту: готовність авто і фінансовий стан відображаються окремо.

## 8. Критерії приймання

1. Діагностика-only не створює WorkOrder ні на заїзді, ні після підтвердження ДК.
2. Прямий ремонт створює WorkOrder без DiagnosticRequest і без ДК, але не стартує без актуальної погодженої КП.
3. Прямий ремонт підтримує `SERVICE_SUPPLIED`, `CUSTOMER_SUPPLIED`, `MIXED`, `NO_PARTS`.
4. SERVICE PART потрапляє у закупівлю; CUSTOMER PART — ні.
5. CUSTOMER PART має 0 грн та потребує підтвердження фактичної наявності перед стартом.
6. Зміна джерела деталі робить попередню КП неактуальною.
7. Комбінований маршрут відкриває ДК до створення ремонтного наряду.
8. “Стоп” без причини не зберігається; причина відображається в історії.
9. Завершення останньої роботи без трьох фото неможливе.
10. Після QC доступний один ідемпотентний акт із фактичними рядками та PDF.
11. Існуючі вже запущені прямі ремонти не блокуються ретроактивно.
12. TypeScript, contract smoke, UI integrity, responsive checks та production build проходять.
