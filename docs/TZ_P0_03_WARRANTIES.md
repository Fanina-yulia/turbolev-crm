# Технічне завдання P0-03 — повноцінний модуль «Гарантії»

## 1. Мета

Винести гарантійний контур у самостійний видимий розділ CRM та забезпечити один зрозумілий післяпродажний процес:

`закритий наряд з гарантією → активна гарантія → звернення клієнта → перевірка → рішення → закриття`

Гарантія не є статусом діагностики, запису або звичайного Work Order. Вона прив'язана до конкретної виконаної роботи у наряді, тому працює і для прямого ремонту, і для процесу «діагностика → ремонт».

## 2. Межі реалізації

### Входить у P0-03

- окремий пункт основної навігації «Гарантії»;
- canonical URL `?section=warranties`;
- збереження старих deep-link/подієвих переходів без відправлення у «Наряди та ремонт»;
- пошук за клієнтом, телефоном, авто, VIN, номером наряду або роботою;
- черги «Активні», «Закінчуються», «Звернення», «Завершені»;
- розрахунок строкової та пробіжної межі;
- реєстрація гарантійного звернення;
- обробка звернення зі статусами та обов'язковим рішенням для відхилення/закриття;
- role/scope enforcement через `WARRANTY.READ` і `WARRANTY.WRITE`;
- contract smoke для кодів і переходів статусів;
- production CI та публікація.

### Не входить у P0-03

- автоматичне створення ремонтного Work Order за гарантійним зверненням;
- автоматичні повернення грошей або складські списання;
- фото/відео гарантійного дефекту;
- окрема бухгалтерська проводка гарантійних витрат.

Ці функції оформлюються окремими P1/P2 задачами, але модуль має залишатися розширюваним.

## 3. Модель даних

### WorkOrderLine

Джерело гарантійних умов:

- `type = LABOR`;
- `status = COMPLETED`;
- батьківський Work Order закритий (`closedAt IS NOT NULL`);
- задано `warrantyKm > 0` або `warrantyDays > 0`;
- `warrantyStartsAt`, якщо відсутня, дорівнює `completedAt`;
- `warrantyEndsAt` може перевизначати розраховану дату;
- `warrantyMileageStartKm` є базою для пробіжної межі.

### WarrantyClaim

Існуюча сутність `WarrantyClaim`:

- `id`;
- `workOrderLineId` — обов'язковий зв'язок з виконаною роботою;
- `status`;
- `reason`;
- `mileageKmAtClaim`;
- `resolution`;
- `openedByUserId`, `openedByName`;
- `closedAt`;
- `createdAt`, `updatedAt`.

Один рядок роботи не може мати більше одного відкритого звернення зі статусом `OPEN`, `REVIEW` або `APPROVED`.

## 4. Канонічні статуси гарантійного звернення

| Код | Назва | Призначення |
|---|---|---|
| `OPEN` | Нове | звернення зареєстроване |
| `REVIEW` | На перевірці | сервіс перевіряє дефект та умови |
| `APPROVED` | Погоджено | гарантійність підтверджена |
| `REJECTED` | Відхилено | гарантійність не підтверджена |
| `CLOSED` | Закрито | звернення завершене після рішення/виконання |

Допустимі переходи:

- `OPEN → REVIEW` або `REJECTED`;
- `REVIEW → APPROVED` або `REJECTED`;
- `APPROVED → CLOSED`;
- `REJECTED → CLOSED`;
- повторне збереження поточного статусу дозволене;
- перехід із `CLOSED` заборонений.

Для `REJECTED` та `CLOSED` API вимагає непорожній коментар-рішення. Це забезпечує пояснюваність рішення та мінімальний audit trail навіть до винесення історії змін в окрему сутність.

## 5. Правила розрахунку гарантії

1. Якщо немає дати старту — стан `PENDING_START`.
2. Якщо поточна дата більша за дату завершення — гарантія прострочена за строком.
3. Якщо поточний пробіг досягнув пробіжної межі — гарантія прострочена за пробігом.
4. Якщо до завершення залишилось не більше 30 днів або 1 000 км — стан `EXPIRING`.
5. В інших випадках — `ACTIVE`.
6. Прострочене звернення дозволено зареєструвати, але UI має явно попередити, що рішення приймає сервіс.
7. Для прямого ремонту діє та сама модель: наявність гарантії визначається рядком виконаної роботи, а не наявністю діагностичної карти або КП.

## 6. Навігація та сумісність

### Новий маршрут

- видимий пункт «Гарантії» у групі «Сервіс»;
- slug: `warranties`;
- `slugFromSection("Гарантії") = "warranties"`;
- `sectionFromSlug("warranties") = "Гарантії"`.

### Старі маршрути

- старі назви «Комерційна пропозиція», «Виробництво» та «Контроль якості» продовжують працювати через compatibility bridge;
- старий перехід «Гарантії» більше не маскується під історію КП;
- deep-link з `workOrderId` відкриває гарантійну чергу, обмежену цим нарядом.

## 7. UI

Сторінка повинна містити:

- заголовок «Гарантійний центр»;
- KPI: активні, такі що закінчуються, відкриті звернення, завершені;
- пошук без перезавантаження сторінки;
- вкладки-черги з лічильниками;
- картку роботи з номером наряду, автомобілем, клієнтом, виконаною роботою;
- строкову та пробіжну межі;
- явні бейджі гарантійного стану і звернення;
- кнопку «Відкрити наряд»;
- «Зареєструвати звернення» для роботи без відкритого звернення;
- «Опрацювати звернення» для відкритого звернення;
- модальне вікно реєстрації: причина та поточний пробіг;
- модальне вікно обробки: статус і рішення сервісу;
- стани loading, empty, error, disabled під час запису.

## 8. API

### GET `/api/warranties`

Query:

- `q` — пошуковий рядок;
- `workOrderId` — необов'язковий deep-link focus.

Response:

`{ ok, rows, counts, canWrite }`

Кожен row містить роботу, наряд, клієнта, авто, умови гарантії, розраховані залишки, openClaim та останні claims.

### POST `/api/warranties`

Body:

`{ workOrderLineId, reason, mileageKmAtClaim? }`

Валідації:

- робота існує та є завершеною;
- наряд закритий;
- робота має строкову або пробіжну гарантію;
- причина не коротша за 5 символів;
- пробіг — додатне число;
- немає іншого відкритого звернення;
- access scope дозволяє роботу.

### PATCH `/api/warranties`

Body:

`{ claimId, status, resolution? }`

Валідації:

- статус входить у canonical contract;
- перехід дозволений таблицею переходів;
- для `REJECTED/CLOSED` передано рішення;
- access scope дозволяє роботу;
- при terminal status проставляється `closedAt`, при поверненні у відкритий статус — очищується.

## 9. Доступи

- `WARRANTY.READ` — перегляд черги;
- `WARRANTY.WRITE` — створення та зміна звернення;
- у режимі `ENFORCED` додатково застосовується scope ALL/TEAM/LOCATION;
- неактивний або не provisioned користувач отримує 401/403 без розкриття даних.

## 10. Автоматизація та контроль якості

- canonical status contract зберігається у `src/domain/warranty/contract.ts`;
- API та UI використовують той самий список кодів/лейблів;
- `scripts/warranty-claim-contract-smoke.ts` перевіряє коди, terminal statuses і переходи;
- navigation smoke перевіряє видимий пункт, slug та legacy bridge;
- production build є обов'язковим gate перед merge.

## 11. Acceptance criteria

1. У головній навігації є «Гарантії».
2. Перехід на «Гарантії» відкриває `?section=warranties`, а не Work Orders.
3. Старі посилання не втрачають контекст і не ламають інші розділи.
4. У черзі відображаються тільки завершені роботи з гарантійними умовами.
5. Пошук за клієнтом, телефоном, авто, VIN, номером наряду та роботою працює.
6. Дата та пробіг розраховуються однаково на API і в UI.
7. Неможливо створити друге відкрите звернення по тій самій роботі.
8. Неможливі переходи `OPEN → CLOSED` та `CLOSED → REVIEW`.
9. Неможливо відхилити або закрити звернення без рішення.
10. Access scope обмежує записи.
11. Smoke та production build проходять.
12. PR злитий у `main`, production deployment має стан READY.

## 12. Подальше розширення

Наступні задачі можуть додати:

- окрему історію подій `WarrantyClaimEvent`;
- фото/відео дефекту;
- автоматичне створення гарантійного наряду;
- облік гарантійних витрат і прибутковості;
- аналітику повторних звернень, причин та LTV.
