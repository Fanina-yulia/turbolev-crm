# TURBO LEV — ТЗ: Пошук запчастин та редагований кошик V4

Дата: 16.09.2026
Модуль: `parts-inventory`
Екран: `/?section=parts` → конкретна Діагностична карта
Статус: IMPLEMENTED

## 1. Мета

Довести робочий підбір до структури, максимально близької до еталонного каталогу постачальника, але не втратити перевірку VIN/OE, бізнес-контекст CRM, ціноутворення та аудит.

Критичне правило: **жодних вигаданих даних**. Назва, артикул, бренд, постачальник, ціна, склад, залишок і термін показуються лише з фактичної відповіді API або з явно позначеного ручного вводу оператора.

## 2. Бізнес-процес

`ДК → потреба → пошук BM Parts/UniTrade/інші API → один рядок = одна пропозиція → вибір → WorkOrderLine → PartsRequestItem → кошик → КП → погодження → закупівля`.

Вибір іншої пропозиції для тієї самої потреби оновлює той самий `WorkOrderLine` і відповідний `PartsRequestItem`; дубль для того самого finding/manualPart не створюється.

## 3. Popup пошуку

### 3.1 Верхня панель

- поле OEM/артикул/назва;
- автомобіль із контексту ДК;
- dropdown `Усі постачальники` + конкретні підключені постачальники;
- `К-ть знайдених запчастин: N`;
- сортування `Бренд`, `Ціна`, `Наявність`, `Термін` із напрямком ↑/↓;
- фактичний статус VIN/OE fitment;
- кількість API, які реально підключені.

### 3.2 Структура результатів

Не використовувати великі картки. Один результат = один компактний рядок.

Результати в одному scroll-контейнері, секціями:

1. `Оригінали`;
2. `Аналоги`;
3. `Потребує перевірки`;
4. `Комплектні альтернативи`.

Рядок містить:

- фото, якщо API його передав; інакше нейтральний placeholder;
- назву;
- `Наявність ⓘ` з розкриттям фактичних складів та кількості;
- короткий код постачальника (`UTR`, `BM` тощо) + повну назву;
- бренд + артикул;
- статус сумісності;
- закупівельну ціну; якщо backend повернув sellPrice — показати її другорядно;
- кнопку `Додати`.

### 3.3 Сумісність

- VERIFIED + exact + confirmed → `✓ підтверджено VIN`;
- PARTIAL / model-only → `◐ модель · перевірити`;
- REVIEW_REQUIRED / UNCONFIRMED → `! сумісність не підтверджена`;
- ASSEMBLY завжди потребує ручної перевірки.

Непідтверджені результати не приховуються, але їх не можна додати без явного checkbox ручної перевірки.

## 4. Кошик

Після вибору пропозиції CRM автоматично заповнює:

`№ | К-сть, шт. | Артикул | Бренд | Номенклатура | Постачальник | Склад | Ціна закупки | Сума закупки | Ціна продажу | Сума продажу | Прибуток | % | Дія`.

Джерело первинних значень — тільки API постачальника + чинні налаштування націнки.

### 4.1 Редаговані поля

Оператор може змінити:

- кількість;
- артикул;
- бренд;
- номенклатуру;
- назву постачальника;
- склад;
- закупівельну ціну;
- ціну продажу;
- % націнки.

Порожнє значення в таблиці повинно бути клікабельним `— ✎`, а не мертвим текстом.

### 4.2 Розрахунки

- `Сума закупки = quantity × purchasePrice`;
- `Ціна продажу = purchasePrice × (1 + markupPercent/100)`, якщо немає прямого override;
- `Сума продажу = quantity × sellPrice`;
- `Прибуток = сума продажу − сума закупки`;
- якщо користувач змінює `%`, sellPrice перераховується автоматично;
- якщо користувач прямо змінює sellPrice без зміни %, відхилення від формули потребує причини;
- якщо змінено лише sellPrice, backend може розрахувати фактичний implied markup.

### 4.3 Audit / provenance

Ручні зміни не маскуються під API-дані.

У `WorkOrderLine.metadata.partsManualOverrides` зберігаються:

- перелік змінених полів;
- причина price override, якщо була;
- дата;
- userId та ім'я оператора.

У UI ручні поля позначаються `ручн.`.

Кожне збереження створює `AuditEvent(action=PART_SELECTION_LINE_MANUAL_OVERRIDE)` із `before`, `after`, `changedFields`.

## 5. Синхронізація

Редагування кошика одночасно оновлює:

- `WorkOrderLine` — опис, артикул, бренд, кількість, cost, sell price, metadata;
- `PartsRequestItem` — description, article, brand, quantity, purchasePrice, sellPrice;
- audit trail.

Якщо `WorkOrderLine` уже `APPROVED` і змінюється комерційна інформація — рядок повертається у `DRAFT`, щоб погодження не залишалося дійсним після зміни ціни/кількості.

Редагування блокується після старту виконання (`IN_PROGRESS/COMPLETED/CANCELLED`) або після переходу закупівлі в `ORDERED/PARTIALLY_RECEIVED/RECEIVED/INSTALLED/RETURNED/CANCELLED`.

## 6. Дані та API

Пошук:

- `/api/parts/search` — canonical/OE/fitment context;
- `/api/parts/suppliers` — живі supplier offers;
- `/api/parts-selection/select` — повторна server-side перевірка та первинне збереження вибраної пропозиції.

Кошик:

- `GET /api/parts-selection/line?diagnosticId=...` — фактичні збережені line facts;
- `PATCH /api/parts-selection/line` — ручні корекції з audit.

## 7. RBAC

- GET кошика: `PARTS_READ`, мінімум LOCATION;
- PATCH: `PARTS_WRITE`, strict, мінімум LOCATION;
- додатково перевіряється location Діагностичної карти;
- UI не обходить API permissions.

## 8. UI / адаптивність

Desktop:

- список потреб + широка таблиця кошика;
- popup до 1420px;
- компактні supplier rows;
- горизонтальний scroll кошика лише для великої таблиці.

Mobile:

- потреби й кошик ідуть вертикально;
- popup займає viewport;
- рядок пропозиції перебудовується у компактну сітку;
- мінімальний UI font — 11px.

## 9. Acceptance

1. Popup більше не показує великі cards як основний формат результатів.
2. Є `К-ть знайдених запчастин`.
3. Є supplier filter та сортування по бренду/ціні/наявності/терміну.
4. Оригінали, аналоги, review та assemblies видно секціями в одному списку.
5. Наявність розкриває реальні склади.
6. Вибір пропозиції автоматично заповнює всі доступні колонки кошика.
7. Порожні/операційно неправильні поля можна редагувати.
8. Derived totals перераховуються без ручного вводу.
9. Manual changes позначені та аудіюються.
10. Зміна supplier offer для тієї самої потреби замінює рядок, не дублює його.
11. Закуплені/виконувані позиції блокуються від небезпечного редагування.
12. Regression smoke та production build проходять.
13. Production deployment `READY`, без нового runtime error cluster для parts-selection.
