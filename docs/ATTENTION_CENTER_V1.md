# Центр уваги CRM — V1

## 1. Мета

Перетворити розділ «Мої задачі» з особистого task-list у єдину операційну чергу CRM: користувач бачить не всі записи системи, а лише ситуації, які потребують дії, контролю або рішення.

Принцип екрану: **що сталося → чому це проблема → скільки часу залишилось/прострочено → що відкрити для вирішення**.

## 2. Два типи сигналів

### 2.1. Постійні workflow-задачі (`CrmTask`)

Використовуємо існуючу модель і DB-тригери. Не створюємо дублікати для процесів, які вже автоматизовані:

- погодження кошторису;
- підбір / погодження / замовлення / отримання запчастин;
- дебіторська заборгованість клієнта;
- контроль якості;
- гарантійні випадки;
- ручні задачі.

Workflow-задача має стабільний `dedupeKey`, переходить разом зі статусом процесу і автоматично закривається при завершенні причини.

### 2.2. Живі сигнали

Рахуються read-only з поточного стану CRM під час відкриття Центру уваги. У БД окрема задача не створюється. Після усунення причини сигнал зникає при наступному оновленні.

Це використовується для SLA, відхилень, прострочень, навантаження і контролю стану системи.

## 3. Джерела V1

### Комунікації

- нове звернення без реакції;
- пропущений Binotel-дзвінок у черзі нових звернень;
- SLA першої реакції — 15 хв;
- 15+ хв → високий пріоритет;
- 60+ хв або пропущений дзвінок → критичний.

### СТО / Планувальник

- плановий час завершення авто минув;
- записаний клієнт не прибув / прибуття не підтверджене через 15 хв після часу запису;
- авто вже у процесі, але немає призначеного механіка;
- авто вже у процесі, але не закріплене за постом;
- авто у статусі PAUSED понад 2 години;
- готове авто очікує видачі понад 1 годину;
- ETA деталей минув, але авто продовжує чекати запчастини.

### Запчастини

Зберігаємо існуючі автоматичні `CrmTask` по `PartsRequest` і додатково контролюємо прострочений `partsEtaAt` конкретного авто.

### Постачальники

- замовлення DRAFT не відправлено понад 2 години;
- SUBMITTED не підтверджено понад 2 години;
- CONFIRMED не завершено понад 24 години;
- PARTIAL не закрито понад 8 годин;
- статус ERROR → критично;
- активна інтеграція постачальника у статусі ERROR → критично.

Сигнали по постачальниках показуються лише користувачам із відповідним доступом до закупівель. Інтеграційний health-check глобального постачальника показується лише при глобальному procurement scope.

### Наші платежі

Контролюємо `FinancialObligation(direction=PAYABLE)`:

- прострочений платіж;
- платіж протягом найближчих 3 днів;
- відкрите зобов'язання без дедлайну старше 7 днів;
- показуємо невиплачений залишок `amount - settledAmount`.

Фінансові дані показуються тільки за наявності `FINANCE.READ` і в дозволеному location scope.

### Заробітна плата

Для користувача з глобальним payroll access:

- розрахунковий період завершено, але проведені нарахування перевищують виплати;
- після 5 днів прострочення — критично;
- період завершено, але залишились DRAFT-нарахування;
- період у REVIEW → потребує фінального контролю.

Зарплатні сигнали навмисно не показуються користувачам без глобального payroll scope, щоб не розкрити чужу компенсацію через агреговані дані.

### Завантаженість постів

Для активних постів і графіка станції рахуємо:

`booked minutes / available post minutes × 100%`

Показуємо окремо сьогодні та завтра.

Сигнали:

- сьогодні <35% → низьке завантаження;
- сьогодні >100% → перевантаження;
- завтра <50% → низьке завантаження на завтра;
- завтра ≥95% → майже немає резерву;
- конкретний пост >110% сьогодні → критичне перевантаження.

## 4. Пріоритети

- `CRITICAL` — ситуація вже створює високий ризик клієнту, виробництву, грошам або роботі системи;
- `HIGH` — SLA/дедлайн порушено або скоро виникне суттєва проблема;
- `MEDIUM` — потрібна дія або контроль, але процес ще не критичний;
- `LOW` — некритичний ручний контроль.

## 5. Черги

Кожен сигнал належить до одного стану:

- `ACTION` — користувач може/повинен діяти зараз;
- `WAITING` — очікуємо клієнта, постачальника, поставку або зовнішню відповідь;
- `MONITORING` — ситуація ще не проблема, але має бути на контролі.

## 6. Категорії

- Звернення;
- СТО;
- Діагностика;
- Запчастини;
- Постачальники;
- Фінанси;
- Зарплата;
- Пости;
- Якість;
- Гарантії;
- Мої задачі.

Категорії є фільтрами однієї черги, а не окремими незалежними екранами.

## 7. UX

Вгорі 5 KPI-фільтрів:

1. Критично;
2. Прострочено;
3. Моя дія;
4. Очікуємо;
5. Сьогодні.

Під ними — категорійні фільтри з кількістю сигналів.

Основний блок — «Потребує уваги зараз».

Праворуч:

- «Завантаженість постів» на сьогодні/завтра;
- «Наступні» — найближчі дедлайни, які ще не прострочені.

## 8. Поведінка дії

Кнопка сигналу повинна вести не у загальний розділ, а максимально близько до контексту:

- appointment → конкретний запис Планувальника;
- parts → вкладка запчастин конкретного ЗН;
- estimate → кошторис конкретного ЗН;
- QC / warranty → відповідний контекст ЗН;
- payable / payroll → фінансовий центр;
- supplier → закупівлі;
- inquiry → нові звернення.

## 9. Автозакриття

Для live-сигналів немає кнопки «Виконано». Вони зникають лише після усунення реальної причини в CRM.

Приклади:

- призначили механіка → сигнал «немає механіка» зник;
- змінився статус NEW-звернення → сигнал звернення зник;
- оплатили PAYABLE → сигнал платежу зник;
- постачальник підтвердив замовлення → старий сигнал SUBMITTED зник або змінився на наступний контроль;
- авто видали → сигнал READY_FOR_PICKUP зник.

Ручні задачі залишають кнопки «В роботу» / «Виконано».

## 10. Access control

Центр уваги відкривається через `OVERVIEW.READ`, але кожен тип даних додатково залежить від профільного permission:

- communications → `COMMUNICATIONS.READ`;
- planner/posts → `PLANNER.READ`;
- suppliers/procurement → `PROCUREMENT.READ`;
- finance/payables → `FINANCE.READ`;
- payroll → глобальний `PAYROLL.ALL_READ`, `PAYROLL.WRITE` або `PAYROLL.CLOSE`.

Location-scoped permissions обмежують planner/procurement/finance signals дозволеними станціями.

## 11. Оновлення

- перше завантаження при відкритті;
- раз на 60 секунд, якщо вкладка видима;
- при поверненні фокусу у вкладку;
- при `visibilitychange`;
- через подію `turbolev:attention-refresh` після важливих UI-операцій у майбутньому.

## 12. Acceptance criteria V1

1. Екран не показує фіктивні «100% виконання», якщо бізнес має проблеми.
2. В одній черзі видно ручні задачі і реальні проблеми різних модулів.
3. Пропущений дзвінок / нове звернення без реакції з'являється автоматично.
4. Прострочене авто, авто без механіка або поста видно без ручного створення задачі.
5. Прострочена поставка деталей і зависле supplier order видно у черзі.
6. PAYABLE показує наші майбутні та прострочені платежі з сумою залишку.
7. Payroll показується лише уповноваженим користувачам.
8. На екрані видно завантаження постів сьогодні/завтра.
9. Клік по сигналу веде у робочий контекст.
10. Live-сигнал автоматично зникає після усунення причини.
11. Відсутні дублікати існуючих DB-trigger workflow tasks.
12. Темна і світла тема використовують CRM semantic variables.
13. Mobile layout лишається адаптивним.
14. API security, RBAC, diagnostics і production build проходять без регресій.

## 13. Наступні етапи

V1 створює універсальний read model. Наступні сигнали можна додавати без перебудови UI:

- складські min/max залишки;
- прострочені повернення постачальникам;
- неприйняті рекламації;
- зміни без достатньої кількості персоналу;
- прострочені документи співробітників;
- податки, оренда, регулярні платежі;
- касовий розрив;
- негативні відгуки;
- повторний ремонт тієї ж несправності;
- контроль конверсій і продажів;
- health-check інтеграцій / камер / телефонії.
