# ТЗ: Центр уваги — інцидентна модель V3

## 1. Передумови

Аудит production-екрана «Центр уваги → Потребує уваги зараз» показав 110 активних технічних сигналів. Значна частина з них описує не окремі бізнес-проблеми, а різні технічні наслідки одного візиту.

Типовий приклад одного й того самого запису:
- «не підтверджено приїзд»;
- «час запису минув, статус досі BOOKED».

Такі повідомлення виникають різними контролерами, але для користувача є однією проблемою: результат запланованого приїзду не визначений.

Також виявлено автомобілі з 4–8 повідомленнями одночасно, де змішані старі та нові етапи: BOOKED, прострочення планового часу, ДК на перевірці, оплата, no-show. Це створює шум, завищує KPI «Критично/Прострочено» і не відповідає управлінській моделі «що потрібно зробити зараз».

## 2. Ціль

Перетворити «Центр уваги» зі списку технічних сигналів на керовану чергу бізнес-інцидентів.

Головний принцип:

> Один активний візит / процес = одна картка у Центрі уваги.

Технічних сигналів усередині може бути декілька. Вони не втрачаються і доступні в деталях картки.

## 3. Терміни

**Signal** — технічне правило, яке спрацювало в конкретному модулі.

**Incident** — агрегований управлінський об’єкт, який об’єднує пов’язані сигнали одного візиту або процесу.

**Root cause** — перший/основний блокуючий етап процесу.

**Operational incident** — актуальна проблема, де потрібна дія або контроль.

**Data quality incident** — суперечливі стани одного процесу.

**Data cleanup incident** — старий незакритий процес без активності понад 7 днів, який не повинен конкурувати з поточними задачами.

## 4. Ключ групування

Сигнали агрегуються за найточнішим доступним бізнес-ідентифікатором у такому порядку:

1. appointmentId;
2. workOrderId;
3. diagnosticId;
4. taskId;
5. якщо жоден ідентифікатор не доступний — сигнал залишається окремим.

Для APPOINTMENT та WALK_IN_* sourceId трактується як appointmentId.

Не допускається сліпе об’єднання лише за номерним знаком, оскільки один автомобіль може мати кілька різних візитів.

## 5. Етапи процесу

Для вибору кореневої проблеми використовується бізнес-послідовність:

1. Запис / приїзд;
2. Приймання / механік / пост;
3. Діагностика;
4. Розрахунок / кошторис;
5. Погодження клієнтом;
6. Запчастини;
7. Ремонт;
8. Контроль якості;
9. Оплата;
10. Видача.

Якщо декілька сигналів належать одному інциденту, головним вважається найбільш ранній блокуючий етап.

## 6. Спеціальні правила

### 6.1. BOOKED + не підтверджено приїзд

Сигнали:
- «не підтверджено приїзд»;
- «час запису минув, статус досі BOOKED»

об’єднуються в один інцидент:

**«<Авто>: не визначено результат запланованого приїзду»**

Причина:
«Час запису минув, але результат приїзду не зафіксовано. Вкажіть: приїхав, не приїхав, перенесено або скасовано.»

### 6.2. Суперечливі стани

Якщо в одному інциденті одночасно є ранній стан типу BOOKED/no-show і downstream-етап (діагностика, оплата, ремонт тощо), картка отримує тип DATA_QUALITY.

Заголовок:
**«<Авто>: суперечливий стан візиту»**

Це означає, що потрібно перевірити першоджерело та залишити один фактично правильний стан.

### 6.3. Старі незакриті процеси

Якщо:
- остання активність старша 7 днів;
- немає активної фінансової суми;
- категорія не FINANCE/PAYROLL/WARRANTY;

інцидент переводиться в DATA_CLEANUP.

Для нього:
- пріоритет не може бути CRITICAL;
- рівень = MEDIUM;
- bucket = MONITORING;
- картка має бейдж «Старий процес».

Це не видаляє дані, а прибирає історичний шум із вершини оперативної черги.

## 7. Бізнес-пріоритет

Кожному incident присвоюється businessScore 0–100.

Фактори:
- рівень CRITICAL/HIGH/MEDIUM;
- чи потрібна дія співробітника;
- чи є діагностика;
- чи є фінансовий етап;
- чи є можливий простій через механіка/пост;
- чи є сума;
- чи проблема свіжа;
- чи є суперечність даних.

DATA_CLEANUP має мінімальний score і сортується нижче оперативних проблем.

## 8. Сортування

Черга сортується у такому порядку:

1. OPERATIONS;
2. DATA_QUALITY;
3. DATA_CLEANUP.

Усередині класу:
1. businessScore DESC;
2. severity;
3. overdue;
4. тривалість прострочки.

## 9. Картка інциденту

Картка повинна показувати:

- зрозумілий бізнес-заголовок;
- категорію;
- критичність;
- клас проблеми;
- businessScore;
- коротке пояснення;
- етап;
- відповідальну роль;
- SLA/прострочку;
- контрагента;
- суму, якщо доступна;
- кількість технічних сигналів, що об’єднані;
- рекомендовану наступну дію;
- кнопку переходу в точний робочий контекст.

## 10. Розгортання деталей

Якщо relatedSignalCount > 1, картка має блок:

**«Що об’єднано (N)»**

У ньому відображаються всі первинні сигнали:
- заголовок;
- причина.

Це забезпечує аудит і не приховує внутрішню логіку CRM.

## 11. KPI

Після агрегації верхні KPI рахуються по incidents, а не по raw signals:

- Усього;
- Критично;
- Прострочено;
- Потрібна дія;
- Очікуємо;
- Сьогодні.

У шапці додатково показується:
- кількість incident-карток;
- кількість сирих технічних сигналів до агрегації.

Приклад:
Інцидентів: 48 · сигналів: 110.

## 12. Категорійні фільтри

Категорійні лічильники теж рахуються по incident-картках.

Категорія інциденту визначається головним root signal.

## 13. Відповідальна роль

Базове визначення:

- SERVICE / DIAGNOSTICS → Сервіс-менеджер;
- PARTS → Запчастини;
- SUPPLIERS → Закупівлі;
- FINANCE / PAYROLL → Фінанси;
- POSTS → Керівник СТО;
- інше → Відповідальний.

На наступному етапі цю модель можна розширити до конкретного userId.

## 14. Автозакриття

Нова модель не створює окремих записів у БД.

Incident — read model, який збирається при кожному GET /api/tasks.

Після усунення першопричини:
- відповідний signal зникає;
- incident автоматично змінює root cause;
- якщо сигналів більше немає — incident зникає.

## 15. Безпека та сумісність

- RBAC залишається без змін.
- Дані, яких користувач не міг бачити раніше, не з’являються після агрегації.
- Нова логіка працює після всіх existing collectors: base, supplement, operational stalls, walk-in.
- Ручні задачі та глобальні сигнали без vehicle workflow не агрегуються примусово.
- Дані не змінюються, поки користувач явно не виконає існуючу дію.

## 16. Реалізація

Новий pure-domain шар:

src/domain/attention-incidents.ts

API flow:

buildAttentionCenter
→ supplementAttentionCenter
→ appendOperationalStallAttention
→ appendWalkInAttention
→ finalizeAttentionIncidents
→ UI

Frontend:
- картка incident;
- badges DATA_QUALITY, DATA_CLEANUP;
- business score;
- owner/stage;
- expandable related signals;
- header incident count/raw signal count.

## 17. Acceptance criteria

1. Два сигнали одного appointment (arrival + stale-booked) відображаються однією карткою.
2. Сирі сигнали не губляться та доступні в «Що об’єднано».
3. Один номерний знак із різними appointmentId не склеюється в один візит.
4. Старі процеси >7 днів не залишаються CRITICAL лише через вік.
5. Суперечливі стани позначаються як «Перевірити дані».
6. KPI рахуються по incidents.
7. Категорійні фільтри рахуються по incidents.
8. Основна кнопка веде в контекст root/next actionable signal.
9. Неvehicle/global сигнали залишаються окремими.
10. Існуючі RBAC та action endpoints не ламаються.
11. UI працює у світлій/темній темі.
12. Список продовжує скролитися на desktop/mobile.
13. Production build проходить.
14. Contract smoke для incident aggregation проходить.

## 18. Наступні розширення

Після стабілізації V3 можна додати:
- конкретного відповідального користувача, а не роль;
- SLA-ескалації менеджер → керівник;
- фінансовий потенціал КП;
- вартість простою поста;
- push/telegram/escalation notifications;
- окремий фільтр «Проблеми даних»;
- масове очищення старих BOOKED/no-show;
- історію зміни root cause по incident;
- аналітику: середній час усунення інциденту, повторювані причини, найчастіші bottlenecks.
