# Технічне завдання: стабілізація та захист CRM Turbo Lev

## 1. Мета

Підвищити безпеку, надійність і керованість CRM у щоденній роботі СТО. Система повинна:

- не віддавати внутрішні дані без авторизованої сесії та відповідного scope;
- не приймати неавторизовані webhook-запити;
- захищати локальний вхід від автоматичного підбору паролів;
- не дозволяти розпочати роботу не з тим автомобілем;
- повністю проводити звернення механіка від створення до адміністративного рішення;
- фіксувати кожну критичну дію в журналі;
- не створювати дублікати при повторному натисканні або паралельних запитах.

## 2. Обсяг робіт

### 2.1. API та доступ

1. Для внутрішніх маршрутів CRM використовувати `authorize()` або `authorizeScopedLocation()`.
2. Чутливі read-маршрути клієнтів, автомобілів, комунікацій і заявок повинні повертати `401/403` без належного доступу.
3. Глобальний пошук повинен перевіряти сесію і permission незалежно від режиму `SHADOW`.
4. Webhook сайту повинен працювати fail-closed: відсутній секрет = `503`, неправильний секрет = `401`.
5. Для входу та публічних інтеграцій застосувати серверний rate limit на спільній таблиці rate-limit bucket.

### 2.2. Перевірка автомобіля механіком

1. Старт конкретного рядка роботи виконується тільки для авторизованого механіка, якому рядок призначений.
2. Якщо в роботі є номерний знак, перед `START` необхідно підтвердити номер.
3. Номер нормалізується: верхній регістр, без пробілів/дефісів, кириличні символи-візуальні відповідники приводяться до латиниці.
4. Підтримуються способи `CAMERA` та `MANUAL`.
5. Невідповідність номера повертає `409` і не змінює стан роботи.
6. Підтвердження зберігається разом із часом, користувачем і способом підтвердження.

### 2.3. Звернення «Не можу виконати роботу»

1. Одне активне звернення на один рядок роботи.
2. Повторна відправка повертає наявне звернення, а не створює дублікат.
3. Причина зберігається кодом, коментар — до 500 символів.
4. Для `INCORRECT_ASSIGNMENT_DATA`, `LICENSE_PLATE_MISMATCH`, `TIME_UNAVAILABLE`, `OTHER` коментар обов’язковий.
5. До 5 зображень, кожне до 2,8 МБ, загальний обсяг до 10 МБ.
6. Після створення адміністратори локації отримують внутрішні сповіщення.
7. Звернення має стани `OPEN`, `VIEWED`, `NEEDS_CLARIFICATION`, `RESOLVED`, `CANCELLED`.
8. Робота не знімається з механіка автоматично.

### 2.4. Рішення адміністратора

Адміністратор локації може виконати лише одну з валідованих дій:

- `KEEP_CURRENT_MECHANIC` — залишити роботу механіку;
- `HELP` — надати інструкцію та залишити роботу механіку;
- `REASSIGN` — передати іншому активному механіку цієї локації;
- `RESCHEDULE` — змінити дату, час, пост і, за потреби, механіка;
- `REQUEST_CLARIFICATION` — повернути звернення на уточнення;
- `CANCEL` — скасувати рядок роботи та пов’язаний запис планувальника.

Для `REASSIGN`, `RESCHEDULE`, `REQUEST_CLARIFICATION` і `CANCEL` коментар обов’язковий. Перед перенесенням перевіряються конфлікти поста і механіка.

### 2.5. Журнал уточнень

Створюється окрема сутність `WorkExecutionIssueComment` з автором, текстом і часом. Механік може додати уточнення лише до власного активного звернення; адміністратор — до звернення своєї локації.

### 2.6. Адміністративний інтерфейс

У кабінеті керівника станції відображається блок «Потребує рішення адміністратора» з:

- автомобілем, номером, механіком і причиною;
- часом звернення та коментарем;
- вкладеннями;
- доступними адміністративними діями;
- повідомленням про конфлікт або помилку;
- автоматичним оновленням після виконання дії.

### 2.7. Тести та реліз

Обов’язкові перевірки:

- TypeScript;
- API security inventory;
- контрактні smoke-перевірки;
- повторна відправка звернення;
- паралельна відправка звернення;
- правильний/неправильний номер;
- ручне підтвердження;
- відсутній або неправильний webhook secret;
- rate limit входу;
- reassignment/reschedule/cancel;
- конфлікт поста або механіка;
- перевірка production runtime після деплою.

## 3. Критерії приймання

Функція вважається прийнятою, якщо:

1. Внутрішні маршрути без сесії не повертають дані CRM.
2. Webhook без production secret не приймає дані.
3. Пошук не обходить permission через `SHADOW`.
4. Механік не може стартувати роботу з іншим номером.
5. Усі адміністративні дії реально змінюють пов’язані записи, а не лише статус звернення.
6. Повторне або паралельне натискання не створює дублікатів.
7. Відповідь адміністратора приходить механіку як внутрішнє сповіщення.
8. Кожна зміна має audit event.
9. Дані різних локацій не змішуються.
10. Production build і TypeScript проходять без помилок.

## 4. Порядок релізу

1. API guards та rate limit.
2. Assignment-specific plate verification.
3. Повний execution-issue workflow і міграція.
4. Адміністративний UI.
5. Smoke/E2E перевірка.
6. Preview deployment, перевірка, production deployment.
