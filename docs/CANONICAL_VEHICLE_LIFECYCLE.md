# Turbo LEV — еталонний життєвий цикл автомобіля

Дата фіксації: 20.08.2026

## Принцип

У кожного автомобіля в конкретний момент часу є **один основний операційний статус**, який однаково показується на всіх сторінках CRM. Технічні статуси `ServiceAppointment`, `DiagnosticRequest`, `DiagnosticReview`, `WorkOrder`, кошторису, запчастин, QC та оплати залишаються у своїх агрегатах і не створюють паралельних «статусів авто».

Єдине джерело відображення — `deriveVehicleLifecycle()` / `getVehicleLifecycle()`.

Пріоритет джерел після створення відповідних сутностей:

1. майбутній підтверджений запис на наступні роботи (окрема гілка після ДК);
2. активний WorkOrder;
3. DiagnosticRequest + DiagnosticReview + факт активної ДК;
4. ServiceAppointment.

## Еталонні статуси

| Код | Статус | Бізнес-подія переходу |
|---|---|---|
| `PLANNED` | Заплановано | Створено запис у Планувальнику |
| `IN_WORK` | В роботі | Механік відсканував/підтвердив фактичний заїзд; діагностика розпочата |
| `DIAGNOSTIC_COMPLETED` | Завершена діагностика | Механік натиснув «Завершити діагностику» |
| `MANAGER_REVIEW` | На перевірці менеджера | Сервіс-менеджер відкрив завершену діагностику для перевірки |
| `CLIENT_DECISION` | Очікує рішення клієнта | ДК сформована і активне посилання відправлено/доступне власнику |
| `PARTS_SELECTION` | Підбір деталей | Після ДК обрано маршрут «Підбір деталей» |
| `WAITING_APPROVAL` | Очікує погодження | Кошторис/варіант робіт передано клієнту |
| `WAITING_PARTS` | Очікує деталі | Погодження отримано, необхідні деталі ще не готові |
| `READY_FOR_REPAIR` | Готовий до ремонту | Погодження та обов’язкові деталі готові |
| `IN_REPAIR` | У ремонті | Ремонт фактично розпочато |
| `QUALITY_CONTROL` | Контроль якості | Ремонт завершено та передано на QC |
| `WAITING_PAYMENT` | Очікує оплату | QC пройдений, фінальний рахунок сформовано |
| `READY_FOR_PICKUP` | Готовий до видачі | Фінансові умови виконано, авто можна видати |
| `DELIVERED` | Видано | Автомобіль фактично видано, сервісний цикл закритий |
| `CANCELLED` | Скасовано | Сервісний цикл/запис скасовано |
| `CLIENT_DECLINED` | Клієнт відмовився | Клієнт остаточно відмовився від запропонованого продовження робіт |

## Події, які НЕ є основним статусом

- ДК сформовано;
- ДК надіслано;
- клієнт відкрив ДК;
- деталі підібрано;
- запчастини замовлено;
- запчастини отримано;
- оплату отримано;
- повідомлення прочитано.

Такі події фіксуються в audit/timeline та можуть показуватися як пояснення до основного статусу.

## Супутні ознаки, які НЕ є основним статусом

- `OVERDUE` — Протерміновано;
- `NEEDS_ATTENTION` — Потребує уваги;
- `WAITING_MANAGER` — Очікує менеджера;
- `WAITING_CLIENT` — Очікує клієнта;
- `RETURNED_TO_MECHANIC` — Повернено механіку;
- `PAUSED` — Призупинено;
- `REWORK` — Доопрацювання;
- `WARRANTY` — Гарантійне звернення;
- `NO_SHOW` — Не приїхав;
- `RESERVE` — Резерв.

Наприклад: основний статус **«У ремонті»** + ознака **«Протерміновано»**. Не створюємо статус «Протермінований ремонт».

## Діагностичний маршрут

`Заплановано` → механік сканує авто → `В роботі` → механік завершує діагностику → `Завершена діагностика` → менеджер відкриває її → `На перевірці менеджера` → менеджер створює та відправляє ДК → `Очікує рішення клієнта`.

Після ДК:

### Маршрут А — наступний візит

Клієнт/менеджер обирає «Запис на наступні роботи» → створюється майбутній запис → основний статус **«Заплановано»**.

### Маршрут Б — ремонт через підбір деталей

«Підбір деталей» → `Підбір деталей` → `Очікує погодження` → `Очікує деталі` → `Готовий до ремонту` → `У ремонті` → `Контроль якості` → `Очікує оплату` → `Готовий до видачі` → `Видано`.

## Технічне зіставлення

### ServiceAppointment

- `BOOKED`, `RESERVE` → `PLANNED`
- `ARRIVED`, `DIAGNOSTICS` → `IN_WORK`
- `WAITING_PARTS_SELECTION` → `PARTS_SELECTION`
- `WAITING_CALCULATION`, `WAITING_APPROVAL` → `WAITING_APPROVAL`
- `WAITING_PARTS` → `WAITING_PARTS`
- `READY_FOR_REPAIR` → `READY_FOR_REPAIR`
- `IN_REPAIR` → `IN_REPAIR`
- `WAITING_QC` → `QUALITY_CONTROL`
- `WAITING_PAYMENT` → `WAITING_PAYMENT`
- `READY_FOR_PICKUP` → `READY_FOR_PICKUP`
- `COMPLETED` → `DELIVERED`
- `CANCELLED`, `NO_SHOW` → `CANCELLED`
- `PAUSED`, `WARRANTY` → основний `IN_REPAIR` + супутня ознака

### DiagnosticRequest / DiagnosticReview

- `IN_PROGRESS` / `RETURNED` → `IN_WORK`
- `SUBMITTED` без `reviewerUserId` → `DIAGNOSTIC_COMPLETED`
- `SUBMITTED` із `reviewerUserId` → `MANAGER_REVIEW`
- `CONFIRMED` + активна DiagnosticReportShare → `CLIENT_DECISION`

### WorkOrder

- `PARTS_REVIEW` → `PARTS_SELECTION`
- `WAITING_APPROVAL` → `WAITING_APPROVAL`
- `WAITING_PARTS` → `WAITING_PARTS`
- `READY_FOR_REPAIR` → `READY_FOR_REPAIR`
- `IN_REPAIR` → `IN_REPAIR`
- `WAITING_QC` → `QUALITY_CONTROL`
- `WAITING_PAYMENT` → `WAITING_PAYMENT`
- `READY_FOR_PICKUP` → `READY_FOR_PICKUP`
- `CLOSED` → `DELIVERED`
- `CANCELLED` → `CANCELLED`
- `PAUSED`, `REWORK`, `WARRANTY` → основний `IN_REPAIR` + супутня ознака

## Термінологія

Слово **«Лід»** не використовується у видимому інтерфейсі. Розділ називається **«Активні»**. Технічні поля/таблиці `leadId` можуть залишатися для сумісності та не визначають видиму термінологію.
