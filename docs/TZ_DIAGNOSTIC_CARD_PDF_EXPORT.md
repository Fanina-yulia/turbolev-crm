# Технічне завдання: PDF-файл діагностичної карти Turbo LEV

**Код стандарту:** `CRM-DOC-001`
**Версія:** 1.0
**Дата:** 05.09.2026
**Статус:** обов'язкове правило для збереження та поширення діагностичних карт

## 1. Мета

Після перевірки сервіс-менеджером зберігати діагностичну карту як окремий незмінний PDF-файл. Файл має бути відтворюваним, прив'язаним до конкретної ревізії ДК, доступним у CRM для перегляду/завантаження/друку та придатним для передачі клієнту через доступні канали.

PDF не є знімком DOM або тимчасовою копією екрана. Він формується на сервері зі збереженого snapshot конкретної ревізії `DiagnosticCardRevision`, тому зміна розміру монітора, теми, CSS або поточного стану сторінки не змінює вже збережений документ.

## 2. Бізнес-сценарій

1. Механік завершує структуровану діагностику.
2. Діагностика потрапляє до CRM у статусі `SUBMITTED` / «На перевірці».
3. Користувач CRM переглядає і перевіряє факти, findings, фото та примітку механіка.
4. Користувач натискає `Зберегти`.
5. Система забезпечує наявність ревізії ДК, формує PDF з усіма доступними даними та зберігає його у БД.
6. Кнопка змінює підпис на `Збережено`, поруч з'являється зелена іконка файла.
7. Повторне натискання для тієї самої ревізії є ідемпотентним: новий ідентичний PDF не створюється.
8. Якщо після збереження змінено коментар або інший факт ДК, створюється нова ревізія; кнопка знову показує `Зберегти`, доки нова ревізія не буде збережена.
9. Натискання зеленої іконки відкриває PDF у popup-вікні.
10. У popup доступні `Завантажити`, `Друкувати`, `Поділитися`.

## 3. Межі реалізації

### Входить до цього ТЗ

- серверна генерація PDF з кириличним шрифтом;
- збереження бінарного файла та метаданих у БД;
- зв'язок PDF із `DiagnosticCard`, `DiagnosticCardRevision` і номером ДК;
- перегляд PDF у CRM popup без переходу на іншу сторінку;
- завантаження та друк;
- native Web Share API для телефона/браузера, якщо він підтримується;
- fallback через короткоживуче захищене посилання та кнопки Telegram, WhatsApp, Viber і копіювання посилання;
- аудит створення та поширення PDF;
- permission/scope-перевірки та негативні відповіді `401/403/404`;
- адаптивність popup на ноутбуці, планшеті та телефоні.

### Не входить до першої версії

- окремий брендований дизайн PDF, погоджений як поліграфічний шаблон;
- автоматична відправка через серверні API Viber/WhatsApp/Telegram без участі користувача;
- електронний підпис або юридичне підписання документа;
- редагування PDF після формування;
- збереження необмеженої кількості фото без ліміту розміру.

Поточна версія використовує нейтральний читабельний документний шаблон Turbo LEV. Візуальний брендований шаблон можна додати окремою ревізією без зміни API та моделі ідемпотентності.

## 4. Вміст PDF

Документ повинен містити всі дані, які є у snapshot ревізії на момент збереження:

| Розділ | Обов'язкові дані |
|---|---|
| Заголовок | `ДІАГНОСТИЧНА КАРТА`, номер ДК, тип ревізії, дата формування |
| Автомобіль | марка, модель, рік, держномер, VIN, пробіг |
| Учасники | клієнт, телефон, механік, сервісна станція |
| Результат | перевірено/всього, норма, увага, дефекти, критичні findings, дата перевірки |
| Звернення | заявлена проблема, якщо вона є |
| Висновок | технічний висновок CRM, якщо він є |
| Коментарі | коментар механіка та менеджера, якщо вони є |
| Рекомендації | роботи та деталі з назвою, системою, пунктом перевірки й терміновістю |
| Матриця | кожна перевірена позиція, стан, позиція/зона, замір, note, finding, дія |
| Докази | доступні JPEG/PNG-фото findings; інші формати не втрачаються в CRM і позначаються у PDF як доступні в CRM |
| Нижній колонтитул | номер ДК, номер сторінки/загальна кількість сторінок, позначка формування CRM |

Порожнє значення відображається як `—`. `NOT_CHECKED` не рахується дефектом та показується окремим станом «Не перевірено».

## 5. Інтерфейс CRM

### 5.1. Панель дій діагностичної карти

- `Зберегти` — формує або повертає PDF для поточної ревізії;
- `Збережено` — означає, що для актуальної ревізії є PDF;
- зелена іконка файла — відкриває збережений PDF;
- іконка олівця — не змінює PDF напряму, а відкриває редагування примітки механіка;
- `Підбір деталей` — залишається окремим переходом до комерційного процесу.

Якщо PDF існує для старої ревізії, а поточна ревізія змінилася, UI не маскує стан як актуально збережений: кнопка повертається до `Зберегти`, а старий PDF залишається доступним до формування нового.

### 5.2. Popup PDF

Popup має:

- заголовок із назвою файла, ревізією та датою;
- вбудований `iframe`-переглядач PDF;
- `Завантажити` з `Content-Disposition: attachment`;
- `Друкувати` через окреме вікно браузера;
- `Поділитися`;
- fallback-канали: Telegram, WhatsApp, Viber, копіювання захищеного посилання;
- закриття хрестиком, кліком по затемненню та стандартним керуванням браузера;
- keyboard/focus-індикацію і `aria`-назви.

Внутрішня прокрутка дозволена лише в PDF popup як виняток `CRM-UI-002`. Основна сторінка діагностичної карти залишається цілісною та використовує document scroll за `CRM-UI-001`.

## 6. Модель даних

### `DiagnosticCardPdf`

- `id` — технічний ідентифікатор;
- `diagnosticCardId` — зв'язок із карткою;
- `diagnosticCardRevisionId` — унікальний зв'язок із ревізією;
- `fileName`, `mimeType`, `fileSize`, `fileData`;
- `generatedByUserId`, `generatedAt`, `createdAt`, `updatedAt`.

Для однієї ревізії допускається максимум один PDF. Старі PDF не перезаписуються, що зберігає історію документа.

### `DiagnosticCardPdfShare`

- `pdfId` — PDF, який поширюється;
- `tokenHash` — SHA-256 хеш високої ентропії, сам token у БД не зберігається;
- `expiresAt` — строк дії 30 днів;
- `revokedAt` — відкликання попереднього посилання;
- `createdByUserId`, `createdAt`, `updatedAt`.

При створенні нового посилання попереднє активне посилання для цього PDF відкликається. Прямий доступ за `id` PDF або номером ДК не є public-доступом.

## 7. API-контракт

### `GET /api/diagnostics/[id]/pdf?meta=1`

Повертає метадані останнього PDF та ознаку актуальності:

```json
{
  "ok": true,
  "pdf": {
    "id": "...",
    "fileName": "ДК-2026-000001.pdf",
    "mimeType": "application/pdf",
    "fileSize": 12345,
    "generatedAt": "2026-09-05T12:00:00.000Z",
    "revision": 2,
    "currentRevision": 2,
    "isCurrent": true
  }
}
```

### `GET /api/diagnostics/[id]/pdf`

Повертає бінарний PDF для авторизованого користувача. Параметр `download=1` перемикає `Content-Disposition` на `attachment`. Відповідь не кешується публічно.

### `POST /api/diagnostics/[id]/pdf`

Перевіряє `DIAGNOSTICS.WRITE` зі scope `LOCATION`, перевіряє row-level доступ до діагностики, забезпечує snapshot ревізії, генерує файл та повертає `pdf`, `cardNumber`, `revision`, `created`.

### `POST /api/diagnostics/[id]/pdf/share`

Перевіряє той самий доступ, вимагає збережений PDF, відкликає старий share-token та повертає одноразове унікальне посилання зі строком дії.

### `GET /api/public/diagnostic-card-pdf/[token]`

Не вимагає CRM-сесії, але приймає лише дійсний token. Перевіряє хеш, строк дії та відкликання. Повертає тільки PDF із `no-store`, `noindex, nofollow` та `nosniff`.

Помилки:

- `401` — немає сесії;
- `403` — відсутні permission або scope/row access;
- `404` — ДК/PDF/share-token не знайдені або token прострочений;
- `409` — відсутня структурована діагностика для snapshot або PDF застарів після зміни карти (`PDF_OUTDATED`);
- `413` — PDF перевищує ліміт 15 MB;
- `500` — неочікувана помилка, без повернення даних файла.

## 8. Безпека та цілісність

- Не приймати snapshot або HTML від браузера як джерело правди.
- Перед збереженням повторно читати структуровану ДК на сервері.
- Писати audit event `DIAGNOSTIC_CARD_PDF_CREATED` і `DIAGNOSTIC_CARD_PDF_SHARED`.
- Захищати GET/POST row-level scope так само, як картку ДК.
- Не повертати файл механіку або менеджеру іншої станції.
- Не зберігати public token у відкритому вигляді.
- Не включати в public response клієнтські метадані, JSON snapshot або технічні ідентифікатори, крім PDF-потоку.
- Використовувати advisory lock та unique constraint для ідемпотентності паралельних натискань.
- Обмежити розмір PDF і не дозволяти необмежене накопичення фото в одному файлі.

## 9. Адаптивність і доступність

Перевірити popup на ширинах 1920, 1440, 1366, 1280, 1024, 768, 390 і 360 px:

- popup не виходить за межі viewport;
- PDF займає доступну висоту, кнопки не обрізаються;
- на mobile кнопки переносяться у кілька рядків;
- основна сторінка не отримує небажаного fixed/sticky-блоку;
- фокус видимий, кнопки мають назви, посилання відкриваються у новій вкладці з `rel="noreferrer"`;
- помилки та завершення дій оголошуються через `role="status"` або видимий inline message.

## 10. Перевірки та критерії приймання

### Автоматичні

- Prisma schema validation/generation;
- TypeScript/Next production build;
- API security inventory;
- contract smoke для public/internal PDF маршрутів;
- pure renderer smoke: PDF починається сигнатурою `%PDF`, містить щонайменше одну сторінку та не падає на кирилиці;
- responsive/page integrity checks.

### Функціональні

1. Для ДК зі findings натискання `Зберегти` створює один PDF та показує `Збережено`.
2. Повторне натискання не створює другий PDF тієї самої ревізії.
3. Зелена іконка відкриває popup із PDF.
4. PDF можна завантажити й надрукувати.
5. `Поділитися` передає файл через Web Share API або готує посилання.
6. Telegram/WhatsApp/Viber/копіювання використовують захищене посилання, а не внутрішній ID.
7. Після зміни коментаря поточний PDF позначається неактуальним до повторного збереження.
8. Сторонній користувач без дійсного token не отримує файл.
9. PDF містить авто, VIN, номер, клієнта, висновки, рекомендації, матрицю та доступні фото.
10. Відсутня діагностика або відсутній snapshot повертають зрозумілий стан без створення порожнього файла.

### Definition of Done

- міграція застосована на production без ручного редагування БД;
- build і всі релевантні smoke перевірки пройдені;
- у git є ТЗ, schema, migration, service, route handlers, UI та audit contract;
- для релізу зафіксовані commit SHA, deployment URL і результати перевірок;
- немає P0/P1 дефектів у сценарії `ДК → Зберегти → PDF → Popup → Share/Download/Print`.
