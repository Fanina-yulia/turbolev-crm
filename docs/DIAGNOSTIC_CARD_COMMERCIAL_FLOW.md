# Діагностична карта → Комерційна пропозиція

## Бізнес-правило

Діагностична карта (ДК) і Комерційна пропозиція (КП) — різні документи.

- ДК відповідає: **що з автомобілем?**
- КП відповідає: **що пропонуємо зробити і скільки це коштує?**
- ЗН формується тільки після погодження клієнтом позицій КП.

## Статуси ДК

1. `DRAFT` — **Чернетка**. Механік проводить структуровану діагностику.
2. `SUBMITTED` — **На перевірці**. Після завершення механіком CRM автоматично створює/оновлює REVIEW-ревізію ДК.
3. `RETURNED` — **На уточненні**. Сервіс-менеджер повернув діагностику з коментарем.
4. `CONFIRMED` — **Підтверджена ДК**. Сервіс-менеджер підтвердив технічний висновок; створена FINAL-ревізія.

Надсилання клієнту не є статусом ДК.

## DiagnosticCard

На один `DiagnosticRequest` існує одна `DiagnosticCard` з номером `ДК-YYYY-NNNNNN`.

Карта має незмінні ревізії:

- `REVIEW` — автоматичний snapshot після submit механіка;
- `FINAL` — snapshot після підтвердження сервіс-менеджером.

Кожна ревізія має `sourceFingerprint`, snapshot та автора.

## Вміст ДК

Snapshot містить:

- клієнта;
- автомобіль, VIN, держномер, пробіг;
- станцію, механіка, сервіс-менеджера;
- скаргу/завдання;
- усі факти перевірки;
- `OK / ATTENTION / DEFECT`;
- заміри;
- фото;
- терміновість;
- рекомендовані дії;
- рекомендовані роботи та деталі;
- коментар механіка;
- технічний висновок.

ДК не містить цін, націнки, собівартості або постачальників.

## Перевірка сервіс-менеджером

Після `SUBMITTED` CRM формує rule-based технічний висновок. Менеджер може:

- скоригувати текст висновку;
- повернути ДК механіку з обов'язковим поясненням;
- підтвердити ДК.

Підтвердження створює FINAL-ревізію. Механік не має права підтверджувати ДК.

## Надсилання клієнту

Публічне посилання створюється тільки після `CONFIRMED`.

`DiagnosticReportShare` — це канал доставки, а не сам документ. Для нових структурованих діагностик клієнтський report будується з FINAL snapshot ДК. Для історичних підтверджених діагностик залишений legacy fallback.

## Створення КП

Після підтвердження ДК доступна окрема дія **Створити Комерційну пропозицію**.

CRM:

1. створює/повторно використовує внутрішній `WorkOrder` як контейнер процесу;
2. переносить рекомендовані роботи та деталі з `DiagnosticFinding` у `WorkOrderLine`;
3. зберігає зв'язок через `sourceEntity = DIAGNOSTIC_FINDING` та `sourceEntityId`;
4. створює DRAFT `WorkOrderEstimate` — Комерційну пропозицію;
5. якщо є деталі — відкриває `PartsRequest` для підбору.

До погодження клієнтом цей контейнер у UI не слід називати Наряд-замовленням.

## Подальший цикл

`Підтверджена ДК → КП (DRAFT) → підбір деталей / ціни → КП SENT → APPROVED / REJECTED → погоджені позиції → ЗН → ремонт`.

## Основні API

- `GET /api/diagnostics/[id]/card` — карта та список ревізій;
- `PATCH /api/diagnostics/[id]/structured` `action=SUBMIT` — submit механіка + автоматична REVIEW-ревізія;
- `PATCH /api/diagnostics/[id]` `status=CONFIRMED` — підтвердження менеджером + FINAL-ревізія;
- `POST /api/diagnostics/[id]/report` — створення клієнтського посилання тільки для підтвердженої ДК;
- `POST /api/diagnostics/[id]/commercial-proposal` — створення окремої КП.

## Ідемпотентність

- повторний submit з незміненими даними не створює дубль REVIEW;
- повторне підтвердження не створює другу FINAL-ревізію;
- повторний перенос рекомендацій не створює дубль `WorkOrderLine`;
- `WorkOrderEstimate` використовує fingerprint рядків і revisioning.
