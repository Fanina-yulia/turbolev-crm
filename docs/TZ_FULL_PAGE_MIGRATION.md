# ТЗ: стабілізація повноекранних сторінок після відмови від popup-вікон

## 1. Мета

Перевести flow «Нова заявка» з модального popup у звичайну сторінку CRM без
обрізання контенту, вкладених скролів, накладання нижньої панелі на поля та
порушення навігації браузера.

Сторінка заявки повинна однаково працювати після відкриття з огляду станції,
картки клієнта, картки автомобіля, Планувальника, а також після оновлення URL.

## 2. Першопричини проблем

1. Форма сторінки зберігала класи `requestModal` і `requestModalV4`, щоб не
   ламати старі DOM-мости. Глобальний `responsive-popups.css` сприймав її як
   popup і накладав `max-height`, `max-width` та overflow-обмеження.
2. `.requestModalHead` і `.requestActions` залишалися sticky. На сторінці це
   перекривало крок 3 та інші поля під час прокручування.
3. `.requestScroll` успадковував внутрішній scroll-контейнер popup. Виникала
   подвійна прокрутка: окремо сторінка, окремо форма.
4. Контейнер заявки не мав явного page-surface контракту, тому майбутні
   глобальні правила могли знову зачепити його як діалог.
5. Повідомлення Chrome «Щоб вийти з полноекранного режиму…» не є помилкою CRM:
   це системна підказка браузера після F11 або іншої команди fullscreen. CRM не
   викликає `requestFullscreen`.

## 3. Функціональні вимоги

### 3.1. Навігація

- Відкриття заявки додає `?newRequest=1` до URL.
- Оновлення сторінки з `newRequest=1` відкриває той самий flow без втрати стану
  маршруту.
- «Скасувати» та стрілка «Назад» повертають на попередній розділ CRM.
- `Back/Forward` браузера синхронізують стан заявки без дублювання історії.
- Переходи у бічному меню закривають flow заявки та очищають її маршрутні
  параметри.

### 3.2. Геометрія сторінки

- Сторінка займає лише колонку workspace поруч із sidebar.
- Сторінка використовує звичайний document scroll.
- Заборонені `position: sticky/fixed` для header, stepper, body та action bar
  повноекранної заявки.
- `requestScroll` і `requestBody` не мають власного обмеженого scroll.
- Нижня панель дій розміщена після всього контенту і ніколи його не перекриває.
- Усі довгі поля, VIN, телефони та тексти переносяться без горизонтального
  overflow.

### 3.3. Кроки flow

1. Автомобіль: номер/VIN, результат пошуку, ручне уточнення.
2. Клієнт: контактні дані, пошук клієнта, конфлікт власника.
3. Роботи/потреба: попередні роботи з прайсу або ручне введення, опис проблеми.
4. Запис: дата, Планувальник, пост, майстер та фінальне підтвердження.

Кнопки «Далі», «Назад», «Скасувати» і «Записати» повинні бути доступні після
прокрутки на всіх ширинах екрану. Перехід далі не повинен відбуватися при
активному пошуку, неповних даних авто або некоректному клієнті.

### 3.4. Адаптивність

- Desktop: сторінка fluid у межах workspace, без виходу за viewport.
- Tablet: поля та блоки переходять у 1–2 колонки, без горизонтального
  розширення shell.
- Mobile: один стовпець, action bar у нормальному потоці, touch-target не менше
  42px, без накладання на клавіатуру та нижню частину контенту.

### 3.5. Сумісність popup-компонентів

Існуючі клієнтські картки, drawer-и, системні повідомлення та телефонні popup-и
залишаються popup-примітивами. Правила `responsive-popups.css` застосовуються до
них, але не до елементів із `.requestPage` або `data-surface="page"`.

## 4. Технічні вимоги

- Форма має атрибути `data-surface="page"` та `data-page="new-request"`.
- Старі класи `requestModal/requestModalV4` зберігаються лише для сумісності
  DOM-мостів і не визначають геометрію сторінки.
- Page CSS має явно задавати `display:flex`, `flex-direction:column`,
  `max-height:none`, `overflow:visible`.
- Popup CSS має містити виключення `.requestPage` у всіх селекторах, які задають
  viewport-обмеження або scroll.
- Bridge-и можуть монтувати додаткові блоки лише всередину активної заявки та не
  повинні створювати дубльовані host-елементи.

## 5. Критерії приймання

- На висоті 768px крок 3 та поле опису повністю доступні після прокрутки.
- Нижній action bar не накладається на textarea, теги, прайс або помилки.
- У DevTools для `.requestPage` немає `max-height` від popup-контракту та немає
  `position: sticky/fixed` у header/actions.
- Немає горизонтального scroll на `body`, `.shell` і `.workspace`.
- Перезавантаження URL `?newRequest=1`, `Back`, `Forward`, відкриття з
  Планувальника та скасування працюють без дублювання заявки.
- `tsc`, contract smoke та production build завершуються успішно.
