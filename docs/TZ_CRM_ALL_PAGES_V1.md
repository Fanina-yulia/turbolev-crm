# Turbo LEV CRM — повне технічне завдання всіх сторінок

Версія: 1.0  
Дата: 26.08.2026  
Статус: базове ТЗ для стабілізації та подальшого розвитку CRM

## 1. Мета продукту

Turbo LEV CRM — операційна система СТО, у якій один наскрізний маршрут автомобіля проходить від першого звернення до видачі, оплати та післяпродажного супроводу.

CRM є єдиним джерелом фактичного статусу. Дані не повинні дублюватися вручну в окремих списках, Excel або месенджерах.

## 2. Наскрізний процес

`Звернення → Кваліфікація → Запис → Приїзд → Діагностика → ДК → КП → Погодження → Запчастини → Готовий до ремонту → Ремонт → QC → Оплата → Видача → Гарантія`

Кожна сутність має власний статусний цикл:

| Сутність | Призначення |
|---|---|
| Inquiry | вхідний контакт до кваліфікації |
| Lead | комерційний цикл до запису або втрати |
| Client | довгоживучий профіль клієнта |
| Vehicle | довгоживучий профіль автомобіля |
| Appointment | плановий запис і факт приїзду |
| Diagnostic | технічна діагностика |
| DiagnosticCard | зафіксований технічний документ |
| WorkOrder | фактичний виробничий процес |
| WorkOrderLine | окрема робота, запчастина, витратний матеріал або зовнішня послуга |
| PartsRequest | підбір, погодження та отримання деталей |
| SupplierOrder | замовлення постачальнику |
| Payment | конкретна оплата або зобов’язання |
| QualityControl | контроль якості |
| Warranty | окремий післяпродажний цикл |

Статус ремонту, причина очікування та фізичне місцезнаходження автомобіля не змішуються:

- `status` описує життєвий цикл сутності;
- `blocker` пояснює, чому процес не рухається;
- `vehicleLocation` показує, де фізично знаходиться авто.

## 3. Глобальна структура CRM

### 3.1. Основне меню

| Група | Сторінки |
|---|---|
| Робочий стіл | Огляд станції, Центр уваги |
| Робота з клієнтами | Комунікації, Планувальник |
| Клієнти та авто | Клієнти, Авто |
| Сервіс | Діагностика, Замовлення-наряди |
| Запчастини | Підбір запчастин, Закупівлі та склад |
| Фінанси | Фінансовий центр, Оплати |
| Управління | Аналітика, Налаштування |

«Нові звернення» та «Активні» — це контекстні режими/фільтри розділу «Комунікації», а не дублікати окремих даних. Старі маршрути «Виробництво», «Контроль якості», «Гарантії», «Ліди» та «Звернення» повинні редіректитися на актуальний розділ із відповідним фільтром.

### 3.2. URL та deep-link

- кожен розділ має стабільний `section` у query string;
- конкретні клієнт, авто, діагностика, ЗН, запис або метрика відкриваються через ID у URL;
- Back/Forward браузера відновлюють стан сторінки;
- після F5 зберігаються маршрут, активна вкладка й контекст;
- кнопка з Центру уваги відкриває конкретну сутність і потрібну вкладку, а не загальний список.

### 3.3. Єдині стани

Кожна сторінка повинна мати стани:

1. початкове завантаження;
2. оновлення без втрати вже видимих даних;
3. порожній результат;
4. помилка API з кнопкою «Повторити»;
5. відсутність права доступу;
6. успішне збереження;
7. конфлікт або заблокований перехід із поясненням причини.

## 4. Авторизація та доступ

### 4.1. Сторінка входу

Поля: e-mail/логін, пароль. Дії: увійти, відновити пароль, показати/сховати пароль.

Після входу користувач потрапляє у стартовий кабінет відповідно до основної ролі. Неавторизований користувач не отримує дані API й перенаправляється на `/auth/sign-in`.

### 4.2. Відновлення пароля

Поля нового пароля та підтвердження, перевірка складності, повідомлення про результат, без розкриття існування e-mail у системі.

### 4.3. Ролі та scope

Базові ролі: власник, виконавчий директор, керівник станції, сервіс-менеджер, механік, бухгалтер, адміністратор, CRM-адміністратор, спеціаліст запчастин, складський відповідальний.

Права поділяються на `READ`, `WRITE`, `CONFIRM`, `ASSIGN`, `CLOSE` та інші доменні дії. Scope: `SELF`, `ASSIGNED`, `TEAM`, `LOCATION`, `ALL`.

Право приховує сторінку в меню та обов’язково перевіряється повторно на сервері для кожного API-запиту. Секрети інтеграцій не повертаються у відкритому вигляді.

## 5. Сторінка «Огляд станції»

### Мета

Показати керівнику поточний стан станції та найкоротший шлях до дії.

### Блоки

- пошук авто/VIN;
- KPI: авто сьогодні, активні звернення, авто в роботі, очікування, готові до видачі, фінансові показники — залежно від права;
- живий маршрут станції від звернення до грошей;
- «Авто, що потребують уваги»;
- завантаження постів;
- блокери потоку;
- швидкі переходи у Планувальник, Діагностику, ЗН, Запчастини, QC та Оплати.

### Поведінка

Клік по KPI або картці відкриває відповідний розділ із фільтром. Огляд не є окремим сховищем: дані читаються з доменних API та оновлюються без вигаданих значень.

## 6. Сторінка «Центр уваги»

### Мета

Єдина операційна черга всіх ситуацій, які потребують дії, контролю або рішення.

### Фільтри

- Критично;
- Прострочено;
- Моя дія;
- Очікуємо;
- Сьогодні;
- категорії: звернення, СТО, діагностика, запчастини, постачальники, фінанси, зарплата, пости, якість, гарантії, мої задачі.

### Картка сигналу

Кожна картка показує: що сталося, чому це проблема, авто/клієнта, час прострочення або SLA, відповідального, пріоритет і кнопку контекстної дії.

Кнопка відкриває конкретний запис Планувальника, вкладку ЗН, КП, оплату, закупівлю, діагностику або інший контекст.

Живі сигнали не мають ручної кнопки «Виконано» — вони зникають після усунення причини. Ручні задачі мають «В роботу» та «Виконано».

### Правила розрахунку

- прострочений або непідтверджений приїзд;
- немає механіка/поста;
- зависла діагностика, КП, запчастина, постачальник або QC;
- прострочена дебіторка/кредиторка;
- критичні помилки інтеграцій;
- перевантаження постів або недостатнє завтрашнє завантаження.

Оновлення: при відкритті, при поверненні у вкладку, під час видимого екрану не рідше одного разу на 60 секунд і після важливих операцій.

## 7. Сторінка «Комунікації»

### Мета

Єдина inbox-стрічка дзвінків і повідомлень із прив’язкою до клієнта, авто та ліда.

### Канали

Binotel, сайт, Facebook Messenger, Instagram Direct, OLX, Telegram та інші підключені канали. Для кожного каналу показується live-стан інтеграції.

### Інтерфейс

- фільтри: усі, нові, пропущені, очікують відповіді, активні;
- пошук клієнта, телефону, авто або номера;
- список діалогів із unread, останнім повідомленням, каналом і SLA;
- права панель діалогу з хронологією;
- відповідь текстом, вкладеннями та emoji;
- повторна відправка невдалого повідомлення;
- картка клієнта й пов’язані авто;
- прив’язка зовнішнього контакту до існуючого клієнта;
- конвертація звернення в активний Lead;
- оновлення, синхронізація та health-check інтеграцій.

Вхідний дзвінок спочатку створює звернення, а не автоматичного клієнта чи ліда. Телефон нормалізується, виконується пошук існуючого клієнта та ведеться CallHistory.

## 8. Повний flow «Нова заявка»

Це повноекранна сторінка, не popup. Заборонені внутрішні scroll-контейнери, sticky header та sticky action bar, які перекривають поля.

### Крок 1 — Автомобіль

Пошук за держномером або VIN. Автоматично підтягуються марка, модель, рік, VIN, власник і пробіг. Якщо дані неповні — доступне ручне уточнення. Повторний пошук не створює дубль авто.

### Крок 2 — Клієнт

ПІБ, телефон, джерело, відповідальний. Верхнє поле телефону є єдиним основним полем. Кнопка «Пошук» виконує перевірку клієнта за телефоном; нижній дубль телефону не показується. Результат дозволяє використати існуючу картку клієнта.

### Крок 3 — Потреба/роботи

Попередня робота з каталогу або ручна потреба, опис проблеми, пріоритет, примітки.

### Крок 4 — Запис

Дата, час, пост/ресурс, механік, тривалість. Вибір вільної клітинки Планувальника фіксує початок і кінець замовлення в обраних слотах. Передзаповнені авто та клієнт не вводяться повторно.

Кнопки «Назад», «Далі», «Скасувати», «Записати» працюють після прокрутки, не перекривають контент і коректно працюють після F5 та Back/Forward.

## 9. Сторінка «Клієнти»

### Список

Пошук за ПІБ, телефоном, номером авто або VIN. Картка показує ім’я, телефон, кількість авто, кількість ЗН та останній візит. Пагінація — 24 записи на сторінку.

### Картка клієнта

Відкривається як drawer із URL-контекстом і містить:

- ПІБ, телефон;
- пов’язані автомобілі з реальним зображенням;
- дзвінки;
- Telegram-прив’язку;
- клієнтський кабінет;
- пов’язані замовлення-наряди;
- кнопку «Нова заявка».

Клік по авто або ЗН переводить у відповідний розділ, не втрачаючи ідентифікатор.

## 10. Сторінка «Авто»

### Список

Пошук за держномером, VIN, маркою, моделлю або власником. Картка показує бренд, марку/модель/рік, номер, VIN, власника, телефон, кількість ЗН, діагностик і пробіг.

Кожен автомобіль має зображення. Спочатку використовується готовий asset із бібліотеки модельних/кольорових варіантів; нова генерація запускається тільки за відсутності потрібного варіанту. Стан генерації, помилка та відсутність даних повинні бути зрозумілими.

### Картка авто

Вкладки: «Огляд», «Діагностика», «Сервісна історія».

Показати власника, марку, модель, рік, VIN, пробіг, двигун, паливо, привід, колір, зображення, діагностики, ЗН і timeline. Доступні ручне підтвердження кольору, код фарби, HEX та оновлення render.

## 11. Сторінка «Планувальник»

### Режими

- «Календар» — день/тиждень;
- «Пости та механіки» — добова ресурсна сітка.

### Фільтри

Локація, статус, виконавець, пост, пошук за ЗН/клієнтом/авто/номером/VIN.

### Добовий режим

Показати весь робочий день від відкриття до закриття, часовий крок 30 хвилин, пости, механіків, зону приймання, вільні слоти та поточний час. На стандартному desktop сторінка не повинна розтягуватися вертикально.

### Записи

Картка містить час початку/завершення, номер, авто, клієнта, коротку потребу, статус і відповідального. Клік відкриває редагування. Перетягування переміщує запис із перевіркою конфліктів. Захоплення бокового краю змінює тривалість; курсор стає двонапрямною стрілкою.

Клік по вільному слоту відкриває «Нову заявку» з переданими датою, часом, постом і механіком. Вибраний час повинен зберігатися саме в клітинках замовлення.

### Статуси запису

`RESERVE`, `BOOKED`, `ARRIVED`, `NO_SHOW`, `CANCELLED`. Downstream-статуси історичних записів читаються для сумісності, але джерелом правди після приїзду є Діагностика або ЗН.

## 12. Сторінка «Діагностика»

### Список

Фільтри: усі, очікують, в роботі, на перевірці, підтверджені, комерційна пропозиція, скасовані. Пошук за номером, VIN, авто, клієнтом, телефоном, номером ДК або механіком.

### Detail-панель

Показати статус, авто, номер, VIN, клієнта, механіка, дату, ДК, скаргу, висновок, результати структурованого чекліста, фото, дефекти, рекомендації та дії.

### Статусний цикл

- `DRAFT` — механік проводить діагностику;
- `SUBMITTED` — механік завершив, ДК на перевірці;
- `RETURNED` — повернуто механіку з обов’язковим коментарем;
- `CONFIRMED` — сервіс-менеджер підтвердив, створено FINAL-ревізію;
- `CANCELLED` — діагностику закрито без підтвердження.

Механік не може підтвердити фінальну ДК. WorkOrder не створюється автоматично під час підтвердження ДК.

### Діагностична карта

Одна ДК на один DiagnosticRequest, номер формату `ДК-YYYY-NNNNNN`. REVISION `REVIEW` створюється після submit, `FINAL` — після підтвердження. Snapshot містить авто, клієнта, станцію, механіка, скаргу, факти перевірки, заміри, фото, терміновість, рекомендації, роботи, деталі та висновок. Ціни й постачальники до ДК не входять.

### Вимога до layout

Поточні різні `max-height` списку та detail-панелі створюють подвійний scroll і чорну область унизу. Цільове рішення: один узгоджений scroll сторінки або однакова адаптивна висота двох колонок; контент ДК не обрізається.

## 13. Сторінка «Замовлення-наряди»

### Список

KPI: активні, у ремонті, заблоковані, готові до видачі. Пошук за номером ЗН, клієнтом, телефоном, авто або VIN. Фільтри за канонічним статусом.

### Картка ЗН

Показати номер, статус, авто, клієнта, запис, кошторис, оплачено, борг, механіка, пост, технічний висновок, контрольні дати, дзвінки, timeline та наступні дозволені переходи.

Вкладки/контексти: огляд, кошторис, запчастини, оплата, QC, історія.

### WorkOrderLine

Типи: `LABOR`, `PART`, `EXTERNAL`, `CONSUMABLE`, `OTHER`. Поля: опис, кількість, одиниця, планова ціна, собівартість, знижка, фактичні значення, каталог/постачальник, виконавець і статус.

Життєвий цикл рядка: `DRAFT → APPROVED → IN_PROGRESS → COMPLETED`; альтернативно `CANCELLED`. Планова фінансова snapshot-сума перебудовується транзакційно після зміни рядка.

### Hard Gates

- ЗН лише після підтвердженої ДК;
- ремонт лише після погодженої КП;
- замовлення деталей після потрібної оплати;
- старт ремонту лише за наявності обов’язкових деталей і механіка;
- додаткові платні роботи потребують нового погодження;
- `READY_FOR_PICKUP` тільки після успішного QC;
- видача лише після закриття обов’язкового балансу.

### Документи

«Документи / друк» відкриває пакет ЗН: кошторис, рахунок, ДК, акти та інші дозволені документи. Доступний друк і безпечний перегляд за ID.

## 14. Сторінка «Підбір запчастин»

### Вхідні дані

VIN або держномер, назва/артикул деталі, контекст підтвердженої ДК та рекомендації конкретного дефекту.

### Функції

- визначення авто за VIN/номером;
- перевірка fitment і confidence;
- пошук OEM/каталогу;
- пропозиції постачальників, ціна закупівлі, залишок, валюта, кратність, URL;
- розрахунок ціни продажу за націнкою;
- вибір конкретної пропозиції;
- запис у WorkOrderLine і PartsRequest;
- переходи до КП та вкладки запчастин ЗН.

Якщо номер знайдено, але VIN відсутній або некоректний, показати чітку причину й вимогу доповнити картку авто. Не створювати підбір із непідтвердженою ідентичністю.

## 15. Сторінка «Закупівлі та склад»

### Закупівлі

Черга PartsRequest і SupplierOrder: авто/ЗН, деталь, кількість, постачальник, ціна, ETA, відповідальний, статус і blocker.

Статуси: `NEW`, `SELECTING`, `SELECTED`, `WAITING_APPROVAL`, `APPROVED`, `ORDER_REQUIRED`, `ORDERED`, `PARTIALLY_RECEIVED`, `RECEIVED`, `INSTALLED`, `CANCELLED`.

### Постачальники

Картка постачальника показує контакти, API, спосіб оплати, строк доставки, активність та health-check. Прострочені або помилкові замовлення потрапляють у Центр уваги.

### Склад

Склади, зони, залишки, резерви, прихід, часткове отримання, видача в ремонт. Усі рухи мають аудит і зв’язок із ЗН/рядком деталі.

## 16. Сторінка «Фінансовий центр»

### Період і фільтри

Сьогодні, тиждень, місяць або довільний період; локація; drill-down за метрикою.

### KPI

Виручка, валовий прибуток, чистий управлінський прибуток, гроші зараз, дебіторка, кредиторка, прострочені залишки.

### Блоки

- P&L;
- Cash Flow;
- оборотний капітал;
- фінансовий ledger;
- проведені події, транзакції, відкриті зобов’язання, активні рахунки;
- drill-down до конкретного ЗН.

Фінансові дані читаються тільки з проведених фактів. `Outstanding = max(amount - settledAmount, 0)`. Не допускати подвійного нарахування доходу, собівартості або платежу.

## 17. Сторінка «Оплати»

### Черги

Вкладки: до оплати, частково оплачено, оплачено, борг/прострочено. Пошук за клієнтом, телефоном, авто, VIN або ЗН. Фільтр локації.

### Прийняття оплати

Вибір ЗН, сума, рахунок/каса, підтвердження. Оплата проводиться транзакційно, оновлює settled amount, борг, Центр уваги та фінансовий ledger. Кнопка «Відкрити ЗН» веде у вкладку оплати конкретного ЗН.

## 18. Сторінка «Аналітика»

### Вкладки

Загальне, Воронка, СТО/Виробництво, Діагностика, Фінанси, Запчастини.

### Вимоги

- період і локація застосовуються сервером;
- показуються тільки фактичні дані;
- метрики мають пояснення формули та джерела;
- drill-down відкриває операційний контекст;
- не показувати псевдо-100% або метрики з недостатньою/неоднозначною capacity data;
- персональні та фінансові показники приховуються без відповідного permission.

### Основні метрики

Конверсія звернення в запис/ЗН, завантаження постів, прострочення, активні авто, готові авто, діагностики, конверсія ДК→ЗН, виручка, валова/чиста маржа, дебіторка, кредиторка, запчастини та очікування поставок.

## 19. Налаштування

### 19.1. Графік роботи

Для кожного дня: працюємо/вихідний, час відкриття та закриття з кроком 30 хв. Збережений графік використовується Планувальником і availability API.

### 19.2. Персонал

Реєстр працівників: фото, ПІБ, категорія, посада, станція, дата прийняття, тип оформлення, активність. Категорія → посада → системна роль → права та тип кабінету. Основна роль визначає стартовий кабінет. Кнопка «Зберегти» зберігає всі зміни одним узгодженим запитом.

### 19.3. Постачальники

Довідник: назва, телефон, e-mail, сайт, строк доставки, умови оплати, активність. Окремо — API-підключення і тест.

### 19.4. Склад

Додати склад: назва, локація, відповідальний. Увімкнути/вимкнути без видалення історії.

### 19.5. Прайс робіт

Імпорт XLSX у два етапи: перевірка файлу → preview → імпорт. Показати загальну кількість, нові, оновлені та перші 30 рядків. Історичні WorkOrderLine заморожують назву, код, одиницю, ціну та нормо-години на момент створення.

### 19.6. Пости

Додати назву, тип і колір. Типи: підйомник, яма, розвал-сходження, без підйомника та інші налаштовані. Увімкнути/вимкнути пост без видалення історії.

### 19.7. Націнка

Націнка запчастин, доплата за роботу з деталями клієнта, коефіцієнти за типом автомобіля. Значення валідовані, зберігаються з аудитом і застосовуються до нових пропозицій.

### 19.8. Каса

Довідник рахунків/кас: назва, локація, активність. Фактичні оплати ведуться в розділі «Оплати».

### 19.9. Інтеграції

Телефонія Binotel, Meta, Instagram, OLX, Telegram, TikTok, вебхуки. Для кожного провайдера: поля конфігурації, маскування секретів, збереження, тест, статус, дата останньої синхронізації та зрозуміла помилка.

### 19.10. Камери

Додати камеру, UID/логін/пароль, призначення, локацію, токен, тест підключення, події та ротацію ingest-токена. Паролі не логуються й не показуються.

### 19.11. Шаблони діагностики

Створення, редагування, активність, default, порядок; секції та checklist items. Для item: назва, тип результату, обов’язковість, одиниця, допустимі значення, дефект, терміновість, рекомендована робота й деталь.

### 19.12. Оформлення

Тема: світла, темна, автоматична. Вибір зберігається локально та застосовується без перезавантаження.

### 19.13. Процеси та статуси

Показати сутності, системні статуси, переходи, Hard Gates, автоматичні actions, blockers і vehicle locations. Для системних статусів дозволено змінювати лише presentation: назву, колір, порядок, SLA, видимість і відповідальні ролі. Код, terminal, transition і gate незмінні.

### 19.14. Ролі та доступи

Вкладки «Користувачі та кабінети» і «Ролі та дозволи». Створення користувача, e-mail, роль, станція, активність, прив’язка до працівника. Ролі: дозволи за модулями й scope. Персональні ALLOW/DENY винятки мають причину, строк і аудит. Доступний безпечний режим «Переглянути систему очима користувача» без імперсонації.

## 20. Кабінет механіка

### Можливості

- призначені авто;
- сканування держномера та підтвердження приїзду;
- призначені діагностики;
- роботи й WorkOrderLine;
- старт, пауза, продовження, завершення роботи;
- findings, фото, коментарі, підтримка та уточнення;
- сповіщення;
- особистий графік;
- власна компенсація/зарплата в межах дозволу;
- постійно доступна кнопка `↪ Вийти з профілю`.

Механік бачить тільки призначений контекст відповідно до scope. Він не підтверджує фінальну ДК, не змінює фінансові правила й не бачить чужі компенсації.

## 21. Кабінет сервіс-менеджера та керівника

Сервіс-менеджер бачить приймання, клієнта, авто, діагностики на перевірці, КП, погодження, запчастини, супровід ремонту та наступну дію.

Керівник бачить операційний пульт, Центр уваги, виробничий потік, завантаження постів/механіків, фінансові та аналітичні показники в межах ролі.

Власник може без імперсонації переглянути ефективне меню іншого працівника через «Перегляд очима користувача». Це read-only режим і не змінює сесію іншого користувача.

## 22. Кабінет клієнта та публічна ДК

Публічне посилання створюється тільки після підтвердженої ДК. Клієнт бачить авто, результати перевірки, фото, дефекти, терміновість, рекомендації, повідомлення та окрему КП, коли вона готова.

Публічний контур не показує внутрішні нотатки, собівартість, права працівників або службові API. Клієнт може попросити прорахунок, ухвалити/відхилити пропозицію та залишити повідомлення.

## 23. Нефункціональні вимоги

### Адаптивність

- desktop: повна робоча область поруч із sidebar;
- tablet: 1–2 колонки, без горизонтального overflow body;
- mobile: один стовпець, touch-target не менше 42 px;
- довгі тексти, VIN, телефони й назви переносяться;
- сторінки не повинні виглядати як popup після міграції з модальних вікон.

### Продуктивність

- debounce пошуку 200–300 мс;
- AbortController для скасування застарілих запитів;
- `cache: no-store` для live операційних даних;
- eager-завантаження лише перших видимих зображень;
- не запускати повторну генерацію зображення, якщо готовий asset уже існує;
- сторінка не повинна блокуватися довгим F5/оновленням.

### Доступність

Семантичні кнопки й labels, видимий focus, keyboard navigation, aria-label для іконок, достатній контраст, коректні повідомлення screen reader для loading/error/success.

### Надійність

Усі критичні зміни виконуються транзакційно, ідемпотентно та з Audit Log. Повторне натискання не створює дублікати клієнта, авто, ДК, КП, рядка роботи, платежу або задачі.

## 25. Критерії приймання

1. Авторизований користувач бачить лише дозволені сторінки й дані своєї області.
2. Усі пункти меню відкривають правильний розділ без дублювання сутностей.
3. Back/Forward/F5 відновлюють контекст.
4. Нова заявка працює як сторінка без popup-геометрії та подвійного scroll.
5. Телефон у кроці клієнта показується один раз, кнопка «Пошук» виконує перевірку клієнта.
6. Вільна клітинка Планувальника зберігає вибрані дату, час, тривалість і ресурс.
7. Resize запису змінює його фактичний час і перевіряє конфлікти.
8. Клік «Відкрити запис» із Центру уваги відкриває саме прострочений запис.
9. Усі авто мають готове зображення або чесно пояснений стан генерації/відсутності даних.
10. Діагностична карта не обрізається через різні max-height та вкладені scroll-контейнери.
11. ДК, КП, ЗН, оплата, запчастини, QC та видача дотримуються Hard Gates.
12. Повторні дії ідемпотентні та не створюють дублікати.
13. Фінансовий центр використовує лише проведені факти й дає drill-down до ЗН.
14. Кнопка виходу постійно доступна в кабінеті механіка та завершує локальну й auth-сесію.
15. Світла, темна й автоматична теми не ламають читабельність.
16. На ширинах desktop/tablet/mobile немає обрізаних полів, горизонтального overflow body або перекриття action bar.
17. TypeScript, contract tests, RBAC/API smoke tests і production build проходять без помилок.

## 26. Тестовий сценарій end-to-end

1. Створити звернення через телефонію або форму.
2. Прив’язати існуючого клієнта та автомобіль.
3. Створити запис у Планувальнику з вільної клітинки.
4. Підтвердити приїзд скануванням номера механіком.
5. Провести й завершити діагностику.
6. Повернути її на уточнення та повторно подати.
7. Підтвердити ДК сервіс-менеджером.
8. Створити КП, підібрати деталь і відправити клієнту.
9. Погодити позиції, сформувати ЗН, виконати ремонт і QC.
10. Прийняти часткову та повну оплату.
11. Закрити ЗН, перевірити ledger, Центр уваги, аналітику та публічний кабінет клієнта.

Кожен крок має залишати audit trail і бути доступним у timeline автомобіля.
