# Turbo LEV CRM — Аналітика V2

## 1. Мета

Перетворити розділ **«Аналітика»** на центр управління СТО. Кожен показник має відповідати на три питання:

1. Що відбувається?
2. Чи є відхилення або проблема?
3. Куди натиснути, щоб перейти до конкретної операційної роботи?

Головний принцип: **тільки фактичні дані CRM**. Якщо показник неможливо коректно порахувати з наявної моделі даних, він не підміняється оцінкою.

### Етап 2 — реалізовано

### Етап 3 — наступний

- Персонал

## 3. Загальні фільтри

Фільтри спільні для всіх вкладок:

- Сьогодні
- 7 днів
- 30 днів
- Місяць
- Рік
- Довільний період
- Станція: вся доступна мережа або конкретна станція

Часова зона — `Europe/Kyiv`.

Для базових KPI автоматично формується попередній період такої ж тривалості. Він використовується для порівняння динаміки.

## 4. Права доступу

Базова аналітика: `ANALYTICS_READ`.

Додатково:

- фінансові показники: `ANALYTICS_FINANCIAL_READ`;
- продуктивність персоналу: `ANALYTICS_PERSONNEL_READ`;
- аналітика діагностики: `DIAGNOSTICS_READ`;
- аналітика запчастин: `PROCUREMENT_READ` або `PARTS_READ`.

При station-scoped доступі дані фільтруються тільки за дозволеними `locationId`.

Фінансові значення не передаються на клієнт користувачу без відповідного дозволу.

## 5. Загальне

### KPI

- Виручка
- Валовий прибуток
- Середній чек
- Авто приїхало
- Зараз у роботі
- Готово до видачі
- Завантаження постів
- Прострочені авто

### Формули

**Виручка** — сума `WorkOrderFinanceSnapshot.grossRevenue`, `kind=ACTUAL`, для закритих ЗН у періоді.

**Валовий прибуток** — сума `grossProfit` тих самих snapshot.

**Середній чек** — виручка / кількість ACTUAL snapshot.

**Авто приїхало** — є `actualArrivalAt` або статус означає, що етап прибуття вже пройдено.

**Зараз у роботі** — поточні активні записи в операційних статусах.

**Завантаження постів** — планово зайняті хвилини / доступні хвилини активних постів.

**Прострочені авто** — активний запис, де `plannedEndAt < now()`.

## 6. Воронка

Етапи:

1. Звернення / ліди — тільки при коректній глобальній атрибуції
2. Записано на СТО
3. Приїхали
4. Дійшли до діагностики
5. Створено ЗН
6. Передано в ремонт
7. Роботу завершено

Рахуються переходи:

- запис → візит;
- візит → діагностика;
- діагностика → ЗН;
- ЗН → ремонт;
- ремонт → завершення;
- запис → завершення.

Між етапами показуються і відсоток, і абсолютна втрата.

Етапи клікабельні та відкривають відповідний модуль CRM.

## 7. СТО / Виробництво

### Realtime KPI

- у роботі;
- у ремонті;
- очікують запчастини;
- очікують погодження;
- готові до видачі;
- прострочені.

### Завантаження постів

Для кожного активного поста:

- кількість записів;
- зайняті години;
- доступні години;
- % завантаження.

Формула:

`bookedMinutes / ((closeMinute - openMinute) × days)`.

### Цикл авто

Середній цикл — час від `actualArrivalAt` до `actualEndAt`.

Вчасно завершено — частка записів, де `actualEndAt <= plannedEndAt`.

### Причини затримок

Операційна класифікація:

- запчастини;
- погодження / калькуляція;
- не призначено механіка;
- пауза;
- робота / інше.

Список прострочених авто клікабельний та відкриває точний appointment у Планувальнику.

## 8. Діагностика — реалізовано

Джерела: `DiagnosticRequest`, `DiagnosticAssignment`, `DiagnosticInspection`, `DiagnosticCheck`, `DiagnosticFinding`, `DiagnosticTemplateItem`.

Station scope визначається через `DiagnosticAssignment.locationId`.

### KPI

- створено діагностик;
- завершено;
- підтверджено;
- кількість зауважень;
- кількість критичних знахідок;
- конверсія діагностика → ЗН;
- середній час діагностики.

### Стан перевірок

Окремо показуються:

- перевірено пунктів;
- `OK`;
- `ATTENTION`;
- `DEFECT`;
- findings з `urgency=CRITICAL`.

### Топ несправностей

Групування за назвою `DiagnosticTemplateItem.name`.

Для кожної позиції:

- увага;
- дефект;
- загальна кількість.

### Рекомендовані запчастини та роботи

Джерело:

1. `DiagnosticFinding.suggestedPartName / suggestedWorkName`;
2. fallback — `DiagnosticTemplateItem.suggestedPartName / suggestedWorkName`.

Показуються рейтинги найчастіших рекомендацій.

### Середній час

Для завершених inspections:

`completedAt - (startedAt || createdAt)`.

### Динаміка

По днях:

- створені діагностики;
- завершені inspections;
- зауваження.

## 9. Фінанси — реалізовано

Джерела: `FinancialEvent`, `CashTransaction`, `FinancialObligation`, `MoneyAccount`, `WorkOrderFinanceSnapshot`.

### P&L

Показуються:

- доходи;
- COGS;
- валовий прибуток;
- валова маржа;
- OPEX;
- операційний прибуток;
- інші доходи;
- інші витрати;
- податки;
- чистий прибуток;
- чиста маржа.

Розрахунок використовується з доменної функції `calculatePnl`.

### Cash Flow

- надходження;
- вибуття;
- чистий потік;
- операційний потік;
- інвестиційний;
- фінансовий.

Враховуються тільки `POSTED` cash transactions.

### Оборотний капітал

- дебіторська заборгованість;
- кредиторська;
- прострочена дебіторка;
- прострочена кредиторка.

Outstanding = `amount - settledAmount`, мінімум 0.

### Економіка замовлень

Для закритих ЗН з `WorkOrderFinanceSnapshot(kind=ACTUAL)`:

- кількість фіналізованих ЗН;
- виручка;
- валовий прибуток;
- валова маржа;
- середній чек;
- структура виручки: роботи / запчастини / зовнішні / інше;
- структура прямих витрат: запчастини / праця / зовнішні / матеріали / інше.

## 10. Запчастини / Закупівлі — реалізовано

Джерела: `PartsRequest`, `PartsRequestItem`, `Supplier`, `ServiceAppointment`.

При station scope список ЗН визначається через `ServiceAppointment.workOrderId`.

У період потрапляє PartsRequest, якщо в ньому в періоді була одна з подій:

- створення;
- підбір;
- погодження;
- замовлення;
- отримання;
- встановлення.

### KPI

- заявок;
- позицій;
- запитана кількість;
- отримана кількість;
- встановлена кількість;
- кількість, якої не вистачає для ремонту;
- прострочені ETA;
- середній час поставки.

### Фінансові KPI

При фінансовому доступі:

- вартість фактично отриманих запчастин;
- виручка встановлених запчастин;
- прибуток встановлених запчастин;
- маржа встановлених.

Формули:

`purchaseValue = purchasePrice × receivedQuantity`.

`installedRevenue = sellPrice × installedQuantity`.

`installedProfit = (sellPrice - purchasePrice) × installedQuantity`.

### Прострочений ETA

Позиція вважається простроченою, якщо:

- `etaAt < now()`;
- отримано менше, ніж замовлено;
- заявка не в термінальному статусі.

### Не вистачає для ремонту

Для `requiredForRepair=true`:

`max(0, quantity - receivedQuantity)` для незавершених заявок.

### Рейтинг запчастин

Для кожної агрегованої позиції:

- найменування;
- артикул;
- запитано;
- отримано;
- встановлено;
- виручка і прибуток при фінансовому доступі.

Основне сортування — за встановленою кількістю.

### Постачальники

- кількість заявок;
- кількість позицій;
- запитана кількість;
- отримана кількість;
- fulfillment %;
- сума закупівель при фінансовому доступі.

### Важливе обмеження

**Мертвий склад, оборотність залишків 30/60/90 днів і stock ageing не показуються.**

Причина: у CRM поки немає повноцінного складського ledger із залишком і датованим рухом кожної складської позиції. Такий показник без ledger був би недостовірним.

## 11. UX

- усі основні вкладки працюють у межах одного розділу «Аналітика»;
- фільтри не дублюються;
- картки компактні;
- фінансові дані не показуються без дозволу;
- червоний — проблема / прострочення;
- зелений — позитивний стан;
- помаранчевий — брендований акцент;
- таблиці мають горизонтальний скрол на вузьких екранах;
- на мобільному KPI переходять у 1–2 колонки;
- без зовнішньої chart library;
- кнопки переходів відкривають операційні модулі CRM.

## 12. API

- `/api/analytics` — базова аналітика, воронка, СТО;
- `/api/analytics/diagnostics` — діагностика;
- `/api/analytics/finance` — фінанси;
- `/api/analytics/parts` — закупівлі / запчастини.

Всі endpoints:

- `runtime=nodejs`;
- `force-dynamic`;
- `Cache-Control: no-store`;
- виключають demo-записи, де це застосовно;
- поважають RBAC та station scope.

## 13. Критерії приймання Етапу 2

1. У розділі «Аналітика» доступні вкладки `Діагностика`, `Фінанси`, `Запчастини`.
2. Загальні фільтри впливають на нові вкладки.
3. Діагностика показує фактичні checks/findings, а не статусний proxy.
4. Фінанси приховані без `ANALYTICS_FINANCIAL_READ`.
5. Запчастини приховують фінансові колонки без фінансового доступу.
6. Прострочені ETA рахуються по `etaAt` і факту отримання.
7. Немає вигаданого KPI «мертвий склад» без складського ledger.
8. Drill-down кнопки переводять у Діагностику, Фінансовий центр, Закупівлі та склад, ЗН.
9. Production build проходить TypeScript check.
10. На desktop і mobile дані залишаються читабельними.
