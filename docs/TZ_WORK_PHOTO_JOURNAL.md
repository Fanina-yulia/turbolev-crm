# TURBO LEV — журнал робіт і фінальний фотоконтроль

## 1. Мета

Створити єдиний операційний журнал усіх автомобілів і виконаних робіт СТО та зробити три фінальні фотографії обов'язковим завершальним доказом роботи механіка.

Фінальні фото потрібні не для окремого погодження, QC-рішення або «перезйомки». Їх призначення — дисципліна, контроль чистоти поста та можливість власника/виконавчого директора в будь-який момент відкрити історію і побачити, що залишив після себе механік.

## 2. Обов'язкова бізнес-логіка

1. Для останньої активної ремонтної роботи механік перед завершенням робить рівно три фото:
   - `TOOL_FIRST` — складений інструмент, ракурс 1;
   - `TOOL_SECOND` — складений інструмент, ракурс 2;
   - `WORKSPACE_CLEAN` — прибраний робочий пост.
2. Без комплекту 3/3 остання робота не переходить у `COMPLETED`, а Work Order не переходить далі у `WAITING_QC`.
3. Робота, яка не завершила виробничий цикл із 3/3 фінальними фото, не є придатною до нарахування механіку. Поточний захисний gate має залишатися серверним, а не лише UI-перевіркою.
4. Після успішного завершення фото стають незмінним доказом завершення. Механік не може тихо замінити їх після переходу роботи в `COMPLETED`.
5. Немає workflow `Підтвердити / Відхилити / Перезняти`. Власник лише переглядає архів.

## 3. Усунення помилки 413 при завантаженні

Поточна проблема: мобільний клієнт відправляє три оригінальні фото одним multipart-запитом, тому сумарний body може перевищити ліміт платформи.

### Нова логіка

- перед upload браузер стискає кожне фото:
  - довга сторона максимум 1600 px;
  - JPEG quality приблизно 0.82 з пониженням якості, якщо файл усе ще завеликий;
  - цільовий розмір до ~1.5 МБ;
- фото завантажуються послідовно, по одному HTTP-запиту;
- endpoint приймає частковий upload одного або декількох photo kind і робить idempotent `upsert`;
- UI показує прогрес `Зберігаю фото 1/3`, `2/3`, `3/3`;
- серверна перевірка типу і розміру зберігається;
- після збереження всіх трьох виконується `COMPLETE`.

## 4. Зберігання і доказовість

Поточна таблиця `WorkOrderCompletionPhoto` є source of truth. Для кожного фото зберігаються:

- `workOrderId`;
- `workOrderLineId`;
- `kind`;
- `fileName`;
- `mimeType`;
- `fileSize`;
- `fileData`;
- `createdByUserId`;
- `createdAt`;
- `updatedAt`.

На цьому етапі зберігається чинна DB-backed модель, щоб не вводити production-залежність від не налаштованого object storage. Видача фотографій назовні виконується через окремий авторизований endpoint, тому storage backend надалі можна замінити на private Blob/S3 без зміни UI-контракту.

## 5. Новий глобальний розділ CRM «Роботи»

### 5.1. Призначення

Один екран показує автомобілі протягом усього сервісного циклу: діагностика, ремонт, очікування, оплата, видача і закрита історія.

Один рядок = один `WorkOrder` / один сервісний цикл автомобіля.

### 5.2. Основні колонки

- Автомобіль + державний номер.
- № наряду.
- Тип процесу: `Діагностика`, `Ремонт`, `Діагностика + ремонт`.
- Короткий перелік/кількість робіт.
- Механік.
- Пост.
- Стан автомобіля/наряду.
- Оплата: `Оплачено`, `Частково`, `Не оплачено`, `Немає рахунку` (тільки користувачам з payment permission).
- Час початку/завершення.
- Фінальні фото: три малі квадратні thumbnail 3/3 або індикатор відсутнього комплекту.

### 5.3. Режими

- `Активні` — усе, що ще не `CLOSED/CANCELLED`.
- `Виконані` — роботи, де виробнича частина завершена (усі executable lines terminal або Work Order перейшов у post-repair statuses).
- `Усі` — повна доступна історія.

### 5.4. Фільтри

- пошук за авто, держномером, VIN, № наряду, клієнтом;
- механік;
- статус;
- фото: `усі / 3 з 3 / немає комплекту`;
- оплата: `усі / оплачено / частково / не оплачено`;
- дата.

## 6. Перегляд фотографій

У глобальному журналі три thumbnail відкривають fullscreen/lightbox-галерею:

- фото 1 — інструмент;
- фото 2 — інструмент, другий ракурс;
- фото 3 — робочий пост.

Поряд показуються:

- номер наряду;
- автомобіль і номер;
- механік;
- робота, на якій сформовано фінальний комплект;
- дата/час завершення;
- дата/час фото.

Ніяких кнопок погодження або редагування.

## 7. Фото всередині наряду

У `Наряди та ремонт` додається вкладка `Фото`.

Вона показує той самий read-only комплект/комплекти, що й глобальний журнал. Джерело даних одне — `WorkOrderCompletionPhoto`.

## 8. API

### `GET /api/work-journal`

Повертає доступні користувачу Work Orders з:

- vehicle/client;
- number/status;
- latest appointment/post/mechanic;
- executable lines;
- payment summary, якщо є `PAYMENTS_READ`;
- photo sets без binary body;
- URL protected photo endpoint.

Параметри: `scope`, `q`, `mechanicId`, `payment`, `photos`, `workOrderId`, `limit`.

### `GET /api/work-journal/photos/:photoId`

- лише authenticated CRM user;
- permission `WORK_ORDERS_READ`;
- перевірка фактичного WorkOrder scope через `canAccessWorkOrder`;
- `Content-Type` з БД;
- `Cache-Control: private`;
- binary body без публічного URL.

## 9. RBAC

- глобальний журнал використовує existing WorkOrder/production scope;
- користувач із `ALL` бачить усі доступні Work Orders;
- `LOCATION` — лише Work Orders своєї локації;
- `ASSIGNED/SELF/TEAM` — чинна модель `resolveVisibleWorkOrderIds`;
- фінансові поля повертаються тільки при `PAYMENTS_READ`.

## 10. Аудит

При upload створюється `MECHANIC_REPAIR_COMPLETION_PHOTO_UPLOADED` для кожного kind із workOrderId/lineId/kind/fileSize. Фінальний завершальний event залишається окремим.

## 11. Acceptance criteria

1. iPhone-фото не падають одним multipart body; upload 3 фото працює послідовно.
2. Кнопка завершення не переводить останню роботу в `COMPLETED`, якщо немає 3/3.
3. Після `COMPLETED` upload/overwrite фінальних фото для цієї line заборонений.
4. Власник може відкрити `Роботи` і побачити активні, завершені та закриті автомобілі.
5. Для завершеного ремонту видно три thumbnail без відкриття наряду.
6. Клік на thumbnail відкриває повні фото.
7. У наряді є вкладка `Фото` з тим самим комплектом.
8. Фото endpoint не віддає binary користувачу без доступу до відповідного WorkOrder.
9. Payment state не повертається користувачу без `PAYMENTS_READ`.
10. Production build, typecheck і security smoke проходять.
