# Технічне завдання: вирівнювання сторінки «Підбір запчастин» до варіанту 3

**Проєкт:** TURBO LEV CRM
**Модуль:** Підбір запчастин / Комерційна пропозиція
**Статус:** реалізовано в поточній кодовій базі, потребує візуальної перевірки на production
**Дата:** 07.09.2026

## 1. Мета

Переробити сторінку підбору запчастин так, щоб вона відповідала погодженому варіанту 3 та зразку комерційної пропозиції:

- сторінка повинна сприйматися як робочий кошик комерційної пропозиції, а не як технічний майстер із трьома великими темними блоками;
- зліва відображаються всі деталі, рекомендовані Діагностичною картою;
- у центрі відображається повна таблиця фактично вибраних деталей;
- справа відображаються підсумки закупки, продажу, прибутку та націнки;
- натискання на деталь зліва одразу відкриває popup з пропозиціями постачальників;
- після вибору пропозиції popup закривається, деталь зліва переходить у зелений стан, а рядок з’являється у центральній таблиці та підсумку справа.

## 2. Проблеми попередньої реалізації

1. Сторінка мала темні жорстко задані поверхні навіть у світлій темі CRM.
2. Заголовки «Крок 1 / Крок 2 / Крок 3» візуально домінували над робочими даними.
3. Ліва колонка показувала всі позиції червоними, хоча «потрібно підібрати» не є помилкою.
4. Вибраний стан не мав достатньо виразного зеленого оформлення.
5. Центральна область у порожньому стані займала надмірну висоту.
6. Правий блок містив багато порожнього простору та службових пояснень.
7. На сторінці одночасно існували різні візуальні моделі: робочий майстер, таблиця та комерційна пропозиція.
8. Користувачеві було неочевидно, що для відкриття підбору потрібно натиснути саме на рядок деталі.

## 3. Цільова інформаційна архітектура

### 3.1. Контекст ремонту

У верхній компактній панелі показуються:

- повернення до списку підборів;
- номер замовлення-наряду;
- клієнт;
- телефон;
- автомобіль і державний номер;
- пробіг;
- поточний етап замовлення.

Панель не повинна мати темний фон, якщо CRM працює у світлій темі. Вона повинна бути допоміжною, а не конкурувати з основною пропозицією.

### 3.2. Заголовок пропозиції

Показати:

- eyebrow: «ПІДБІР ЗАПЧАСТИН»;
- заголовок: «Комерційна пропозиція · чернетка»;
- коротке пояснення дії;
- праворуч — кількість деталей, кількість вибраних позицій та поточну націнку.

Якщо жодна позиція ще не вибрана, відсоток береться з налаштувань CRM після отримання пропозицій. До моменту отримання конкретного значення показується «з налаштувань», а не вигадана ціна.

### 3.3. Ліва колонка — деталі до заміни

Заголовок:

- «ЗАМІНА · N»;
- «Деталі до заміни»;
- «Позиції з Діагностичної карти»;
- лічильник `вибрано / всього`.

Під заголовком:

- поле «Знайти деталь…»;
- лічильник результатів пошуку;
- список деталей із нумерацією.

Рядок деталі містить:

- номер;
- назву деталі;
- вузол або позицію;
- кількість;
- стан.

Стани:

- `+ очікує` — пропозиція ще не вибрана;
- `✓ вибрано` — пропозиція збережена;
- активний рядок може мати помаранчевий акцент, але не повинен виглядати як помилка.

Вибраний рядок:

- зелений фон із низькою насиченістю;
- зелена вертикальна смуга або зелений border;
- зелений текст стану;
- `aria-pressed="true"`.

Натискання на будь-яку частину рядка відкриває popup підбору для цієї деталі.

### 3.4. Центральна колонка — вибрані деталі

Заголовок:

- «КОШИК · N»;
- «Вибрані деталі»;
- «Позиції, які увійдуть до Комерційної пропозиції»;
- кнопка `+ Додати` для переходу до наступної невибраної деталі.

Таблиця повинна містити такі колонки:

1. №
2. Кількість, шт.
3. Артикул
4. Бренд
5. Номенклатура
6. Постачальник
7. Склад
8. Ціна закупки, грн
9. Сума закупки, грн
10. Ціна продажу, грн
11. Сума продажу, грн
12. Прибуток, грн
13. % націнки
14. Дія

Для таблиці:

- горизонтальна прокрутка дозволена лише всередині таблиці;
- сторінка не повинна розширюватися за межі viewport;
- заголовок таблиці залишається читабельним;
- закупівельні значення мають нейтральний колір;
- продаж, прибуток і позитивний фінансовий результат — зелений;
- дія `Змінити` повторно відкриває popup для відповідної деталі.

Порожній стан має бути компактним і містити:

- `Вибраних деталей ще немає`;
- коротку інструкцію;
- кнопку `Додати першу деталь`.

### 3.5. Права колонка — кошик та маржа

Заголовок:

- «ПІДСУМОК»;
- «Кошик та маржа»;
- «Автоматичний розрахунок пропозиції».

Показати:

- стан підбору: не завершено або завершено;
- кількість вибраних позицій;
- закупку;
- продаж;
- прибуток;
- націнку;
- загальну суму до пропозиції;
- джерело даних: постачальник, склад, API.

Фінансові значення перераховуються від `selectedLines`, а не від локально введених користувачем значень.

Кнопки:

- `Підготувати до погодження`;
- `Відкрити в ЗН →`.

Кнопки недоступні, якщо немає вибраних позицій або відсутній `workOrderId`.

## 4. Popup підбору постачальника

Функціональна логіка popup зберігається:

1. Відкрити popup натисканням на деталь.
2. Автоматично підставити назву/артикул деталі.
3. Передати VIN або державний номер до пошуку.
4. Паралельно запросити довідковий каталог і пропозиції постачальників.
5. Показати вкладки «Оригінали» та «Аналоги».
6. Показати постачальника, склад, наявність, закупівельну та продажну ціну.
7. При натисканні `Вибрати` зберегти вибір через `/api/parts-selection/select`.
8. Закрити popup після успішного збереження.
9. Оновити зелену ознаку рядка, центральну таблицю та правий підсумок.
10. При помилці залишити popup відкритим і показати повідомлення користувачу.

Popup повинен закриватися:

- кнопкою `×`;
- кнопкою `Закрити`;
- натисканням поза межами діалогу;
- клавішею `Escape`.

## 5. Дані та розрахунки

### 5.1. Джерело деталей

Деталі беруться з результатів структурованої Діагностичної карти та ручних рекомендацій, якщо вони присутні.

### 5.2. Джерела цін

Пропозиції завантажуються через чинні API CRM:

- BM Parts;
- Юнік Трейд;
- інші налаштовані постачальники.

Якщо один із провайдерів не відповів, сторінка не повинна падати. Показується попередження «Не всі API відповіли» із переліком проблемних провайдерів.

### 5.3. Формули

Для кожного рядка:

```text
сума закупки = ціна закупки × кількість
сума продажу = ціна продажу × кількість
прибуток = (ціна продажу − ціна закупки) × кількість
```

Значення `ціна продажу` та `markupPercent` приходять із серверного розрахунку постачальника/налаштувань CRM. Клієнтський інтерфейс не повинен самостійно підміняти серверний розрахунок.

## 6. Візуальні стандарти

- світла тема: `var(--bg)`, `var(--panel)`, `var(--panel-2)`, `var(--line)`, `var(--text)`;
- темна тема: ті самі глобальні токени, без жорстко зашитих темних поверхонь у робочій області;
- помаранчевий — основна дія та активний етап;
- зелений — вибрано, доступно, продаж, прибуток;
- жовтий — очікує або потребує уваги;
- червоний — лише помилка, недоступність або критичний стан;
- мінімальний розмір тексту — 10px для технічних підписів і 11px для робочих даних;
- картки: border-radius 8–10px;
- відступи між колонками: 10px;
- не використовувати великі порожні блоки з фіксованою висотою.

## 7. Адаптивність

### Desktop

- три колонки;
- центральна таблиця прокручується горизонтально всередині себе;
- права колонка не розтягується на всю висоту екрана без контенту.

### Tablet

- ліва та центральна колонки залишаються зверху;
- підсумок переходить на всю ширину нижче;
- фінансові показники та дії розкладаються у дві внутрішні колонки.

### Mobile

- колонки переходять у послідовний вертикальний порядок: деталі → вибрані деталі → підсумок;
- контекстна панель приховує другорядні поля;
- таблиця залишається горизонтально прокручуваною всередині контейнера;
- popup займає доступну ширину з відступом 8px;
- кнопки мають доступну область натискання не менше 31px.

## 8. Доступність

- заголовки колонок мають `aria-labelledby`;
- popup має `role="dialog"` та `aria-modal="true"`;
- рядки деталей мають `aria-pressed`;
- статусні повідомлення мають `aria-live="polite"`;
- кожне поле пошуку має доступний label або `aria-label`;
- усі дії доступні з клавіатури;
- focus-visible не повинен бути видалений глобальними стилями.

## 9. Критерії приймання

1. У світлій темі сторінка має світлі поверхні та відповідає зразку комерційної пропозиції.
2. У темній темі сторінка не має білого «вибитого» фону та продовжує читатися.
3. Клік по деталі зліва відкриває popup без додаткового натискання іншої кнопки.
4. Після вибору пропозиції popup закривається.
5. Вибрана деталь стає зеленою зліва.
6. Вибрана деталь з’являється в таблиці з усіма погодженими колонками.
7. Правий підсумок показує правильні закупку, продаж, прибуток і націнку.
8. Зміна постачальника оновлює саме відповідний рядок, не створюючи дубль.
9. Пошук зліва фільтрує список деталей без перезавантаження сторінки.
10. При відсутності пропозицій або помилці API користувач отримує зрозуміле повідомлення.
11. На ширині desktop немає горизонтального overflow всієї сторінки.
12. На mobile таблиця прокручується тільки в межах таблиці.
13. TypeScript, UI-контракти та production build проходять без помилок.

## 10. Обсяг змін

У межах цього доопрацювання змінюються:

- `app/parts-catalog.tsx` — цільова структура представлення, стани вибору та доступність;
- `app/parts-catalog.module.css` — світла адаптивна візуальна система варіанту 3;
- цей документ — зафіксовані вимоги та критерії приймання.

API постачальників, серверний розрахунок націнки, endpoint збереження вибраної деталі та бізнес-логіка замовлення-наряду не змінюються.
