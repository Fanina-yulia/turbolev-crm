# TURBO LEV CRM — Підбір запчастин: full-width «Вибрані деталі» + inline пропозиції постачальників

Дата: 17.09.2026  
Модуль: `parts` / підбір запчастин із Діагностичної карти  
Екран: `PartsSelectionWorkspaceV4`  
Статус: approved implementation spec

## 1. Мета

Перебудувати сторінку підбору запчастин відповідно до погодженої візуалізації без втрати наявного функціоналу, API-контрактів, аудиту, staging-логіки та переходу до Комерційної пропозиції.

Ключова вимога: блок **«Вибрані деталі» повинен займати всю доступну ширину робочої області**. Це головна робоча поверхня, у якій надалі з'являтиметься додаткова інформація. Під ним на desktop розташовується двоколонкова робоча зона: зліва «Деталі до заміни», справа «Пропозиції постачальників».

## 2. Джерело істини

Не створювати нову паралельну бізнес-логіку. Використовувати чинний `PartsSelectionWorkspaceV4`, його state, API та функції:

- `/api/diagnostics/[id]/structured`;
- `/api/diagnostics/[id]/commercial-handoff`;
- `/api/parts/search`;
- `/api/parts/suppliers`;
- `/api/parts-selection/select`;
- `/api/parts-selection/line`;
- поточний audit trail ручних правок;
- pre-confirmation staging;
- VIN/OE/OEM/аналоги/assembly cascade;
- ручне підтвердження непідтвердженої сумісності;
- захист locked/ordered/received позицій;
- поточний handoff до Комерційної пропозиції.

Жодних вигаданих цін, залишків, термінів, маржі, постачальників або статусів.

## 3. Нова desktop-компоновка

Робоча область на екранах від `1181px` будується у дві колонки:

- ліва колонка: `clamp(340px, 27vw, 430px)`;
- права колонка: `minmax(0, 1fr)`;
- gap: 12px;
- усі основні панелі вирівнюються по верхньому краю.

Порядок блоків:

1. Контекст авто / клієнта — на всю ширину.
2. «Вибрані деталі» — на всю ширину.
3. «Деталі до заміни» — нижче зліва.
4. «Пропозиції постачальників» — нижче справа.
5. Системне повідомлення — нижче на всю ширину.

## 4. Контекст авто

Зберегти без втрати даних:

- номер ЗН;
- автомобіль;
- держномер;
- VIN;
- клієнта;
- телефон;
- кнопку «← До центру».

Контекст не повинен розтягувати нижні панелі та не повинен змінювати бізнес-логіку навігації.

## 5. «Вибрані деталі» — головна full-width поверхня

### 5.1. Геометрія

- `grid-column: 1 / -1`;
- займає 100% доступної ширини контенту;
- не обмежується шириною правої колонки;
- горизонтальний overflow таблиці дозволений лише всередині table-scroll контейнера;
- сама картка не повинна створювати горизонтальний scroll сторінки.

### 5.2. Header

Зберегти:

- `КОШИК · N`;
- заголовок `Вибрані деталі`;
- пояснення про автоматичні API-дані та аудит ручних правок;
- суму продажу;
- прибуток.

### 5.3. Таблиця

Не видаляти жодну чинну колонку:

1. №;
2. К-сть, шт.;
3. Артикул;
4. Бренд;
5. Номенклатура;
6. Постачальник;
7. Склад;
8. Ціна закупки, грн;
9. Сума закупки, грн;
10. Ціна продажу, грн;
11. Сума продажу, грн;
12. Прибуток, грн;
13. %;
14. Дія.

Ширина таблиці має залишатися достатньою для майбутнього розширення без нового редизайну. Наявні inline-edit, `Редагувати`, `Змінити`, lock reason, ручні маркери та derived values зберегти.

### 5.4. Footer

Зберегти:

- Закупка;
- Продаж;
- Прибуток;
- CTA `До комерційної пропозиції →`;
- поточну disabled-логіку CTA, якщо немає WorkOrder або кошик порожній.

## 6. «Деталі до заміни»

На desktop блок розміщується під full-width кошиком у лівій колонці.

Зберегти:

- фактичну кількість потреб;
- selected/total counter;
- назву деталі;
- позицію;
- кількість;
- `✓ вибрано`;
- `+ підібрати`;
- активний рядок;
- відкриття підбору саме для вибраної потреби.

Рядки залишаються компактними, назва може займати до двох рядків.

## 7. «Пропозиції постачальників» як inline робоча зона

### 7.1. Desktop

Чинний picker перестає сприйматися як fullscreen popup і в desktop-режимі вбудовується у праву нижню колонку поруч із «Деталі до заміни».

Це **не новий компонент і не дубль API-логіки**. Використовується той самий picker/state, який уже:

- запускає reference search;
- викликає supplier API;
- сортує за брендом / ціною / наявністю / терміном;
- фільтрує постачальника;
- групує оригінали / аналоги / review-required / assembly;
- показує залишки по складах;
- показує compatibility;
- вимагає manual confirmation там, де це потрібно;
- додає позицію у staging/canonical cart через поточний API.

### 7.2. Empty state

До вибору деталі справа повинна бути видима окрема робоча зона з текстом:

- `Пропозиції постачальників`;
- `Оберіть деталь зі списку зліва`;
- `Тут з’являться живі пропозиції, ціни, наявність і терміни з підключених API.`

Це лише UI-empty-state. Він не містить фейкових рядків або цін.

### 7.3. Відкритий picker

На desktop:

- `position` не `fixed`;
- немає затемнення всього CRM;
- немає blur фону;
- picker займає 100% правої колонки;
- header picker візуально читається як секція `Пропозиції постачальників`;
- close button залишається;
- усі чинні controls і supplier rows залишаються функціональними;
- max-height обмежується так, щоб список мав власний scroll, а сторінка не стрибала.

## 8. Tablet / mobile

На ширині до `1180px` не змінювати перевірену popup-модель:

- picker може залишатися modal/fullscreen відповідно до чинних responsive rules;
- «Вибрані деталі» залишається вище «Деталі до заміни»;
- нижня зона складається в одну колонку;
- жодна дія не повинна ставати недоступною.

## 9. Функціонал, який категорично не можна втратити

- VIN → OE/OEM → аналоги → постачальники;
- пошук по назві/артикулу;
- BM Parts / UniTrade / інші configured suppliers;
- OEM/analog/assembly cascade;
- compatibility tiers;
- ручне підтвердження непідтверджених позицій;
- stock details;
- сортування;
- supplier filter;
- staging до CONFIRMED;
- canonical selection після CONFIRMED;
- аудит;
- ручне редагування кошика;
- markup / sell price logic;
- причина ручної зміни ціни;
- locked rows;
- синхронізація PartsRequestItem;
- перехід до КП.

## 10. Технічні обмеження

- жодних DB migrations;
- жодних змін API contract;
- жодних hardcoded business values;
- шрифти не нижче 11px;
- новий layout override завантажується після `parts-picker-ultra-compact.css`, щоб desktop inline layout мав фінальне слово;
- responsive modal rules зберігаються для <=1180px.

## 11. Acceptance criteria

Реалізація прийнята, якщо одночасно виконано все нижче:

1. На desktop «Вибрані деталі» візуально займає всю ширину робочої області.
2. Під ним зліва знаходяться «Деталі до заміни».
3. Під ним справа є зона «Пропозиції постачальників».
4. До вибору деталі справа показується чесний empty state без вигаданих даних.
5. Після натискання на потребу чинний supplier picker відкривається inline справа, а не поверх усього CRM.
6. Пошук, сортування, supplier filter, compatibility, stock details та додавання в кошик працюють без зміни API.
7. Всі 14 колонок кошика збережені.
8. Inline editing кошика працює.
9. `До комерційної пропозиції →` має ту саму бізнес-умову доступності.
10. Tablet/mobile не втрачає modal-поведінку picker.
11. `npm build` проходить, включно з parts picker smoke та UI font floor.
12. Production deployment має стан `READY`.
