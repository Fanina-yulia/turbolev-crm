# Turbo LEV CRM — стандарт адаптивності всіх сторінок

**Код стандарту:** `CRM-UI-003`  
**Версія:** 1.0  
**Дата:** 2026-09-02  
**Статус:** обов'язковий для всіх внутрішніх і клієнтських екранів CRM  
**Пов'язаний стандарт:** `CRM-UI-001` — цілісна сторінка без фіксованих робочих секцій

## 1. Мета

CRM повинна однаково добре працювати на робочому моніторі, ноутбуці 15", планшеті та телефоні. Користувач не повинен змінювати масштаб браузера, щоб побачити основний заголовок, авто, статус, таблицю або головну дію.

Цей документ є єдиним UI-контрактом для:

- shell, бічної навігації та глобальних дій;
- усіх 17 функціональних модулів із `docs/modules/module-registry.json`;
- сторінок у query-маршруті CRM та клієнтських кабінетів;
- нових сторінок, компонентів і CSS після дати набуття чинності.

## 2. Принципи

1. **Спочатку ширина робочої області.** Shell використовує `minmax(0, 1fr)`, сторінки не розширюють body через власний `min-width`.
2. **Один документний вертикальний scroll.** Основний список, detail, header, action bar і нижній контент ростуть разом. Внутрішній scroll дозволений лише за винятками з розділу 8.
3. **Не стискати текст заради сітки.** На вузькому екрані блоки переходять у колонку, а не перетворюють підписи на мікротекст.
4. **Одна головна дія.** На екрані має бути зрозуміло, що робити далі; другорядні дії не конкурують з primary CTA.
5. **Дані важливіші за декор.** Першими залишаються авто, номер, VIN, клієнт, статус, blocker і наступна дія.
6. **Статус не залежить лише від кольору.** Кожен статус має текст і/або іконку; червоний, жовтий і зелений є підсиленням.
7. **Компонентний стандарт.** Повторюваний VehicleHeader, StatusBadge, ActionBar, DataTable, EmptyState або ErrorState виправляється в одному місці.
8. **Робота на 100% browser zoom.** Перевірки виконуються без вимоги зменшувати масштаб Chrome/Edge.

### 3.1. Breakpoint contract

Breakpoint-и є орієнтирами, а не приводом робити окрему версію кожної сторінки:

| Діапазон | Token / поведінка |
|---|---|
| `>= 1601px` | `--crm-layout-gutter: clamp(24px, 2vw, 34px)`; expanded sidebar; багатоколонкова сітка. |
| `1181–1600px` | `--crm-layout-gutter: clamp(16px, 1.7vw, 26px)`; зменшені картинки та gap. |
| `901–1180px` | sidebar до 215px; основні двоколонкові блоки переходять в один потік, якщо колонки стають менші за 320px. |
| `761–900px` | tablet/малий laptop; header і action groups переносяться, таблиці скроляться локально. |
| `481–760px` | mobile navigation, одна колонка, кнопки не менші 44px по висоті. |
| `<=480px` | одна колонка для KPI та форм, gutter 12px, довгі значення переносяться. |

Не можна використовувати viewport breakpoint як єдину умову для збереження трьох колонок. Перед вибором сітки перевіряється мінімальна ширина контенту: `minmax(0, 1fr)` або `minmax(280px, 1fr)` для самостійних карток.

## 4. Глобальні розміри та типографіка

| Токен | Значення | Застосування |
|---|---:|---|
| `--crm-font-copy` | 16px | основний текст сторінки |
| `--crm-font-control` | 15px | input/select/button |
| `--crm-font-label` | 14px | label і підписи полів |
| `--crm-font-meta` | 12–13px | час, джерело, helper, статусний контекст |
| `--crm-font-floor` | 11px | абсолютний мінімум для видимого UI; виняток — тільки мікрографіка номерного знака |
| control height | 40px desktop / 44px touch | поля, кнопки, tabs |
| spacing scale | 4/8/12/16/20/24/32px | gap, padding, секції |
| radius | 8/10/12/16px | control, card, modal відповідно |

Заголовки можуть бути fluid через `clamp`, але не мають ламати header:

- H1 сторінки: `clamp(24px, 2.2vw, 32px)`;
- H2 секції: `clamp(18px, 1.5vw, 24px)`;
- назва картки: 14–18px;
- VIN, артикул і системні ID: monospace, `overflow-wrap:anywhere`, copy action.

Довільний `font-size` менше 11px для тексту заборонений. Підписи не приховуються через `white-space: nowrap`, якщо це призводить до обрізання; для one-line таблиць використовується ellipsis + title/tooltip.

## 5. Shell і навігація

### Desktop

- shell: `grid-template-columns: clamp(215px, 14vw, 265px) minmax(0, 1fr)`;
- sidebar не має розширювати body; його внутрішня навігація може scrollитися лише вертикально;
- workspace має `min-width: 0`, width 100% і fluid horizontal padding;
- глобальні launcher/toast не беруть участі в grid flow;
- fixed-елемент не перекриває заголовок, поле або CTA.

### Tablet/mobile

- sidebar переходить у кероване mobile menu;
- відкриття меню не зсуває і не обрізає робочу сторінку;
- кнопка menu має доступну назву, `aria-expanded` і видимий focus;
- нижня частина сторінки не перекривається navigation/action bar;
- touch target — не менше 44×44px.

### Групи меню

Групи залишаються короткими й відповідають ролі. Не додавати дублікати одного процесу під різними назвами. Пункти «Поточні» та «Історія» не використовуються як загальні дублікати, якщо сторінка вже має статусні фільтри.

## 6. Універсальна структура сторінки

Рекомендований порядок DOM:

1. page header: eyebrow, title, коротке пояснення;
2. context row: авто/клієнт/номер/VIN/період;
3. filters/search;
4. primary content;
5. secondary content/details;
6. empty/error state;
7. actions у логічному кінці сценарію.

Правила:

- header і toolbar можуть переноситися на 2 рядки;
- action group — `display:flex; flex-wrap:wrap; gap:8px`;
- картка не має фіксованої висоти, якщо текст може бути різним;
- `min-width:0` ставиться на grid/flex children, які містять довгий текст;
- `min-height` використовується лише для стабільності skeleton або touch target;
- `height:100vh` не застосовується до основної сторінки;
- `max-height:calc(100vh...)` не застосовується до списку/detail основного контенту;
- `overflow:hidden` не може приховувати важливий текст, фото, кнопку чи нижній блок.

## 7. Стандарт даних і станів на кожній сторінці

Кожен екран має реалізувати: loading, success, empty, error, forbidden, saving/saved і conflict state. Успішне збереження показується тільки після позитивної відповіді API. Помилка не очищає введені дані.

На екрані завжди зрозуміло:

- яке авто/клієнт відкрито;
- який статус і його текстове значення;
- хто відповідальний;
- що очікується або блокує процес;
- яка наступна дія;
- коли дані оновлено.

## 8. Дозволені внутрішні scroll-зони

Внутрішній scroll є винятком і явно позначається у CSS/ТЗ:

1. modal/dialog/drawer з власним заголовком і доступним close;
2. горизонтальна таблиця, якщо всі колонки не можуть поміститися;
3. planner day/week grid;
4. parts diagram/zoom viewport;
5. gallery/photo viewer;
6. довгий список у спеціалізованому picker, якщо сторінка зберігає контекст і має власні controls.

Не дозволяється робити внутрішнім scroll-ом всю сторінку, detail-панель або сусідні робочі блоки лише для того, щоб зберегти стару висоту.

Для scroll-зони обов'язково:

- `max-width:100%` у батьківському блоці;
- `overscroll-behavior-x:contain` для горизонтальної області;
- видимий контекст колонок/заголовок;
- keyboard і touch доступ;
- на mobile не приховувати єдину основну дію за scroll.

## 10. Спеціальні стандарти CRM

### 10.1. Vehicle header

- показувати модель/рік, держномер, VIN, клієнта і статус workflow;
- VIN є копійованим значенням, не декоративним текстом;
- зображення `object-fit:contain`, без розтягування;
- для laptop 1280–1366px image не повинно займати весь перший екран: цільовий контейнер — до 340×180px, з подальшим fluid зменшенням;
- лінія під зображенням не використовується як декоративний separator між авто та owner, якщо owner є окремим логічним блоком;
- workflow tabs завжди в одному ряду на desktop, на mobile — горизонтальний scroll тільки самої tab-панелі або wrap без обрізання;
- активна сторінка й етап підсвічуються статусним кольором: зелений — завершено/погоджено, жовтий — очікує, червоний — проблема/не розпочато.

### 10.2. Діагностика і ДК

- список діагностик — рядки, клік по рядку відкриває конкретну діагностичну карту;
- не показувати праворуч дубльований preview-блок, який займає половину екрану;
- findings групуються за зоною, але кожна позиція має чіткий рядок, статус і наступну дію;
- «Підбір деталей» доступний після валідного стану ДК і передає конкретні findings;
- фото є доказом конкретної позиції та не повинно розтягувати батьківський layout.

### 10.3. Підбір запчастин

- переходи: головне меню → вибір авто/ДК → підбір; ДК → наступний крок → підбір;
- пріоритет пошуку: VIN, потім номер деталі;
- якщо VIN-пошук не дав однозначного результату — обов'язкове ручне підтвердження;
- однакові деталі **не об'єднувати**: у кожному рядку видно деталь, її місце/позицію, постачальника, артикул, наявність і ціну;
- постачальники можуть додаватися без зміни UI-моделі: `supplier`, `brand`, `article`, `price`, `stock`, `delivery`, `fitment`, `updatedAt`;
- закупівельна ціна × `1,40` застосовується автоматично з налаштувань CRM;
- робота по заміні деталі підтягується з прайсу робіт і перераховується за класом авто;
- для fixed services коефіцієнт застосовується лише якщо в прайсі встановлено «Застосовувати коефіцієнт типу авто»;
- націнка на роботу з деталлю клієнта додається тільки до labor line заміни деталі й береться з налаштувань;
- ручна деталь має маркер «введено вручну» і не маскується під пропозицію постачальника.

### 10.4. Сервісна історія

- верхній контекст авто однаковий із Vehicle record;
- хронологія — вертикальні події без злитого тексту та без сирих технічних назв;
- кожна подія: дата/час, тип, статус, опис, сума/оплата за наявності, deep link;
- фільтри не дублюють «Поточні/Історія», якщо події вже розділені статусом;
- порожня історія має пояснення і CTA, але не виглядає як помилка.

## 11. Доступність і взаємодія

- весь функціональний UI доступний клавіатурою;
- `:focus-visible` має контрастне orange ring;
- icon-only button має `aria-label` і tooltip;
- картка-рядок, яка відкриває сторінку, є `button` або посиланням, не `div` з onClick;
- hover-ефект для рядків: м'який фон, зміна border і легкий рух стрілки до 2px; без миготіння;
- `prefers-reduced-motion: reduce` вимикає transform/animation;
- помилки показуються текстом поруч із полем і в summary для screen reader;
- колір статусу дублюється текстом/іконкою;
- contrast для звичайного тексту — не нижче WCAG AA.

## 12. Продуктивність і стабільність layout

- зображення мають відомі width/height або aspect-ratio, щоб не викликати layout shift;
- hero image завантажується eager лише для відкритого авто, списки — lazy;
- запити списків мають pagination/limit і не тягнуть зайві 500+ записів без обґрунтування;
- під час оновлення зберігається видимий контент, skeleton показується в межах блоку;
- глобальні CSS-правила не повинні змінювати geometry public portal або mechanic cabinet без перевірки їхнього surface contract;
- сторінка не використовує JS для визначення розміру, якщо достатньо CSS container/grid правил.

## 13. Статичні правила code review

Перед merge перевірити:

- немає `width:100vw` у workspace/page layout;
- немає `height:100vh` або `max-height:calc(100vh...)` у головному списку/detail;
- немає page-level `position:fixed/sticky`, що перекриває контент;
- grid children мають `min-width:0`;
- таблиця з min-width має батьківську локальну scroll-зону;
- mobile media query існує для нового multi-column блоку;
- текстовий floor не порушений;
- є loading/empty/error/forbidden states;
- є keyboard focus і accessible labels;
- новий виняток додано в цей документ і в таблицю стандартів.

## 14. QA і критерії приймання

Для кожного модуля з матриці пройти viewport-и 1920, 1440, 1366, 1280, 1024, 768, 390 і 360px:

1. body/workspace не має небажаного горизонтального overflow;
2. заголовок, авто, VIN/номер і primary CTA доступні без browser zoom;
3. нижній контент не обрізаний і до нього можна дійти документним scroll;
4. довгі українські/латинські назви не ламають картку;
5. таблиці мають лише навмисний локальний scroll;
6. hover/focus/reduced-motion працюють однаково;
7. після F5, Back/Forward зберігаються route і контекст;
8. loading/error/empty не змінюють layout так, що кнопки стрибають або зникають;
9. зміна theme/density/radius не повертає overflow;
10. основний сценарій завершується на кожному профілі ширини.
