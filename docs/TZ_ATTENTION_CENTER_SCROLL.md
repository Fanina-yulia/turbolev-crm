# ТЗ: доступ до всіх подій «Центру уваги»

Дата: 2026-10-05. Модуль: `core-platform`. Пов’язаний стандарт: CRM-UI-004.

## 1. Мета

Користувач повинен мати доступ до кожної події, отриманої від API та включеної
до поточного фільтра. Колесо миші, вертикальний жест двома пальцями на тачпаді
та клавіатура мають прокручувати список до останнього запису. Кількість даних
не повинна впливати на доступність нижніх записів.

## 2. Підтверджена причина

У `app/my-tasks.module.css` desktop-сторінка має обмежену висоту й
`overflow:hidden`. Основна колонка була grid-контейнером з `overflow-y:auto`,
але її дочірня панель мала `overflow:hidden`. Автоматичний grid-рядок стискав
панель до видимої висоти. Великий список залишався всередині обрізаної панелі,
а зовнішня колонка не отримувала scrollHeight, достатнього для прокручування.

В ізольованому Chromium на реальному компоненті з 60 тестовими подіями
зафіксовано: висота колонки й scrollHeight — 546 px; внутрішня панель —
543 px заввишки зі scrollHeight 7314 px та `overflow:hidden`.
Це відтворення на тестових даних, а не вимірювання production-акаунта.

Архів не мав визначеної scroll-зони. Додатково UI залишав лише перші 100
архівних задач через `.slice(0,100)`.

## 3. Обсяг

- Основний список «Потребує уваги зараз».
- Архів завершених і скасованих задач.
- Права колонка: завантаженість постів та найближчі події.
- Вузькі, низькі та мобільні viewport.
- Перевірка сусідніх реєстрів на аналогічне обрізання контейнера.

Не змінюються права доступу, джерела сигналів, операції над задачами, порядок
сортування, масштаб CRM 0.90, спільний Page Header і Кабінет механіка.
Не додаються сторонні бібліотеки до runtime-залежностей CRM.

## 4. Desktop-композиція

Для ширини понад 900 px та висоти понад 560 px:

1. Заголовок, KPI та категорії залишаються над робочою областю.
2. Робоча область займає залишок висоти без розтягування сторінки.
3. Основна колонка — flex-контейнер з `min-height:0`.
4. Панель подій — flex-column; її заголовок не стискається.
5. Сам список має `flex:1`, `min-height:0`, `overflow-y:auto`.
6. Рядки списку зберігають висоту за вмістом: `grid-auto-rows:max-content`.
7. Прокрутка основного списку не рухає заголовок сторінки.
8. Права колонка прокручується незалежно; її панелі не стискаються:
   `grid-auto-rows:max-content`.
9. Для архіву використовується така сама схема панель → заголовок → список.
10. Не допускається горизонтальна прокрутка документа.

## 5. Введення та доступність

- Використовується нативна browser-прокрутка без перехоплення `wheel` і
  без `preventDefault` для жестів.
- Контейнери подій і архіву мають `role="region"`, український `aria-label`
  та `tabIndex=0`.
- Сфокусований контейнер має видиму рамку фокуса.
- Стрілки, PageDown/PageUp та Ctrl+End/Home працюють нативно.
- `scrollbar-gutter:stable` резервує місце для смуги прокрутки.
- Видимість самої смуги залежить також від налаштувань ОС; доступність даних
  не повинна залежати від її постійного відображення.

## 6. Фільтри та оновлення

- У головному списку відображаються всі `filteredSignals`, без `.slice()`.
- При зміні KPI або категорії список починається згори: ключ контейнера
  складається з `viewFilter` та `categoryFilter`.
- Фонове отримання даних при незмінних фільтрах не перемонтовує контейнер;
  позиція прокрутки зберігається, якщо це дозволяє нова довжина списку.
- Лічильник у панелі дорівнює числу відображених після обох фільтрів подій.
- Загальні KPI та лічильники категорій зберігають існуючу семантику API;
  вони можуть відрізнятися від перетину двох активних фільтрів.
- Архів показує всі завершені/скасовані задачі з отриманої відповіді API.
  Серверна межа `listTasksForUser` — 500 задач — не змінюється. Ця зміна не
  є пагінацією всієї історії бази даних.
- Блок «Наступні» залишається короткою добіркою до 8 подій; це не основний
  список, і його ліміт не змінюється.

## 7. Адаптивність і крайові стани

- При ширині 761–900 px або висоті до 560 px desktop-сторінка отримує
  загальну вертикальну прокрутку. Вкладені списки мають природну висоту.
- На mobile до 760 px зберігається прокрутка документа і масштаб 1.0.
- Повинні залишатися доступними остання подія, архів, права колонка та
  форма створення задачі.
- Порожній результат, завантаження й помилка не повинні створювати
  недоступну частину інтерфейсу або перекривати фільтри.

## 8. Файли реалізації

- `app/my-tasks.tsx`: іменовані scroll-регіони, ключ фільтра, класи панелей,
  видалення додаткового client-side ліміту архіву.
- `app/my-tasks.module.css`: локальна модель прокрутки, природна висота
  рядків і панелей, focus-стан та fallback для вузьких/низьких екранів.
- `scripts/attention-scroll-browser-smoke.mjs`: відтворюваний браузерний тест.

## 9. Матриця приймання

| Умова | Очікуваний результат |
|---|---|
| 60 подій, 1366×768 та 1280×720 | Колесо прокручує список; Ctrl+End показує останню подію |
| Desktop-прокрутка | Заголовок сторінки залишається на місці |
| Фонове оновлення | Позиція списку зберігається |
| Фільтр «Фінанси» з 30 подіями | 30 записів; позиція скидається до початку |
| 120 архівних задач | Доступна задача №120; немає прихованого ліміту 100 |
| 900×720, 1366×500, 390×844 | Доступні останні записи через адаптивну прокрутку |
| Усі viewport | Відсутня горизонтальна прокрутка документа |
| Права колонка | Панелі зберігають висоту вмісту; нижній вміст доступний |
| Нуль подій | Видимий порожній стан; фільтри доступні |

## 10. Перевірка суміжних сторінок

Переглянуто компоненти й CSS реєстрів Клієнти/Авто, Роботи, Діагностика,
КП/ЗН, Закупівлі, Оплати, Гарантії та Процеси. Вони мають власні scroll-зони.
Ідентичний ланцюг «auto grid row → обрізана панель → непрокручувана зовнішня
колонка» для основних списків цим аудитом не підтверджено. Спільні стилі та
інші сторінки в межах виправлення не змінюються.
Це аудит коду; повний live E2E усіх бізнес-сценаріїв не заявляється.

## 11. Відтворювані тести

Браузерний тест збирає справжні MyTasks, CrmPageHeader і CrmScreenContractFrame
із CSS-модулями та глобальними стилями застосунку. API замінюється синтетичною
відповіддю у локальному браузері. Production-дані не читаються і не змінюються.
Для CSS-модулів відтворюються стабільні фрагменти назв, на які спираються
наявні глобальні правила. Це component integration test, а не Next.js live E2E.

```sh
npm install --no-save --package-lock=false esbuild playwright-core @sparticuz/chromium
node scripts/attention-scroll-browser-smoke.mjs
```

Альтернатива: залежності встановлюються в окрему директорію, шлях до її
`node_modules` передається через `CRM_BROWSER_DEPS`.

Перед публікацією: браузерний тест, `ui:screen-contracts:check`, `ui:scale:check`,
`ui:header:check`, `ui:fonts:check`, `git diff --check` і production build Vercel.

## 12. Публікація та відкат

Зміни публікуються через окрему гілку/PR і merge у main після перевірок.
Публікація підтверджується станом READY для deployment відповідного коміту.
За регресії — revert коміту виправлення з повторною публікацією.
Міграцій бази та змін production-даних немає.
