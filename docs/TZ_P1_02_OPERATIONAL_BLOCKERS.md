# ТЗ P1-02 — Повноцінна сутність Operational Blocker

## Мета

Перетворити blocker із текстової ознаки або локального звернення механіка на єдину операційну сутність CRM. Статус процесу та причина зупинки більше не змішуються: запис/наряд зберігає свій workflow-статус, а `OperationalBlocker` пояснює причину, відповідального та наступну дію.

## Модель даних

- `OperationalBlocker` має код із канонічного довідника, статус `OPEN / ACKNOWLEDGED / RESOLVED / CANCELLED`, пріоритет `LOW / MEDIUM / HIGH / CRITICAL`.
- Обов'язкове джерело: `sourceType + sourceId`; додаткові зв'язки з локацією, записом, Work Order, рядком роботи, автомобілем і клієнтом.
- Пара блокерів з однаковим джерелом і кодом не дублюється в активному стані.
- Зміни мають аудитуватися через `AuditEvent`.

## API

- `GET /api/blockers` — фільтр за локацією, статусом, джерелом, авто, записом, нарядом.
- `POST /api/blockers` — створення або ідемпотентне оновлення активного блокера.
- `GET /api/blockers/:id` — отримання блокера.
- `PATCH /api/blockers/:id` — `ACKNOWLEDGE`, `RESOLVE`, `CANCEL`, `REOPEN`.

Доступ до API вимагає `PRODUCTION.READ/WRITE` і не дозволяє читати або змінювати чужу локацію.

## Життєвий цикл

`OPEN → ACKNOWLEDGED → RESOLVED|CANCELLED`. Закритий блокер можна `REOPEN`, якщо робота знову зупинилася. Дубльований POST оновлює причину та дедлайн існуючого активного запису.

## Інтеграція

- Зупинка роботи механіком створює/оновлює блокер, пов'язаний із `WORK_ORDER_LINE`.
- Рішення менеджера над execution issue закриває відповідний активний блокер.
- Контрольний центр станції читає активні блокери як окремі сигнали.
- Старі `WorkExecutionIssue` не видаляються: вони залишаються журналом комунікації та доказом, а blocker стає операційним джерелом причини зупинки.

## Нефункціональні вимоги

- Дедуплікація захищена транзакцією та advisory lock.
- Обмежені довжини полів і ліміт вибірки.
- Доступ закритий для неавторизованих і нерозподілених користувачів.
- Міграція не змінює існуючі записи.
