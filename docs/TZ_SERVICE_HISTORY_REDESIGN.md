# Технічне завдання

## Модуль «Сервісна історія автомобіля»

### 1. Мета

Зробити історію обслуговування автомобіля зрозумілою з першого погляду. Користувач має бачити не плоский перелік технічних записів, а послідовність сервісних звернень: який візит актуальний, що відбулося під час кожного візиту та яка остання фактична дія.

### 2. Обсяг змін

Оновлюється компонент єдиної хронології, який використовується у:

- персональному розділі автомобіля;
- картці автомобіля у CRM;
- бічній панелі історії замовлення, клієнта або автомобіля.

Джерелом залишаються фактичні події CRM через `/api/vehicles/:id/timeline`, `/api/work-orders/:id/timeline` та відповідні scope-ендпоїнти. Ручні нотатки не повинні підміняти події процесу.

### 3. Нова структура екрана

1. Заголовок «Хронологія сервісу» та лічильники подій і сервісних звернень.
2. Фільтри: «Усі», «Сервіс», «Кошторис», «Запчастини», «QC», «Оплати». Фільтр із нульовим результатом не показується.
3. Легенда кольорів типів подій.
4. Перемикач «Показати технічні події».
5. Список сервісних звернень, відсортований від найновішого до найстарішого.
6. Усередині звернення — події, згруповані за календарною датою в часовій зоні Europe/Kyiv.

Кожне звернення має виразний заголовок:

- «Поточний візит» для найновішої групи;
- «Сервісний візит» для попередніх груп;
- номер звернення, кількість подій і час останньої події;
- дію «Відкрити звернення», якщо користувач перебуває у контексті автомобіля або клієнта.

### 4. Правила групування

- Події з однаковим `workOrderId` належать до одного сервісного звернення.
- Події без `workOrderId` групуються за автомобілем і локальною календарною датою, щоб вони не створювали помилковий окремий ремонт.
- Групи та події всередині них сортуються за `occurredAt` у напрямку від нових до старих.
- Дата показується один раз для групи подій одного дня.
- Час події завжди показується окремо у форматі години та хвилини; повна дата доступна у підказці.
- «Поточний візит» — це найновіша група подій, а не просто остання подія.

### 5. Типи подій і візуальна система

| Тип | Приклади | Відображення |
|---|---|---|
| Сервіс | запис, прибуття, зміна статусу | сірий / синій |
| Діагностика | карту створено, карту підтверджено | фіолетовий |
| Кошторис | створено, відправлено, погоджено, відхилено | жовтий |
| Запчастини | підібрано, замовлено, отримано, встановлено | блакитний |
| Роботи | погоджено, розпочато, завершено | помаранчевий |
| QC | контроль якості розпочато або завершено | бірюзовий |
| Оплата / фінанси | платіж, фіналізація фінансів | зелений |
| Технічні | службові системні події | нейтральний, приховано за замовчуванням |

Колір не є єдиним носієм змісту: кожна подія додатково має текстову назву типу та піктограму.

### 6. Поведінка та навігація

- Перемикання фільтра відбувається без перезавантаження сторінки.
- Під час завантаження показується спокійний стан «Завантажую історію…».
- Помилка API показується окремим повідомленням і не маскується під порожню історію.
- Порожній результат фільтра має текст «Подій за цим фільтром поки немає».
- «Відкрити звернення» переходить у відповідний контекст комерційної пропозиції / замовлення з вкладкою історії.
- У контексті конкретного замовлення кнопка не дублює перехід, а показує номер звернення як текст.

### 7. Продуктивність

- Один екран використовує один агрегований timeline-запит для вибраного scope.
- На клієнті не виконується додатковий запит на кожну подію.
- Список обмежується серверним `take` та клієнтським `limit`; базова межа — 120 подій, для повної картки автомобіля — до 220.
- Фільтрація, групування та формування лічильників виконуються через `useMemo`.
- Медійні файли у хронології не завантажуються; історія містить лише дані подій і переходи.
- Подальше розширення має додати cursor-пагінацію за `occurredAt`, індекси для `vehicleId`, `workOrderId`, `createdAt` та агрегування подій на рівні API.

### 8. Контракт події

Обов'язкові поля: `id`, `occurredAt`, `kind`, `title`.

Контекстні поля: `workOrderId`, `workOrderNumber`, `vehicleId`, `clientId`, `plateNumber`, `actor`.

Фінансові поля: `amount`, `currency`.

`occurredAt` — час фактичної події. `createdAt` може використовуватися лише як резервний час створення запису і не повинен видаватися за час виконання робіт.

### 9. Адаптивність і доступність

- На десктопі дата розташована зліва, вертикальна лінія — у центрі між датою та карткою події.
- На вузьких екранах дата переходить над подіями, без горизонтального скролу всієї сторінки.
- Фільтри можуть прокручуватися горизонтально всередині власного контейнера.
- Кнопки мають зрозумілий текст, `:focus-visible` і мінімальну зону натискання 44×44 px.
- Іконки є декоративними, а зміст дублюється текстом; структура читається скрінрідером.
- Шрифт інтерфейсу не нижче 11 px.

### 10. Критерії приймання

- Користувач одразу відрізняє поточний візит від попередніх.
- Події одного сервісного звернення не змішуються з іншим зверненням.
- Хронологія всередині звернення читається зверху вниз: від останньої дії до попередніх.
- Фільтри коректно рахують і показують події.
- Технічні події не перевантажують основний сценарій і доступні окремим перемикачем.
- Клік по зверненню відкриває правильний контекст CRM.
- Порожній, завантажувальний та помилковий стани відображаються окремо.
- Інтерфейс не ламається на мобільному екрані та при збільшенні масштабу браузера.
- TypeScript, production build і наявні contract/CI-перевірки проходять без помилок.
